# Feature Specification: Zero-Friction Install Surfaces (Experiment E7)

**Feature Branch**: `121-install-surfaces` (worktree branch; spec number 121 chosen because 118 and 119 are already taken by sibling branches `118-auto-rescan-on-change`, `118-pin-visibility-boundary`, `119-day-two-activation`)
**Created**: 2026-10-20
**Status**: Draft. All clarifications self-answered (see Clarifications). Cross-model review verdicts are recorded in [review-log.md](review-log.md).
**Input**: Experiment E7 from the Q4 2026 growth research pass (approved by the maintainer): competitors win on distribution — Docker MCP Toolkit is zero-install, 1MCP has `cli-setup --codex/--claude`, mcpm.sh ships a curl one-liner and `llm.txt`. MCPProxy's official-registry entry has `packages: []`, so registry-fed catalogs show no install action; there is no winget, scoop or chocolatey package; there is no agent-readable install prompt (`llms.txt` and `llms-full.txt` are already generated by the docs build, but neither leads with install guidance and `llms-full.txt` is ~3 MB); and no one can tell, from telemetry, which install channel a running install came from.
**Related**: Spec 079/092 (install-channel detection and update guidance, `internal/updatecheck`), Spec 111 (Personal-edition Docker image — spec only, nothing published), `docs/mcp-registry-publishing.md`, `docs/release-runbook.md`, `docs/features/telemetry.md`.
**Success measure (E7)**: at least 10 attributable installs per month for each new surface (registry, winget, scoop, agent prompt), read from the install-channel telemetry this spec adds.

## Context & Motivation

Windows is 14% of active installs and rising; Claude Desktop (reached through an `mcp-remote` bridge) is 18%. A Windows user today must find the GitHub release page, pick the right `.exe`, and click through an installer. A user browsing the official MCP registry, or a catalog fed by it, sees MCPProxy with no install action at all. An agent (Claude Code, Codex) asked "install mcpproxy" has no single page that tells it how.

Four surfaces fix this, and a fifth (telemetry) makes them measurable:

| Surface | What a person or agent gets |
|---|---|
| A. Registry packages | The official MCP registry entry carries a runnable package, so registry-fed catalogs show an install action |
| B. Windows package managers | `winget install` and `scoop install` work and stay current on every release without a person in the loop |
| C. Agent-readable install | A paste-into-your-agent prompt, plus the existing `llms.txt` / `llms-full.txt` hardened (install-first ordering, bounded size, no unpublished pages), so an agent can install, start and connect MCPProxy on its own |
| D. Install-channel telemetry | The heartbeat says which channel the install came from, as a closed bucket, never free text |
| E. `.mcpb` bundle | **Out of scope** — only a follow-up note with the open questions |

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Registry entry shows an install action (Priority: P1)

A person (or a catalog that mirrors the official MCP registry) opens the `io.github.smart-mcp-proxy/mcpproxy-go` entry and sees a package they can run, not an empty list.

**Why this priority**: it is the cheapest surface (data, no new code path), it unblocks every registry-fed catalog at once, and the current empty list is an outright defect in how MCPProxy presents itself.

**Independent Test**: validate `server.json` with the registry's own publisher validator (offline) and publish dry-run output; after a real stable release, `GET /v0/servers?search=mcpproxy&version=latest` returns a non-empty `packages` array.

**Acceptance Scenarios**:

1. **Given** the committed `server.json`, **When** it is validated against the registry's schema and semantic rules, **Then** validation passes with a non-empty `packages` array.
2. **Given** a stable release tag `vX.Y.Z`, **When** the registry publish step runs, **Then** the package identifier references the image tag published for that same release, and the step runs only after that image is pushed.
3. **Given** the published container image, **When** its labels are inspected, **Then** it carries the registry's ownership label whose value equals the `server.json` name (the registry rejects the publish otherwise).
4. **Given** the image tag for the release is missing or lacks the label, **When** the publish step runs, **Then** it fails fast with a message naming the cause instead of publishing a broken entry (the step stays non-blocking for the release, as today).
5. **Given** a release candidate tag, **When** the release workflow runs, **Then** nothing is published to the registry (unchanged).
6. **Given** the recovery workflow (`retry-sign-release.yml`) republishes a release, **When** its registry step runs, **Then** it uses the same stamping and pre-publish checks as the main release (one shared script), so a stale committed identifier can never reach the registry.
7. **Given** the declared package, **When** it is started with exactly the environment, arguments and port mapping that `server.json` declares, **Then** a client can complete an MCP `initialize` handshake against it (smoke test run before publishing).

### User Story 2 — Windows user installs with one command (Priority: P1)

A Windows user runs `winget install smart-mcp-proxy.mcpproxy` or `scoop install mcpproxy` (after adding the bucket) and gets a working install; it updates with the package manager's normal upgrade command.

**Why this priority**: Windows is the fastest-growing platform and the only major platform without a package-manager install.

**Independent Test**: render both manifests from a real past release's assets in a scratch directory and validate them (schema validation for winget, JSON validity plus hash/URL checks for scoop); run the release jobs in dry-run mode on a non-release ref.

**Acceptance Scenarios**:

1. **Given** a stable release, **When** the release workflow completes, **Then** a scoop manifest for that version (zip archive URL and SHA-256 taken from the release's checksum file) is pushed to the bucket repository, with no human step after the one-time setup.
2. **Given** a stable release, **When** the release workflow completes, **Then** a winget manifest update for that version is submitted to the community winget repository as a pull request, with no human step after the one-time bootstrap.
3. **Given** the one-time setup has not been done (bucket repository or token missing), **When** the release workflow runs, **Then** the Windows jobs skip with a visible notice and the release is not failed.
4. **Given** a release candidate tag, **When** the workflow runs, **Then** neither manifest is published.
5. **Given** a scoop install, **When** the user upgrades with `scoop update mcpproxy`, **Then** the bucket's own autoupdate metadata resolves the next version without edits.
6. **Given** a scoop-installed binary, **When** `mcpproxy update` runs, **Then** it does NOT self-replace the scoop-owned executable and instead tells the user to run `scoop update mcpproxy` (the zip's weak `tarball` stamp must not make a package-manager-owned file self-updatable).
7. **Given** the recovery workflow re-runs a release, **When** it completes, **Then** the Windows package jobs can be re-run for that tag via the same reusable workflow (manual dispatch with a tag input).
8. **Given** the installer runs silently (as winget runs it), **When** any warning dialog would normally appear (e.g. PATH length), **Then** none blocks the install.

### User Story 3 — An agent installs MCPProxy from one prompt (Priority: P1)

A person pastes a self-contained prompt from the README (or docs page) into Claude Code or Codex. The agent installs MCPProxy for the current OS, starts it, and runs the connect flow for the client it is running in.

**Why this priority**: this is the "zero-friction" demo and the surface competitors already have. It also costs no product code.

**Independent Test**: run the prompt verbatim in a fresh Claude Code session in a scratch directory with `HOME` and the listen port isolated; the agent ends with MCPProxy running on the isolated port and a connect dry-run/preview for its own client.

**Acceptance Scenarios**:

1. **Given** the README, **When** a reader looks for an install shortcut, **Then** a clearly marked "Paste this into your agent" block is present with the prompt in a copyable code fence.
2. **Given** the prompt, **When** an agent follows it on macOS, Linux or Windows, **Then** it selects the right installer (Homebrew/winget/scoop/release archive), verifies the install, starts the service, runs `mcpproxy connect <client>` for the client it is running in, and tells the user the truthful follow-up (reload/restart that client) — it never claims a live connection it has not observed.
3. **Given** the prompt, **When** it is read, **Then** it never asks the agent to run something that overwrites an existing running install without confirming, and states the verification commands and expected outputs.
4. **Given** the docs site, **When** `/llms.txt` and `/llms-full.txt` are requested, **Then** they list the install guidance first, cover the published pages only (never the explicitly excluded internal documents), and are produced by exactly one generator (the existing plugin, tuned — no second generator).
5. **Given** the docs build, **When** the install page links are checked, **Then** the build still passes (no broken links) and the new page(s) are reachable from the sidebar.

### User Story 4 — The maintainer can see which channel installs come from (Priority: P2)

The heartbeat carries `install_channel`, a closed enum, so the E7 success measure (≥10 installs/month per surface) can be read from telemetry.

**Why this priority**: it makes the experiment measurable, but is only useful once surfaces ship; it is also the only Go change.

**Independent Test**: table-driven unit tests over every enum value and every override source; a payload-privacy test proving no free text or path can reach the payload.

**Acceptance Scenarios**:

1. **Given** any running install, **When** the heartbeat is built, **Then** `install_channel` is exactly one value of the closed set: `brew`, `dmg`, `winget`, `scoop`, `windows-installer`, `deb`, `rpm`, `docker`, `registry`, `curl`, `tarball`, `go-install`, `unknown`.
2. **Given** an install whose channel the existing detector already knows (Homebrew, DMG, deb, rpm, docker, Windows installer, tarball, go install, and the new scoop), **When** no explicit declaration exists, **Then** the detector's answer is reported, mapped onto the closed set.
3. **Given** an *authoritative* declaration (the `MCPPROXY_INSTALL_CHANNEL` environment variable, accepting any set member except `unknown`; or an installer-owned `install-channel` marker file next to the executable, accepting only `winget`) whose value is valid for its source, **When** the heartbeat is built, **Then** the declared value wins; **Given** an out-of-set value, **Then** it is ignored and never transmitted.
4. **Given** a *weak* declaration (a marker file in the data directory containing only `curl`, written by the agent prompt for archive installs), **When** the detector's answer is `tarball`, `go-install` or `unknown`, **Then** the declared value is reported; **When** the detector positively identified a package-manager/installer channel, **Then** the weak declaration is ignored (a stale `curl` marker cannot mask a later Homebrew or winget install).
5. **Given** a winget install, **When** the installer ran with the winget switch, **Then** the marker file written beside the installed executable makes the heartbeat say `winget`; **When** the installer later runs without the switch (direct reinstall/upgrade), **Then** the stale marker is removed; **When** the app is uninstalled, **Then** the marker is removed with it.
6. **Given** telemetry is disabled, **When** the process runs or a payload preview is requested, **Then** no usage heartbeat is sent and no marker is read by the telemetry path (the existing one-time opt-out beacon is unchanged).
7. **Given** a user-facing surface that already shows the install channel for update guidance (`/api/v1/info`, `mcpproxy status`, `mcpproxy doctor`, `mcpproxy update`), **When** this feature ships, **Then** their behavior is unchanged for every existing channel; the only change is the new scoop channel (guidance `scoop update mcpproxy`, no self-update).

The field means the *current* install channel as last declared or detected, not the original acquisition channel. Counting "new installs per month" uses the dashboard's first-seen date per machine, not recurring heartbeats.

### User Story 5 — `.mcpb` bundle is scoped for later (Priority: P3)

The maintainer has a written follow-up note listing the open design questions for a Claude Desktop `.mcpb` bundle, so the next spec starts from decisions rather than discovery. **No bundle is built or published by this feature.**

**Acceptance Scenarios**:

1. **Given** the spec directory, **Then** `followup-mcpb.md` exists and lists the open questions and a recommended starting position.

### Edge Cases

- **Immutability**: the registry stores each version once; a failed or partial publish for version X.Y.Z cannot be corrected by republishing X.Y.Z. The pre-publish checks (US1-4) exist to prevent shipping a bad entry that can never be replaced.
- **Image tag spelling**: the container image is tagged with the git tag including the leading `v` (`vX.Y.Z`), while the registry `version` has none. The identifier must use the image's real tag.
- **Private image**: a package first created by the CI token starts private; an anonymous pull must be verified, because a private image makes the registry entry unusable.
- **Server-edition image**: the only published image today is the Server edition (distroless, no shell, no Node/uv). The registry package describes what it is; a Personal-edition image (Spec 111) will supersede it for most users and is a follow-up, not a dependency.
- **Winget bootstrap**: the winget automation can only update a package that already exists in the community repository; the first submission is manual and moderated by Microsoft (review latency days to weeks).
- **Windows installer needs admin and a fixed silent-install contract**: winget runs the installer silently; the installer must accept the winget channel switch without prompting.
- **Same artifact, several channels**: winget and a direct download use the same installer; the Docker image and the registry package are the same image. Only an explicit declaration can tell them apart, which is why declarations are first-class.
- **Marker file tampering / garbage**: unreadable, oversized, or out-of-set marker content degrades to detection; it must never be transmitted raw.
- **Idempotent regeneration**: `llms.txt` generation run twice on the same input yields byte-identical output (no timestamps).
- **Secrets in prompt/docs**: the install prompt never embeds an API key and never asks the agent to read or print the config file, the instance admin key, or a client credential. `mcpproxy connect` writes a per-client credential itself and returns it masked; verification uses CLI commands that return sanitized output. The PR evidence is redacted the same way.
- **Existing running install**: the prompt and docs must not reinstall over a running local MCPProxy without telling the user; the verification step checks for an existing install first.

## Requirements *(mandatory)*

### Functional Requirements

**Registry (A)**

- **FR-001**: `server.json` MUST contain at least one package of a registry-supported type, validated by the registry's own publisher validator.
- **FR-002**: The package MUST reference the published Server-edition container image by an explicit tag equal to that release's image tag, with the correct transport and the port/ listen-address settings needed to reach it.
- **FR-003**: The published image MUST carry the registry ownership label with value equal to the `server.json` `name`, set in the image build so it holds for every future build.
- **FR-004**: One shared script MUST stamp `version` and the package identifier from the release tag at publish time; both the main release workflow and the recovery workflow MUST use it, and the publish MUST remain ordered after the image push (already transitively true in the main workflow; MUST be preserved).
- **FR-005**: Before publishing, the workflow MUST verify the target image tag exists, is anonymously pullable, and carries the label, and MUST run the package's smoke test (start with the declared environment/port, complete an MCP `initialize`); on failure it MUST print the cause and skip the publish without failing the release.
- **FR-006**: RC tags MUST NOT publish to the registry (unchanged).
- **FR-007**: A repository check (test or script run in CI) MUST fail if `server.json` loses its `packages`, if its `name` differs from the label in the image build, or if its schema validation fails.

**Windows package managers (B)**

- **FR-010**: A scoop manifest MUST be generated from each stable release's archive asset and its published SHA-256, include `checkver`/`autoupdate` metadata, expose the core binary on PATH, and be pushed to a bucket repository without human action.
- **FR-011**: A winget manifest update MUST be submitted to the community winget repository for each stable release, using the signed installer asset, without human action after one-time bootstrap.
- **FR-012**: Both jobs MUST run only for stable tags, MUST depend on the release having published its assets, and MUST skip (not fail) with a visible notice when their credentials or target repositories are not configured.
- **FR-016**: A new `scoop` channel MUST be recognized by the existing detector from the scoop apps directory layout of the resolved executable path, MUST take precedence over the weak `tarball` stamp, and MUST map to update guidance `scoop update mcpproxy` with no self-update.
- **FR-017**: The Windows package jobs MUST live in one reusable workflow invoked by the release workflow and manually dispatchable with a tag input, so a recovered or re-run release can republish them idempotently (re-submitting an existing version is a no-op or a clearly reported skip).
- **FR-013**: The manifest generation logic MUST be a script runnable locally against any released tag, with a test that renders manifests from fixture data and validates them; the release job calls the same script.
- **FR-014**: The Windows installer MUST accept a channel switch that records the winget channel as a marker file beside the installed executable, MUST remove a stale marker when run without the switch and on uninstall, and MUST NOT show any blocking dialog in silent mode (including the existing PATH-length warning).
- **FR-015**: Documentation MUST list the exact one-time human steps (create the bucket repository, create and store the tokens, perform the first winget submission) and the install/upgrade/uninstall commands for each Windows channel.

**Agent-readable install (C)**

- **FR-020**: README and a docs page MUST contain a "Paste this into your agent" prompt that is self-contained: OS detection, install via Homebrew / winget / scoop / release archive (checksum-verified), existing-install check, start, verification with sanitized CLI output only, and `mcpproxy connect <client>` for the agent's own client, ending with the truthful reload/restart instruction. Claude Desktop (not in the CLI client list) is directed to the Connect wizard in the Web UI.
- **FR-021**: The prompt MUST be a single source of truth: the README block and the docs page are generated from, or checked against, one file so they cannot drift (a test fails if they differ).
- **FR-022**: The existing docs-build generator (the Docusaurus llms plugin) MUST be tuned, not duplicated: install guidance first, internal/excluded pages absent, and `llms-full.txt` bounded in size by excluding generated reference pages that are not useful to an agent. Exactly one generator MUST own these files.
- **FR-023**: A post-build check MUST fail the docs build if either file is missing, if the install page is not first, if an explicitly excluded document appears, or if `llms-full.txt` exceeds the documented size budget.
- **FR-024**: The prompt MUST be verified end-to-end by running it in a fresh agent session against an isolated instance (separate port, scratch data directory, scratch config, sandboxed HOME) without touching the maintainer's live install; the evidence (redacted of any credential) is recorded in the PR. "Connected" in this spec means: the client's config entry is written and `connect --list` shows it; a live handshake is proven by the isolated harness, not claimed by the prompt.

**Install-channel telemetry (D)**

- **FR-030**: The heartbeat MUST include `install_channel`, a member of the closed set listed in US4, with the payload documentation updated. The field is purely additive and always populated (worst case `unknown`), so the schema version is NOT bumped (avoids a merge collision with concurrent specs that bump it; consumers detect the field by presence).
- **FR-031**: Resolution order MUST be: (1) environment declaration, (2) installer-owned marker beside the executable, (3) the existing detector, (4) the data-directory marker only when (3) answered `tarball`, `go-install` or `unknown`; each explicit source MUST be validated against the closed set, an invalid value falls through, and the marker read MUST be size-capped and happen only on the telemetry-enabled path.
- **FR-032**: The mapping from the existing detector's identifiers to the telemetry set MUST be total and tested for every detector identifier (Homebrew→`brew`, Windows installer→`windows-installer`, etc.), and an unrecognized identifier MUST map to `unknown`.
- **FR-033**: The scoop channel MUST be recognized without any declaration (FR-016).
- **FR-034**: The registry package MUST declare the registry channel through the package's environment variable list so a container started from the registry entry reports `registry`.
- **FR-035**: No path, file content beyond the enum token, hostname or user name MAY reach the payload; the existing payload privacy test MUST cover the new field.
- **FR-036**: Existing install-channel behavior used for update guidance (`/api/v1/info`, `status`, `doctor`, `update`) MUST remain unchanged for every existing channel; declarations and the weak data-directory marker affect only the telemetry mapping, which is a separate function. The only guidance change is the new scoop channel (FR-016).
- **FR-037**: The receiver and dashboard repositories are outside this repository; the PR MUST list the receiver/dashboard change needed to store and chart the new field and MUST confirm the receiver accepts unknown fields in the meantime.

**Follow-up note (E)**

- **FR-040**: `followup-mcpb.md` MUST capture the open questions for the `.mcpb` bundle; no bundle code, workflow or manifest is added.

### Key Entities

- **Install channel**: a closed, low-cardinality label for how a running install was obtained. Attributes: token (enum), source of the answer (declaration vs detection — internal, not transmitted).
- **Channel declaration**: an explicit statement of the channel — environment variable or `install-channel` marker file — containing exactly one token.
- **Package entry**: one element of `server.json` `packages`, describing a runnable distribution of the server for registry consumers.
- **Distribution manifest**: a generated, version-specific description of a release for a package manager (winget manifest set, scoop manifest).
- **Agent install prompt**: the single-source text that instructs an agent how to install, start and connect MCPProxy.
- **llms index / llms full text**: generated, deterministic documents describing the published docs for language models.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: After the first stable release containing this feature, the official registry returns a non-empty `packages` array for the latest MCPProxy version.
- **SC-002**: A Windows user can install MCPProxy with one winget command and one scoop command (after one `bucket add`), and upgrade with the package manager's upgrade command, with zero maintainer actions per release after one-time setup.
- **SC-003**: Pasting the README prompt into a fresh Claude Code session in a scratch environment results in a running isolated MCPProxy with the client's entry configured and the correct reload instruction reported, with no further human input beyond approving tool permissions, and with no credential in the transcript.
- **SC-004**: `llms.txt` and `llms-full.txt` are served from the docs site, list install guidance first, contain 0 explicitly excluded documents, and `llms-full.txt` stays under the documented size budget.
- **SC-005**: 100% of heartbeats carry an `install_channel` that is in the closed set; 0 values outside it in the payload tests; the `unknown` bucket is below 40% of installs one month after release (read from telemetry — the measure of whether detection and declarations are adequate).
- **SC-006**: E7 experiment target: at least 10 attributable *new* installs (first-seen machines) per month for each of registry, winget, scoop and agent-driven archive installs (`curl`), evaluated one month after the first release that ships them. Agent-driven installs through Homebrew/winget/scoop are attributed to those channels, not to the prompt; this is a known limit of a single-valued enum.
- **SC-007**: Lint (both tag sets), unit tests with race detection, the API end-to-end script and the docs build all pass; no existing install-channel test changes.

## Assumptions

- The Server-edition image is the only published image at the time of writing (verified: only `mcpproxy-server` is pushed by the release workflow; Spec 111's Personal image is spec-only). The registry entry therefore points at it; swapping to the Personal image is a one-line follow-up once Spec 111 ships.
- The registry has no raw-binary package type; the only archive-style type is `mcpb` (a Claude Desktop bundle), which is out of scope. Therefore binary release assets are not listed in `packages`.
- The registry validates the OCI ownership label at publish time against the exact tag in the identifier; therefore the first release carrying the label is the first that can publish packages (already-published versions are immutable and stay package-less).
- Winget automation uses an established, SHA-pinned community action that wraps the official manifest tooling; its first submission for a new package id must be manual. Winget's installer type for the existing signed installer is `inno`.
- Scoop installs the release zip archive (core + tray executables), not the installer, so scoop installs do not need admin rights and are path-identifiable.
- `llms.txt` / `llms-full.txt` are already live (verified 2026-10-20: HTTP 200, 39 KB and ~3 MB) via `docusaurus-plugin-llms` configured in `website/docusaurus.config.js`; this spec tunes that generator rather than adding another.
- The recovery workflow `retry-sign-release.yml` carries its own registry-publish job and must share the new stamping script.
- The Server-edition image was smoke-tested for this spec: it starts, serves `/mcp` on 8080 and registers an MCP session with no extra configuration.
- Telemetry receiver and dashboard live in other repositories (`mcpproxy-telemetry`, `mcpproxy-dash`); they tolerate unknown payload fields, and extending them is a tracked follow-up, not part of this PR.
- Chocolatey is deliberately not included (no demand signal; moderation overhead); revisit if winget+scoop prove out.
- The `curl` channel means "installed from the release archive by an agent or script following the documented prompt"; it is declared by the prompt writing a marker file into the data directory, so it is attributable but self-reported.

## Out of Scope

- The `.mcpb` Claude Desktop bundle (follow-up note only).
- A Personal-edition Docker image (Spec 111).
- Chocolatey, apt/dnf repository changes, Nix, AUR.
- Receiver / dashboard changes (listed in the PR as follow-ups).
- Any change to update-guidance behavior or to the existing channel detector's public results.

## Clarifications

### Session 2026-10-20 (self-answered, per the zero-interruption policy)

- Q: Which image does the registry package point at? → A: `ghcr.io/smart-mcp-proxy/mcpproxy-server` (the only published image), tag = the release's image tag with its leading `v`. The Personal image from Spec 111 replaces it later.
- Q: Does the registry support a binary-release package type? → A: No (`npm`, `pypi`, `nuget`, `cargo`, `oci`, `mcpb`). So binaries are not listed; `mcpb` is the follow-up.
- Q: How is the OCI ownership proven? → A: An image label/annotation `io.modelcontextprotocol.server.name` equal to the `server.json` name, set in the Dockerfile and the build step's labels; checked by the registry at publish time.
- Q: Winget: installer exe or zip-portable? → A: The signed installer (`inno`), because it carries the tray app, Start-menu entry and PATH registration users expect; portable would lose the tray. The installer therefore needs a channel switch for attribution.
- Q: Scoop: bucket repo or manifest in this repo? → A: Bucket repository `smart-mcp-proxy/scoop-bucket` fed by the release workflow (this repo cannot commit manifests after tagging without a write-back), plus docs; the one-time human step is creating the repository and token.
- Q: Which winget automation? → A: A SHA-pinned winget-releaser action on an Ubuntu runner (no Windows runner minutes); needs a classic PAT with public-repo scope and a fork of `microsoft/winget-pkgs`.
- Q: How are `curl`/`registry`/`winget` distinguished from `tarball`/`docker`/`windows-installer`? → A: Explicit declarations (env var, marker file) take precedence over detection, validated against the closed set; detection still answers when nothing is declared.
- Q: Should the install prompt hit a hosted install script? → A: No new hosted script; the prompt tells the agent to use the package manager or the release archive and verifies checksums from `checksums.txt`. Avoids a new trusted-remote-code surface.
- Q: Does `llms.txt` come from the Docusaurus build or a script? → A: A deterministic generation step in the docs build (script reading the docs include allowlist and sidebar), output into the static directory before `docusaurus build`; failing on missing pages.
- Q: Telemetry privacy risk of the marker? → A: Only the enum token is ever read and transmitted; file size capped; non-members discarded.
