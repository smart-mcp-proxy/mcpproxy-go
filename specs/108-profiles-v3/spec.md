## Context & Motivation

A profile today (`ProfileConfig{Name, Servers}`, `internal/config/profiles.go:12`) is a list of servers. Spec 057 made it addressable (`/mcp/p/<slug>`, `set_profile`), Spec 105 made every MCP surface intersect token scope with profile scope. What a user actually wants from a profile — "Cursor may only *read* my work servers" — cannot be expressed:

| # | Finding | Today | Consequence |
|---|---|---|---|
| P1 | Header "Profile:" switcher (Web UI) and tray "Profile" submenu | call `PUT /api/v1/profiles/active`, documented as a UI default that "does not affect live MCP sessions" (`internal/httpapi/profiles.go:182`) | Users believe they scoped their agents; they did not |
| P2 | Profiles are config-file only | REST = list + UI default; no CLI group, no MCP admin tool, no UI editor | Feature undiscoverable; no way to change a client's scope from any surface |
| P3 | No tool tier on profiles; unannotated tools count as read | `contracts.DeriveCallWith` defaults to read (`internal/contracts/intent.go:223`) | A "read-only" scope lets an unannotated `delete_repo` through |
| P4 | Connected clients have no identity | connect writes the same `/mcp` URL with no credential or the instance **admin API key** (`internal/connect/connect.go:252`, `clients.go:379-443`) | Cannot bind a profile to "Cursor"; cannot tell Cursor's calls from Codex's; every agent may hold a key that opens the REST admin API. **What this spec fixes**: no new write of the admin key (FR-024); pre-existing copies are closed only when the operator runs the previewed bulk upgrade and then rotates the admin key (FR-025) — until then they are reported on every surface, never silently tolerated |
| P5 | Four profile sources (pin, URL, `set_profile`, none) + a fifth UI default; none shown | `profile_resolver.go:239` | Nobody can tell which profile a call ran under or why |
| P6 | Grids cannot be filtered by client/profile; pages barely link | `ActivityRecord` has no profile/client fields (`activity_models.go:190`); only `Activity.vue` reads one URL filter (`?session=`) | "What did Codex do today?" is unanswerable |
| P7 | Agent tokens duplicate profiles | token `allowed_servers` + `permissions` + `profile_pin` intersect (`auth/agent_token.go:50-58`) | Two overlapping scope systems; Web UI and macOS cannot set a pin at all, only the CLI can |

The surface inventories (Web UI, macOS, CLI, MCP/REST) confirm each surface today offers a *different* subset: the CLI can pin a token to a profile, the Web UI and macOS cannot; the tray and the Web UI both render the misleading switcher; no surface can create a profile. This spec makes **profile** the single unit of scope, binds it to **clients** through per-client credentials, enforces it on every MCP surface, records it on every activity record, and specifies every capability identically for all four surfaces.

## Scope Boundary *(read before planning)*

| Already exists (reused, not rebuilt) | Extended by this spec |
|---|---|
| Profile slug rules, reserved slugs, warn-skip of unknown servers (Spec 057 FR-007/015) | Profile gains optional policy fields; legacy entries load and behave unchanged |
| Profile resolver precedence pin > URL > `set_profile` > none (`profile_resolver.go`) | Adds client-binding and `anonymous_profile` tiers and `switchable_to` limits |
| Token ∩ profile server-scope intersection on `retrieve_tools`, `describe_tool`, `call_tool_*`, `code_execution`, `/mcp/all` (Spec 105) | Adds the profile **tool policy** (tier cap, rules, unannotated handling) at the same choke points |
| Target-tier resolution from annotations (`tierForAnnotations`, `mcp_code_execution.go:1653`) | Reused as the tool's intrinsic tier; profile policy evaluated on top |
| Cache provenance stamps (Spec 105 `cache_authz.go`) | Stamp gains the profile policy fingerprint |
| Agent tokens with `profile_pin` (CLI-only today) | Token gains `client_id`, `kind`, `profile_mode`; every surface can set the profile |
| `metadata.client_name` / `metadata.profile` on activity (best-effort) | Promoted to first-class, filterable fields with provenance |
| `tools/list_changed` push on config reload (`mcp_routing.go`) | Also sent to the live sessions of a reassigned client |

**Editions.** Profile policy, enforcement, attribution and filters apply to both editions and the profile object carries no edition-specific field. Client bindings (which write local client config files) are **personal edition only**; the server edition keeps its administrator-created agent tokens (`POST /api/v1/tokens`, registered in both editions), which can be bound to a profile through the token dialog/`token create --profile`, and its per-user tokens (Spec 024/107, `POST /api/v1/user/tokens`), which **cannot** carry a profile in this spec — adding `profile` to that route is a listed follow-up (research D22, tasks.md Follow-ups). Server-edition `/api/v1/clients` returns `404` (route not registered).

**Transport.** HTTP MCP endpoints `/mcp`, `/mcp/all`, `/mcp/call`, `/mcp/code`, `/mcp/p/<slug>` and legacy aliases. Native stdio remains local-administrator-only and unscoped (unchanged; out of scope). The tray socket remains an administrator identity.

## Definitions *(binding)*

- **Profile**: a named scope = server set + tool policy + session capabilities. Identified by its slug (`name`); `title` is display-only.
- **Legacy profile**: a profile entry that sets none of the v3 policy fields (`max_tier`, `unannotated`, `tools`, `code_execution`, `management_tools`, `switchable_to`). It behaves exactly as under Specs 057/105. `title` and `description` are display-only: setting them never makes a profile non-legacy (data-model §1 `IsLegacy()` is defined over exactly these six policy fields).
- **Tier**: `read` < `write` < `destructive`. A tool's **intrinsic tier** is derived from its effective annotations (upstream annotations, then per-server `annotation_overrides` once PR #1323 lands): `destructiveHint=true` → destructive; `readOnlyHint=false` → write; `readOnlyHint=true` → read; neither hint → **unannotated**. This mapping is computed by exactly one function, Spec 109-a's `contracts.AnnotationTier` (its FR-028), which `profile.IntrinsicTier` calls through an exhaustive adapter (data-model §2) — so Web, macOS, CLI, MCP tier labels and profile enforcement can never disagree, and 108-a merges after 109-a (research D30). A tool whose identity cannot be resolved is destructive (unchanged).
- **Profile tier** of a tool under a profile: its intrinsic tier; if unannotated, the profile's classification for that tool if one exists, else the profile's `unannotated` policy (`deny` → not admitted, `as_write` → write, `as_read` → read).
- **Profile decision** for a tool: `admitted` or `excluded(reason)`, reason ∈ {`server_not_in_profile`, `denied_by_rule`, `unannotated_hidden`, `above_tier_cap`}, computed by one predicate (FR-010).
- **Client**: an AI tool that talks to MCPProxy and is identified by a **client credential** — an agent token of kind `client` minted for exactly one `client_id` (e.g. `cursor`, `claude-code`, or a user-named custom id). A connection with no credential is **unidentified**.
- **Client binding**: the (client, profile, mode) triple, where mode is `locked` (the agent can never change its profile) or `switchable` (the agent may `set_profile` among the bound profile's `switchable_to`). Stored on the client credential, so the binding is server-side state and reassignment never rewrites the client's config file. A binding to a named profile is **enforceable in every configuration**: the binding guard (FR-008a) makes omitting the credential never wider than the binding.
- **Effective profile** of a request and its **profile source**: the result of resolution (FR-020) — one of `pin`, `binding`, `url`, `session`, `anonymous`, `none`.
- **Effective access** to a tool: the intersection of credential scope (token servers/permissions), effective profile decision, server state (enabled, not quarantined, connected/authenticated), and tool approval (Spec 032). Each link is evaluated by its existing owner; this spec adds only the profile link and the explanation of the chain.
- **Scope filter**: the query-parameter contract shared by every grid and chart on every surface. It is **owned by Spec 109** (`specs/109-ux-navigation-consistency/contracts/url-filter-contract.md`, composable `useScopeQuery()`, macOS `ScopeFilter`); this spec owns only the backend meaning of `profile`, `client` and `token` (FR-031) and the availability signal that un-hides them ([contracts/url-filter-contract.md](contracts/url-filter-contract.md) is a pointer).
- **Surface**: Web UI, macOS app (window + tray), CLI, MCP (built-in tools) — REST is the substrate the first three use and is specified with them.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — A read-only profile really is read-only (Priority: P1)

A user defines "Work Read-only" = GitHub, Linear, Notion, read tools only. Any session under that profile — however it got there — cannot discover or execute a write, destructive, denied or unclassified tool, through any MCP surface — nor, for a profile-pinned agent token, through the REST discovery and dispatch routes (FR-015, FR-015a).

**Why this priority**: This is the security promise the word "read-only" makes; today it is false (P3). Everything else in the spec is management on top of this guarantee.

**Independent Test**: Config-only fixture (no UI): servers `github` (annotated read/write/destructive tools + one unannotated tool), `filesystem`; profile `work-readonly {title:"Work · Read-only", servers:[github], max_tier:read}` (the title is what the explainer and activity surfaces show; the agent-facing refusal names neither title nor slug, [contracts/refusals.md](contracts/refusals.md)). Drive `/mcp/p/work-readonly`, a token pinned to it, and `set_profile` on `/mcp`; assert discovery and call outcomes per the enforcement matrix ([contracts/enforcement-matrix.md](contracts/enforcement-matrix.md)).

**Acceptance Scenarios**:

1. **Given** a session under `work-readonly`, **When** it calls `retrieve_tools("create issue")`, **Then** no write/destructive/unannotated GitHub tool is returned, no `filesystem` tool is returned, and the response carries `hidden_by_profile ≥ 1` without naming any hidden tool. *(audit acceptance check 1)*
2. **Given** the same session, **When** it calls `call_tool_write` with `github:create_issue`, **Then** the call is refused before any upstream I/O with `blocked by profile: github:create_issue is a write tool; this profile allows read tools only` — the same bytes whether the profile came from a pin, a binding, `anonymous_profile`, the URL or `set_profile`, so the refusal never tells a caller that it is pinned or to what (Spec 105 precedent, FR-013) — and an activity record is written with `status=blocked`, `block_reason=profile_tier`, `profile=work-readonly`. *(audit acceptance check 2, first half)*
3. **Given** a GitHub tool with no annotations, **When** a session under `work-readonly` searches for it, describes it or calls it, **Then** it is absent from discovery, `describe_tool` returns the uniform not-found response, and a call is refused with `block_reason=profile_unannotated`; **When** the user classifies it `read` in the profile (any surface), **Then** it becomes visible and callable. *(audit acceptance check 3)*
4. **Given** the enforcement-matrix `work-readonly` fixture (`servers: [github, notion]`, `max_tier: read`, `tools.deny: ["github:*secret*"]`, `tools.allow: ["notion:update_page", "github:get_secret_scanning_alert", "filesystem:read_text_file"]` — [contracts/enforcement-matrix.md](contracts/enforcement-matrix.md); note `notion` is in `servers`, unlike the minimal Independent Test profile above), **When** discovery runs, **Then** secret-matching tools are excluded (`denied_by_rule`) even though they are read tools **and** `github:get_secret_scanning_alert` is also matched by an allow rule (deny beats allow on overlap); `notion:update_page` is admitted even though it is a write tool; and the allow rule naming `filesystem` (outside `servers`) is saved with the FR-007 warning and ignored, so `filesystem:read_text_file` stays `server_not_in_profile` (FR-004).
5. **Given** `code_execution: false` on the profile, **When** the session lists tools on `/mcp` or `/mcp/code`, **Then** `code_execution` is absent and a call to it is refused; **Given** `code_execution` enabled, **When** a script calls `call_tool('github','create_issue',…)`, **Then** the nested call is refused with the same profile refusal and recorded as a child record (`parent_id`) with `block_reason=profile_tier`.
6. **Given** the direct surface `/mcp/all` under a pinned token, **When** `tools/list` runs, **Then** above-cap tools are absent and a `tools/call` naming one is refused identically to item 2.
7. **Given** a legacy profile (`name`+`servers` only), **When** any Spec 057/105 test runs against it, **Then** behaviour is byte-identical to `origin/main` (no tier cap, unannotated = read, management tools per global gates).
8. **Given** a regular agent token pinned to `work-readonly`, **When** it calls the REST discovery routes `GET /api/v1/index/search?q=issue`, `GET /api/v1/tools`, `GET /api/v1/servers/github/tools` or `GET /api/v1/servers/github/tools/export`, **Then** `github:create_issue`, `github:delete_repo`, `github:search_code` and every `filesystem` tool are absent exactly as from `retrieve_tools`, and `GET /api/v1/servers/github/tools/create_issue/diff` answers the unknown-tool `404` (FR-015a).

### User Story 2 — Bind a profile to a client and change it from anywhere (Priority: P1)

A user connects Cursor with "Work Read-only", locked. Later they move Cursor to "Work Full" from the Web UI, the macOS app, the CLI or an admin MCP session. Cursor's config file is never rewritten; its next request runs under the new profile, and its live session is told its tool list changed.

**Why this priority**: The maintainer's core requirement ("set this profile for any AI client … change a client's profile via the Web UI, MCP and the CLI"); fixes P4 and P2.

**Independent Test**: Sandboxed HOME with a Cursor config and `require_mcp_auth: true`; `mcpproxy connect cursor --profile work-readonly --lock`; open an MCP session with the written credential; reassign via each surface in turn; assert the next `retrieve_tools` result, the `notifications/tools/list_changed` notification, the unchanged config-file hash, and one `profile_change` activity record per reassignment.

**Acceptance Scenarios**:

1. **Given** `require_mcp_auth` on, or off with `anonymous_profile` set to a profile not wider than the binding (FR-008a — e.g. `work-readonly` with no `switchable_to`; otherwise scenario 7's refusal applies), **When** the user connects Cursor with profile `work-readonly` (any surface), **Then** a client credential `client-cursor` (kind `client`, pinned `work-readonly`, mode `locked`) is minted, written into Cursor's config via the client's supported carrier, and the instance admin API key is **not** written; the preview shows the credential masked and names the profile.
2. **Given** Cursor bound and connected, **When** `mcpproxy client set-profile cursor work-full` runs, **Then** Cursor's next request resolves to `work-full` with `profile_source=pin` (the command keeps Cursor's `locked` mode, and a locked client credential resolves at the pin tier, FR-020; a `switchable` one would report `binding`), no client config file changes (byte-identical), and Cursor's live session receives `notifications/tools/list_changed`. *(audit acceptance check 4)*
3. **Given** the same, **When** the reassignment is made from the Web UI Clients page, the macOS Clients view or tray submenu, or the MCP `profiles` tool (`operation: assign`), **Then** the outcome is identical and each writes one activity record `type=profile_change` naming actor, surface, client, previous and new profile.
4. **Given** Cursor bound `locked` to `work-readonly`, **When** its session calls `set_profile("work-full")` or initializes via `/mcp/p/work-full`, **Then** it receives the uniform non-disclosing refusal (Spec 105 shape). **Given** mode `switchable` and `work-readonly.switchable_to = ["work-full"]`, **Then** `set_profile("work-full")` succeeds and `set_profile("admin-all")` gets the uniform refusal. **Given** Cursor bound `locked` to `work-readonly` and its client config pointing at `/mcp/p/work-readonly` (or its session calling `set_profile("work-readonly")`), **Then** the request is admitted — naming the caller's own pin or bound profile is not a switch (FR-022), exactly as a pinned token may initialize `/mcp/p/<its-own-pin>` today. *(audit acceptance check 5, first half)*
5. **Given** an admin credential session (API key or socket) with no effective profile, **When** it lists tools, **Then** the `profiles` tool is present and callable; **Given** a pinned or bound session, an anonymous session, or an admin session whose effective profile does not set `management_tools: true`, **Then** `profiles` is absent from `tools/list` and a call to it is refused. *(audit acceptance check 5, second half)*
6. **Given** a client whose credential is revoked or forgotten, **When** it next calls `/mcp`, **Then** it is rejected `401` and the Clients surfaces show it as "credential revoked — reconnect".
7. **Given** `require_mcp_auth` is off **and** `anonymous_profile` is unset or wider than the binding to profile P (the US5-4 condition — wider by servers, tier cap, unannotated handling, any admitted tool incl. deny/allow rules, `switchable_to` reachability or the code-execution/management capabilities, FR-008a — evaluated by the one shared function, data-model §7), **When** any surface tries to bind a client to P (`locked`, or `switchable` with a non-empty pin — connect, `client add`, binding change, bulk move, bulk admin-key upgrade with a profile, MCP `assign`) or makes an existing binding bypassable (a profile edit, classification, delete or `reassign_to` that shrinks what the binding reaches — including a member of P's `switchable_to` — or grows what anonymous callers reach), **Then** the operation is **refused** with `409 {code: "binding_bypassable_without_auth", fixes: [...]}` — "a client bound to a profile could escape it by omitting its credential while authentication is optional" — and nothing is minted, written or changed; the fixes offered are "turn on `require_mcp_auth`" (listing the unidentified clients that would lose access) and "set `anonymous_profile` to a profile not wider than the binding" (target P when P itself qualifies — for a `locked` binding only if P's `switchable_to` reaches nothing wider); after either fix the same request succeeds. With a non-wider `anonymous_profile` already set, the binding succeeds with no warning. The refusal text and codes are identical on REST, CLI, Web UI, macOS and MCP (FR-008a).
8. **Given** Cursor still holding the admin API key (`credential_state=admin_key`) and a scoped, non-administrator agent token `ro-bot`, **When** `ro-bot` calls `GET /api/v1/connect`, `GET /api/v1/connect/cursor` or `GET /api/v1/connect/cursor/preview`, **Then** each returns `403` and the body carries no `credential_state`, client list or preview; **When** the admin API key or the tray socket calls the same routes, **Then** they return `200` with `credential_state` per client (FR-025a — the same administrator-only rule as Spec 109's `GET /clients`).

### User Story 3 — See and filter everything by profile and client, with deep links (Priority: P1)

A user asks "What did Codex do today?" and "Why can't Cursor use `github:create_issue`?". Every grid and chart (Activity, Sessions, Usage, Tools, Servers, Clients, Tokens) filters by profile, client and token; filters live in the URL; every client row, profile card, chart bar and activity row links to the related page already filtered; an explainer walks the access chain.

**Why this priority**: Without attribution, scope is unverifiable (P5, P6); the maintainer lists filters and deep links as a hard requirement.

**Ownership**: the URL parameters, their page wiring, the sticky/Back behaviour and every deep link below are Spec 109's (`useScopeQuery`, link map, macOS `ScopeFilter`, 109-k); they are wired there and stay hidden until this spec's backend reports `scope_filters` available (FR-031). This story's scenarios are the joint acceptance: this spec supplies the recorded fields, the backend filters, the view-as verdicts, the explainer and the Profiles-page targets; Spec 109 supplies the navigation.

**Independent Test**: Seed two clients (Cursor bound to `work-readonly`, Codex bound to `work-full`), generate calls including one blocked call, then load `/activity?client=cursor&status=blocked`, `/tools?client=cursor`, `/usage?profile=work-readonly`, `/sessions?client=cursor` and the equivalent CLI/macOS filters; assert identical record sets across surfaces.

**Acceptance Scenarios**:

1. **Given** Cursor's blocked call from US1 scenario 2, **When** the user opens `/activity?client=cursor&status=blocked` (or `mcpproxy activity list --client cursor --status blocked`, or the macOS Activity filter), **Then** exactly that record is listed, showing client, profile (with source) and token as chips. *(audit acceptance check 2, second half)*
2. **Given** a Web UI user, **When** they open `/tools?client=cursor`, `/usage?profile=work-readonly` and `/sessions?client=cursor`, **Then** each page loads already filtered, shows a removable filter chip, and the chip survives navigation to another scope-aware page and Back. *(audit acceptance check 6)*
3. **Given** `/tools?client=cursor`, **Then** the list shows exactly what Cursor can see and call: excluded rows are greyed with the reason (`above tier cap`, `denied by rule`, `unannotated — classify`, `server not in profile`, `token permission`, `quarantined`, `disabled`).
4. **Given** any activity record written after upgrade, **Then** it carries `profile`, `profile_source`, `client_id`, `client_name` (reported by the client), and `token_name`; **Given** a record written before upgrade, **Then** it remains listable and shows "unattributed" for missing fields (its legacy `metadata.profile` still matches the `profile` filter).
5. **Given** a client is reassigned from `work-readonly` to `work-full`, **When** the user filters activity by `profile=work-readonly`, **Then** calls made before the reassignment are still listed (the recorded profile, not the current binding, is filtered).
6. **Given** the access explainer for (client `cursor`, tool `github:create_issue`) on any surface (Web UI modal, macOS sheet, `mcpproxy access explain`, MCP `profiles` `explain`), **Then** it lists the chain credential → profile → server in scope → tool rule → tier vs cap → token permission → global gate → server state → tool approval (the enforcement order), stops at the first failing link, names the fix ("Allow this tool in Work Read-only" / "Move Cursor to Work Full"), and its verdict equals the enforcement outcome of an actual call (same predicate).
7. **Given** the Clients page, **Then** each client row shows last seen, active sessions, calls and blocked calls in 24 h, the profile chip with lock state and source, and links "Activity · Sessions · Tools it sees · Usage" carrying `?client=<id>`; each profile card links "Tools · Activity · Clients · Tokens" with `?profile=<name>`; a blocked activity row links "Allow in profile…" to the profile editor focused on that tool.

### User Story 4 — Manage profiles from every surface (Priority: P2)

A user creates, edits, classifies, tries, renames and deletes profiles from the Web UI, macOS app, CLI or admin MCP tool, with the same fields, names, validation and outcomes everywhere.

**Why this priority**: Fixes P2; required for US2 to be usable without editing JSON, but US1–US3 are testable with config-file profiles.

**Independent Test**: For each operation, perform it on one surface and read it back on the other three; compare against the shared contract fixtures ([contracts/](contracts/)).

**Acceptance Scenarios**:

1. **Given** no profiles, **When** the user runs `mcpproxy profile create work-readonly --servers github,linear,notion --max-tier read --unannotated deny` (or the Web UI/macOS editor, or MCP `profiles` `create`), **Then** the profile is persisted to `mcp_config.json`, hot-reloaded, and visible on every surface with tool counts by tier and the unannotated count.
2. **Given** the profile editor, **When** the user presses "Try it" with a query, **Then** a real `retrieve_tools` search runs under the **unsaved draft** and returns results plus `hidden_by_profile` with per-tool reasons, without persisting anything.
3. **Given** a profile used by clients or tokens, **When** the user deletes it, **Then** the operation is refused (`409`) with the list of affected clients and tokens until a `reassign_to` target is given (or `force`, which leaves pins and bindings dangling → deny-all, never wider); a profile that is the `anonymous_profile` is refused with its own `409` (`profile_is_anonymous_profile`) even under `force`, until `reassign_to` is given (research D19); rename moves every pin and binding to the new name — the `profile_pin` of every agent token and client credential in `config.db`, plus other profiles' `switchable_to` and `anonymous_profile` references — so no previously working token or client is left dangling by a rename. A delete or `reassign_to` whose result would make a client binding bypassable (FR-008a: a binding moved to a narrower target, a switchable binding losing the deleted profile from its `switchable_to`, `anonymous_profile` moved to a wider target) is refused with `409 binding_bypassable_without_auth` and nothing is deleted or moved.
4. **Given** invalid input (unknown tier, malformed rule pattern, `switchable_to` naming the profile itself), **Then** every surface rejects it with the same validation error from the one validator. **Given** input that is only a warning under FR-007 (a rule or classification naming a server outside `servers`, `switchable_to` naming an unknown profile), **Then** the profile is saved, the offending entry is ignored (FR-004) and every surface shows the same warning message — it is never a rejection.
5. **Given** a token dialog (Web UI, macOS) or `mcpproxy token create --name ci-bot --profile work-readonly`, **Then** the token is created bound to the profile with an expiry, without requiring server/permission fields; tokens with legacy `allowed_servers`/`permissions` show them read-only as "legacy scope" and the CLI suggests `--profile`.
6. **Given** the Web UI header, **Then** there is no "Profile:" switcher; a "Viewing: profile · client" filter chip reflects and edits the URL scope filter and is labelled as a view filter; `PUT /api/v1/profiles/active` still answers for one minor release with a `Deprecation` header and is called by no first-party surface. *(fixes P1, H2)*

### User Story 5 — Uncredentialed callers are confined (Priority: P2)

A user who keeps `require_mcp_auth` off (for legacy clients) can still confine anonymous callers to a profile, and can never end up in a configuration where a bound client escapes its profile by dropping its credential.

**Why this priority**: A lock only holds if the client must present its credential; without this story, US2 is bypassable by dropping a header.

**Independent Test**: With `require_mcp_auth: false` and `anonymous_profile: "readonly-all"`, an MCP session without credentials sees only `readonly-all`'s tools, cannot `set_profile` outside `readonly-all.switchable_to`, cannot reach `/mcp/p/<other>`, and does not see management tools unless the profile allows them.

**Acceptance Scenarios**:

1. **Given** `anonymous_profile` unset **and** no active client credential bound to a named profile (or `require_mcp_auth` on), **Then** anonymous behaviour is unchanged (all servers, legacy). **Given** `anonymous_profile` unset or wider than some named binding while `require_mcp_auth` is off — reachable only by a hand edit, since every API path refuses to create it (US2-7) — **Then** the binding guard (FR-008a) resolves every anonymous caller to deny-all (`profile_source=anonymous`) and every surface reports `anonymous_denied_by_binding_guard`.
2. **Given** `anonymous_profile: X`, **When** an anonymous caller (no credential, or an unrecognised non-agent token) uses any MCP surface, **Then** it resolves to `X` with `profile_source=anonymous` and is treated as scoped for refusal shapes.
3. **Given** `anonymous_profile` names a missing profile, **Then** anonymous callers resolve to deny-all (never all servers) and config validation warns.
4. **Given** any client credential bound to a named profile — `locked`, **or** `switchable` with a non-empty pin (the omitted-credential bypass works identically for both) — and `require_mcp_auth: false` and `anonymous_profile` unset or wider than that binding (FR-008a: some profile an anonymous caller can reach — `anonymous_profile` or its `switchable_to` — has a server, tier cap or unannotated handling beyond the binding, admits a tool the binding does not admit, e.g. because the bound profile denies it by rule, or enables code execution or management tools the binding does not), **When** the condition arises (only possible by hand-editing the config file or by a pre-existing binding when the operator hand-clears `anonymous_profile`; every API path refuses it, US2-7), **Then** the lock still holds: anonymous callers resolve deny-all (FR-008a), and `mcpproxy doctor`, the clients `warnings[]`, the Web UI Clients page and the macOS Clients view all report `anonymous_denied_by_binding_guard`, naming the bindings that triggered it and the fix. The "All servers" binding (empty pin) does not trigger it — omitting the credential grants no wider server reach, and the management-tool difference is covered by D5's connect notice.

### Edge Cases

- **Pinned or bound profile deleted or renamed outside the API** (hand-edited config): pins **and switchable bindings** dangle → deny-all (existing `profile_resolver.go` stale-pin rule, extended to the binding tier by FR-020 — never a fall-through to `none`); Clients/Tokens surfaces show "profile missing" with a reassign action.
- **Unannotated tool gains annotations upstream** (or a #1323 override): its intrinsic tier now applies; a stale profile classification is ignored and flagged "classification ignored — tool is now annotated" in the editor/`profile show --effective`.
- **Allow rule for a tool above cap whose server is quarantined or disabled**: still unavailable; allow never bypasses server state, approval, token permissions or global `read_only_mode`.
- **Allow/deny/classification naming a server not in `servers`**: validation warning (warn-skip, same as unknown servers); never widens the server set.
- **`switchable_to` cycles** (A→B→A): legal; each switch is evaluated against the *bound* profile's list, not the current one, so a chain cannot escalate beyond the bound profile's list.
- **Two surfaces reassign the same client concurrently**: last write wins by token-store transaction; both writes are recorded as `profile_change`; the final state is reported to both callers with the resulting profile.
- **Live session of a reassigned client whose client ignores `list_changed`**: enforcement is per request — the credential is re-read and any stored `set_profile` selection is re-validated against the new base (FR-020) and cleared by the reassignment (FR-026) — so the next call is evaluated under the new binding regardless.
- **Operator narrows `switchable_to` while a session sits on a switched-to profile**: the stored selection fails re-validation on the next request and is cleared (FR-020); the session falls back to its binding.
- **Cache entry produced under the old profile/policy**: refused by the Spec 105 cache-authorization rule because the stamp carries the policy fingerprint and pin (FR-027).
- **Client credential expiry** (365-day cap, Spec 107 FR-011): surfaces show "expires in N days" from 14 days before; rotate = reconnect (config rewrite with diff preview), never silent.
- **Crash or config-write failure during rotation (or reconnect over an active credential)**: rotation is staged (FR-021a) — the new secret is added as a pending secret next to the old one, both authenticate, the config is written, then an idempotent finalize drops the old one; after a crash the next reconciliation reads which secret the client config holds and finalizes or rolls back accordingly, so the client is never left holding an invalidated secret.
- **Malformed client-credential record** (missing/unknown `kind`, a `client-` record without `client_id`, a `locked` mode without a pin, a `mcp_cli_` secret whose record is not `kind=client`, or a `kind=client` record reached through a `mcp_agt_` secret): authentication fails closed (`401 Agent token invalid: malformed credential record`) on every request (FR-021); it never degrades to a regular wildcard agent token.
- **Rollback to a pre-108 binary**: client credentials use the `mcp_cli_` secret prefix, which a pre-108 binary does not treat as an agent token — on REST it is compared with the admin key and rejected `401`; on MCP it is rejected when `require_mcp_auth` is on and otherwise treated exactly like an omitted credential (research D27). It can never authenticate as a wildcard agent token on an older binary. It is, however, **not confined** there when `require_mcp_auth` is off: a pre-108 binary has no `anonymous_profile` or binding guard, so the credential-less path it falls into is today's unconfined, admin-shaped anonymous caller. Operators downgrading past 108-c MUST turn `require_mcp_auth` on first (downgrade note in docs and release notes, T124/T125); SC-010 promises rollback safety only in that configuration.
- **Custom client with the same id as a supported client**: refused; ids are unique per instance.
- **Pre-108 regular token already named `client-<id>`**: never revoked or overwritten by connect; the mint is refused with `409` naming the conflicting token and the remediation (revoke/delete it, then connect again), and the Clients row shows `client_token_name_conflict` (FR-021).
- **Reconnecting a forgotten client**: the soft-revoked `client-<id>` record is replaced in the mint transaction (FR-021), so forget → connect works without a manual delete.
- **Clients connected before upgrade** (keyless or holding the admin API key): listed as "unidentified" or "holds admin key"; "Upgrade to client credential" rewrites the entry only after an explicit preview; nothing is rewritten automatically on upgrade. Because the admin key stays valid in every config that still holds it, the remediation is explicit and two-step (FR-025): a previewed **bulk upgrade** of every client holding the admin key, then **rotate the admin API key** (the documented v0.69.0 procedure: set a new `api_key` and restart; the remediation links to it), which invalidates every copy that was not upgraded — the surfaces keep the `client_holds_admin_key` warning and a Needs-attention item (Spec 109) until both steps are done.
- **Client credential presented to the REST API**: rejected (`403 client credentials are valid on MCP endpoints only`) — a client can never read activity, config or other clients over REST.
- **Profile with `max_tier: destructive` and no other v3 field**: no cap is effectively applied; `unannotated` defaults to `as_read`, so the discoverable and callable tool **set** is identical to legacy. The profile is nonetheless non-legacy (it sets a policy field), so `retrieve_tools` carries `hidden_by_profile: 0` and `profile` (FR-011) — the JSON shape differs from a legacy response by design; byte-parity (SC-003) is promised for legacy profiles only.
- **Binding a client that has no client credential** (`credential_state` `none`, `admin_key`, `revoked` or `expired`): refused on every surface with `409 no_client_credential` and the remediation "connect <client> with a profile" (FR-026); no credential is minted implicitly (FR-025).
- **`code_execution: true` on a profile while the global flag is off**: global flag wins (a profile can only narrow).
- **Server edition**: profile CRUD admin-only; administrator-created agent tokens may carry a profile, per-user tokens (`POST /user/tokens`) may not yet (follow-up, D22); `/clients` not registered; Server-edition per-identity narrowing (`httpapi/profiles.go:64`) continues to filter `GET /profiles`.

## Requirements *(mandatory)*

### Functional Requirements

**A. Profile policy model (PV-A)**

- **FR-001**: A profile MUST accept these optional fields in addition to `name` and `servers`: `title` (display, ≤ 80 chars), `description` (≤ 500 chars), `max_tier` (`read`|`write`|`destructive`), `unannotated` (`deny`|`as_write`|`as_read`), `tools` (`allow`, `deny`: arrays of `server:tool` glob patterns; `classify`: map `server:tool` → tier for unannotated tools), `code_execution` (bool or unset = inherit, except off under a `read`/`write` cap — FR-003a), `management_tools` (bool or unset = inherit/legacy), `switchable_to` (array of profile names or unset). Field names are identical in config, REST, CLI flags (kebab-case), MCP tool arguments and UI labels per the terminology table. Kebab-case applies to CLI flag **names** only: enum **values** are spelled identically on every surface (`as_write`, `as_read`), so a value copied between surfaces works; the CLI additionally accepts `as-write`/`as-read` as input aliases and always prints the canonical spelling.
- **FR-002**: A legacy profile MUST load and behave exactly as under Specs 057/105; every existing profile test passes unchanged. Unset fields mean: no tier cap; unannotated classified read (legacy); no rules; `code_execution` and `management_tools` inherit global gates; `switchable_to` legacy semantics (FR-022). On a v3 profile with a `read` or `write` cap, FR-003 and FR-003a replace the unannotated and code-execution defaults with fail-closed ones.
- **FR-003**: When `max_tier` is `read` or `write` and `unannotated` is unset, unannotated handling MUST default to `deny` (fail closed). When `max_tier` is `destructive`, it defaults to `as_read`.
- **FR-003a**: When `max_tier` is `read` or `write` and `code_execution` is unset, code execution MUST default to **off** (fail closed, the FR-003 rule): the global `enable_code_execution` is on by default since v0.66.0, so plain inheritance would give a read-capped profile a tool that exists to orchestrate calls, contradicting the cap it was created for. With `max_tier` `destructive` or unset (every legacy profile, FR-002) it inherits the global flag. An explicit `code_execution: true` under a cap is honoured (every nested call still passes the FR-013 gate), and the global flag always wins (FR-006). One helper, `EffectiveCodeExecution()` (data-model §1), feeds enforcement, `tools/list` visibility, view-as, the explainer and FR-008a (iii) (zcode review).
- **FR-004**: Patterns MUST be canonical `server:tool` with `*` as the only wildcard, matched case-sensitively against the canonical tool identity (Spec 105 registration identity, never a flattened display name). Invalid patterns are fatal validation errors; patterns naming a server outside `servers` are warnings and ignored.
- **FR-005**: `tools.classify` entries MUST apply only to tools whose effective annotations carry no tier hint; entries for annotated tools are ignored and reported as stale by `effective_tools` on every surface.
- **FR-006**: A profile MUST NOT widen anything: allow rules cannot add servers, bypass quarantine/approval/enabled state, token permissions, `read_only_mode`, or the global `enable_code_execution`/`disable_management` gates.
- **FR-007**: Validation MUST be one function used by config load, REST, CLI (via REST), MCP `profiles` and the editors' live validation (through REST), returning identical messages. Fatal: invalid slug/reserved/duplicate (existing), unknown enum value, invalid pattern, `switchable_to` naming itself, `title` longer than 80 or `description` longer than 500 characters (FR-001 limits). Warning (saved, entry ignored — never a rejection): unknown server in `servers` (Spec 057 warn-skip), an allow/deny rule or classification naming a server outside the profile's `servers` (FR-004), unknown `switchable_to` profile, stale classification (FR-005), unknown `anonymous_profile` (FR-008). Messages: data-model §1.
- **FR-008**: Top-level `anonymous_profile` (string, default empty) MUST confine every caller whose request authenticates as credential kind `anonymous` — no credential, **or** an unrecognised non-agent token accepted by the `require_mcp_auth: false` back-compat branch (`internal/server/server.go:568`) — to that profile when set (FR-020); a missing profile resolves to deny-all with a validation warning.
- **FR-008a** (binding guard): a client binding to a named profile P (`locked`, or `switchable` with a non-empty pin) is **bypassable** when `require_mcp_auth` is off and `anonymous_profile` is unset or **wider** than the binding — one shared condition function (`BindingBypassable`, data-model §7). **Wider** compares everything a caller can reach, not only servers and cap (codex round 3): the anonymous caller's *reachable set* is `anonymous_profile` Q plus every profile in Q's `switchable_to` (one hop, FR-022); the binding's reachable set is P for `locked`, P plus P's `switchable_to` for `switchable`. The binding is bypassable when some anonymous-reachable profile R (i) has a server outside the union of the binding-reachable profiles' servers, a higher effective tier cap than every binding-reachable profile, or a more permissive effective `unannotated` handling (admission order `deny` < `as_write` < `as_read`) — the tool-independent structural conditions; or (ii) **admits** under the FR-010 predicate (`CompiledPolicy.Decide`, deny/allow rules, classification and unannotated handling included) some tool of the current published (index, snapshot) pair, with its current effective annotations, that no binding-reachable profile admits; or (iii) turns on an effective `code_execution` or `management_tools` capability that every binding-reachable profile has off. Example: P and Q with the same servers and `max_tier` where only P has `tools.deny: ["github:delete_repo"]` → bypassable by (ii). Because (ii) depends on the tool set, the runtime guard (2) re-evaluates the condition on every published (index, snapshot) pair, so a tool that appears later and makes a binding bypassable trips the guard instead of widening anyone. (1) **API refusal** — a **candidate-state delta**, not a per-route list of conditions (zcode round 2): every operation that writes a client binding, a profile, `anonymous_profile` or `require_mcp_auth` builds the candidate state (config and token store as they would be after the write) and calls one function, `BindingGuardDelta(current, candidate, pair)` (data-model §7), which returns every binding that is bypassable in the candidate but not in the current state; a non-empty result refuses the operation with `409 {error, code: "binding_bypassable_without_auth", bindings: [...], fixes: [...]}` and changes nothing (a bulk move instead skips the refused clients, FR-026). Because the delta compares the complete reachable sets, it catches every write that shrinks the binding-reachable set or grows the anonymous-reachable one, including: narrowing P; narrowing, deleting or renaming away **any member S of P's `switchable_to`** for a `switchable` binding, or removing S from that list — the binding-reachable union shrinks exactly as if P were narrowed (`DELETE /profiles/{S}` removes S from every `switchable_to`); widening any anonymous-reachable profile or adding one to that set (editing Q's `switchable_to`, or creating a profile an existing `switchable_to` names); a `tools.classify` change, which changes what `Decide` admits; moving bindings or `anonymous_profile` (`DELETE /profiles/{name}?reassign_to=`, rename); minting bindings (connect, `client add`, and `POST /clients/upgrade-admin-key-holders` with `apply` and a named `profile`, FR-025); binding changes and bulk moves; MCP `profiles` `create`/`update`/`delete`/`rename`/`classify`/`assign`; and `PATCH /config`/`POST /config/apply` turning `require_mcp_auth` off, clearing/widening `anonymous_profile` or carrying a profiles list that does any of the above. contracts/refusals.md lists every guarded route and operation; a route-coverage test (T070a) fails when a mutating route or MCP operation of the profiles, clients, connect or config families is neither guarded nor on the explicit exempt list (operations that cannot shrink or grow either set: rotate, finalize, forget/`DELETE /clients/{id}`, disconnect, `POST /profiles/try`). (2) **Runtime guard** (hand edits, config reload): while any active binding is bypassable, every anonymous caller resolves to **deny-all** (`profile_source=anonymous`, like a dangling base: no URL/session selection admitted), so omitting the credential is never wider than any binding; every surface reports `anonymous_denied_by_binding_guard` naming the bindings and the fixes. A lock is therefore enforceable in every configuration, not only advised.
- **FR-009**: The profile object MUST remain edition-neutral (no user/team fields) so the server edition can later map profiles to teams. Pinned by a field-set test (T004) that fails when `ProfileConfig` gains any JSON field beyond the FR-001 set, under both build tags.
- **FR-009a** (rollout gate): no build may admit a policy it cannot enforce on every dispatch path. Until the execution enforcement of 108-d ships, the one validator MUST reject any profile that sets a v3 policy field (`max_tier`, `unannotated`, `tools`, `code_execution`, `management_tools`, `switchable_to`) with the fatal error `profiles[%d]: %s is not supported by this build (Profiles v3 enforcement incomplete)`, driven by one constant `profile.PolicyEnforcementReady` that is `false` from 108-a and flipped to `true` in 108-d, in the same commit that lands the last execution gate. **The same constant gates the top-level `anonymous_profile`** (zcode review): while it is `false`, a non-empty `anonymous_profile` is the fatal error `anonymous_profile is not supported by this build (Profiles v3 enforcement incomplete)` from the one validator (config load, `PATCH /config`, `POST /config/apply`), because 108-a/108-b builds have no anonymous resolver tier at all and 108-c's tier lacks the confined-anonymous non-admin view (`auth.ScopedView`, FR-016) that lands in 108-d — admitting the field earlier would advertise a confinement the build does not enforce. In those builds the FR-008a guard treats anonymous callers as unconfined (every named binding with `require_mcp_auth` off is bypassable, so the API refuses it and the runtime guard denies anonymous callers) and its `fixes[]` offers only `require_mcp_auth`. Tests in 108-a–108-c enable the policy and `anonymous_profile` through a test-only override whose mechanism is fixed so that a shipped binary cannot reach it (zcode round 2): `PolicyEnforcementReady` is a Go `const`; the validator reads the gate only through `profile.policyGateOpen()` = `PolicyEnforcementReady || (testOverride.Load() && testing.Testing())`; `testOverride` is an unexported `atomic.Bool` set only by `profile.EnablePolicyForTest(tb testing.TB)`, which panics unless `testing.Testing()` reports a `go test` binary and resets the flag in `tb.Cleanup`. No environment variable, config field, CLI flag or build tag feeds the gate, so no runtime input of a released binary can open it. T004a pins this structurally (an AST check of the gate function and of every caller of `EnablePolicyForTest`, which must sit in `_test.go` files) and behaviourally (the built `mcpproxy` binary refuses a `max_tier` config with exit code 4). 108-d deletes the override together with the flip (T055a). A release built from any commit between 108-a and 108-d therefore behaves exactly like a pre-108 build for profiles and anonymous callers (discovery can never hide a tool that execution would still run).

**B. Enforcement (PV-A)**

- **FR-010**: One predicate MUST compute the profile decision for (profile, tool identity, effective annotations): (1) server ∉ servers → `server_not_in_profile`; (2) matches deny → `denied_by_rule`; (3) matches allow → admitted; (4) unannotated and unclassified with policy `deny` → `unannotated_hidden`; (5) profile tier > `max_tier` → `above_tier_cap`; else admitted. Enforcement, `effective_tools`, "view as client", "Try it" and the access explainer MUST all call it.
- **FR-011**: `retrieve_tools` MUST exclude profile-excluded tools **before** the result limit (Spec 105 FR-005 scope-aware search, never "search then drop"). Today's pre-limit predicate (`index.SearchToolsScoped(query, limit, inScope func(serverName string) bool)`, `internal/index/bleve.go`) sees only the server name, and `indexedToolVisible` runs on the already-cut result, so the policy cannot be evaluated there: the index API MUST be extended with a hit-level predicate that receives the hit's canonical `server:tool` identity (`SearchToolsAdmitted(query, limit, admit func(Hit) Admission)`, exhaustive paging as today). The index stores no annotations (`ToolDocument`/`readToolMetadata`, `internal/index/bleve.go`, carry none) and this spec adds none — no index-schema change, no reindex: the predicate, built by the server from the request's one resolution, obtains the hit's effective annotations through the **same identity seam every dispatch path uses** (`resolveExactToolIdentity` behind `profile.EffectiveAnnotations`, T013; an O(1) StateView lookup per hit, inside the SC-007 budget), so discovery and execution classify a tool from one source and a tool whose identity is not found is destructive (`IntrinsicTier(nil,false)`) and reports, per rejected hit, whether it failed on server scope or only on policy, so the limit is applied to admitted hits only and `hidden_by_profile` is counted in the same pass over the full match set. It MUST return `hidden_by_profile` = the number of query-matching tools on servers inside the caller's effective server scope that the tool policy excluded (reasons 2, 4, 5). It never names or describes a hidden tool and is identical across the Spec 105 two-fixture differential oracle. Presence is keyed on the profile, never on the query: `hidden_by_profile` is **present — possibly `0` — whenever the effective profile is non-legacy** (sets any of the six policy fields named in Definitions; `title`/`description` do not count), and **omitted** when there is no effective profile or it is legacy (byte-parity, SC-003). The companion `profile` field names the effective profile **only when the caller selected it** (`profile_source` `url` or `session`); for a base the caller did not choose (`pin`, `binding`, `anonymous`) it is omitted, so discovery never tells a caller that it is pinned or to what (Spec 105 precedent, research D27). A **dangling base** (FR-020 deny-all resolution for a pin, binding or `anonymous_profile` naming a profile no longer in config) and the FR-008a guard have no `ProfileConfig` to test and always count as **non-legacy**: `hidden_by_profile` = `0` (the effective server scope is empty) and `profile` is omitted (the source is a base).
- **FR-012**: `describe_tool` MUST apply the same visibility; excluded tools receive the uniform not-found response (Spec 105 FR-010).
- **FR-013**: `call_tool_read|write|destructive` MUST refuse a profile-excluded tool on an in-scope server before any upstream I/O with the refusal text in [contracts/refusals.md](contracts/refusals.md), naming the tool, its tier and the reason but **never the profile's title or slug** — the text is byte-identical whatever the profile source (pin, binding, anonymous, URL, session), so it cannot confirm that a caller is pinned or to what (Spec 105 `set_profile` precedent; the operator sees the profile on the activity record and in the explainer) — and record `status=blocked` with `block_reason` ∈ {`profile_tier`, `profile_rule`, `profile_unannotated`} (plus `profile_code_execution`, `profile_management` for FR-014/FR-016 refusals). Out-of-scope servers keep the Spec 105 non-disclosing refusal. The Spec 105 token-permission and target-tier gates are unchanged and evaluated independently (all must pass).
- **FR-014**: `code_execution` MUST be absent from `tools/list` and refused at call time on `/mcp`, `/mcp/code` and `/mcp/p/<slug>` when the profile's effective code execution is off (`code_execution: false`, or unset under a `read`/`write` cap — FR-003a), and refused on both REST routes into the shared handler (`POST /api/v1/tools/call`, FR-015, and `POST /api/v1/code/exec`, below); every nested `call_tool` inside a script MUST pass the FR-013 gate and write its child record with `parent_id`, whichever route started the script. `POST /api/v1/code/exec` (the CLI-client-mode route, `internal/httpapi/code_exec.go`) dispatches through `CallToolDirect("code_execution")` and has its own error classifier (`classifyCodeExecError`), so the profile refusal MUST reach it as a **typed** error (`errors.As`, the Spec 097 technique that classifier already uses): code execution hidden by the effective profile → `403` in the route's existing `CodeExecResponse` error shape (`{ok:false, error:{code:"PROFILE_BLOCKED", message:<refusals.md text>}, request_id}`) and a `status=blocked`, `block_reason=profile_code_execution` record, never the `500 EXECUTION_FAILED` fall-through. The same typed error formats as the `unknown tool: code_execution` text on `POST /api/v1/tools/call` and MCP (FR-015), so only `/code/exec` — whose sole purpose is code execution, so admitting that a profile disabled it discloses nothing — reports a profile refusal, and its message names neither the profile's title nor its slug (FR-013). When both the profile and the global `enable_code_execution` gate refuse, the profile answer wins (refusal precedence, [contracts/refusals.md](contracts/refusals.md)).
- **FR-015**: The direct surface `/mcp/all` MUST omit profile-excluded tools from `tools/list` and refuse them at `tools/call` (mcp-go re-runs tool filters at call time); `/mcp/call` and `/mcp/code` inherit FR-013/FR-014. **Every dispatch path**: `WithToolFilter` governs only `tools/list` visibility and the mcp-go `tools/call` path; the FR-013, FR-014 and FR-016 gates MUST also be enforced **inside the shared handlers** (`handleCallToolVariant`, `handleCodeExecution` and its nested `call_tool`, `handleUpstreamServers`, `handleQuarantineSecurity`, `handleRetrieveTools`, `describe_tool`) from the request's one `ProfileResolution`, so that the existing REST routes into those handlers — `POST /api/v1/tools/call` (`handleCallTool` → `CallToolDirect`, which dispatches to them by name and bypasses every mcp-go tool filter) and `POST /api/v1/code/exec` (→ `CallToolDirect("code_execution")`, FR-014) — yield the same outcome as MCP. No other REST route dispatches a built-in tool handler (verified: `internal/httpapi/server.go` mounts only these two). One further REST route dispatches an **upstream** call without going through any built-in handler: `POST /api/v1/tool-calls/{id}/replay` (`Server.ReplayToolCall` → `runtime.ReplayToolCall`, which calls the upstream client directly). For a caller with an effective profile (on REST: a pinned `kind=agent` token) it MUST evaluate the FR-010 decision for the recorded `(server, tool)` with the tool's current effective annotations before dispatch. A `server_not_in_profile` exclusion takes the route's **existing non-disclosing out-of-scope `404`** — byte-identical (after substituting the echoed id) to the answer for an unknown record id and for a server outside the token's `allowed_servers`, with zero upstream calls and no activity record beyond what that 404 writes today — because a descriptive `403` would confirm to a pinned token that a record exists on a server outside its profile (refusals.md precedence: server scope keeps the Spec 105 shape). Only the three policy reasons (`denied_by_rule`, `unannotated_hidden`, `above_tier_cap`), which concern a server inside the caller's effective scope, answer `403` with the [contracts/refusals.md](contracts/refusals.md) text, a `status=blocked` record with the FR-013 `block_reason` and zero upstream calls. Administrator API keys (no profile) keep today's replay behaviour. `POST /api/v1/tools/call` is reachable by administrator API keys (no profile → unchanged) and by `kind=agent` tokens, including pinned ones (client credentials are refused by FR-023): an upstream tool excluded by a policy reason on an in-scope server → `403` with the [contracts/refusals.md](contracts/refusals.md) text (typed refusal capture, the Spec 097 `withCodeExecCapture` pattern) and the same `status=blocked` activity record; `code_execution` or a management tool hidden by the profile → the route's existing unknown-tool response, produced by the same `unknown tool: <name>` formatter (`internal/server/mcp.go` `CallToolDirect` default branch) with the same status and body shape as a nonexistent tool name — it differs from e.g. `{tool_name:"no_such_tool"}` only in the echoed tool name (and per-request identifiers such as `request_id`); `upstream_servers` under `management_tools: true` keeps the `AuthorizeServerOp` op set. The `profiles` tool is not added to `CallToolDirect`'s dispatch (REST has its own routes) and answers unknown-tool there.
- **FR-015a** (REST discovery, codex round 3): the REST routes that return tool names, descriptions or schemas to a non-administrator caller MUST apply the caller's own effective profile, so a pinned `kind=agent` token cannot read over REST a tool its profile hides from every MCP discovery surface (US1). At `638fa805a` these routes filter by the token's `allowed_servers` only (`canSeeServer`, `internal/httpapi/scope.go`) and ignore the pin entirely: `GET /api/v1/index/search` (`handleSearchTools`, `SearchToolsScoped` with a server-name predicate), `GET /api/v1/tools` without view-as parameters (`handleGetGlobalTools`), `GET /api/v1/servers/{id}/tools` (`handleGetServerTools`), `GET /api/v1/servers/{id}/tools/export` and `GET /api/v1/servers/{id}/tools/{tool}/diff`. From 108-d (the PR that lifts the FR-009a gate), for a caller whose resolution carries a profile (on REST: a pinned `kind=agent` token), each of them evaluates the FR-010 decision with the same predicate `retrieve_tools` uses: `GET /index/search` goes through `SearchToolsAdmitted` (filter before limit; the REST response gains no `hidden_by_profile` field — its shape is unchanged, excluded tools are simply absent); `GET /tools`, `GET /servers/{id}/tools` and the export omit excluded rows (exactly the non-admin `GET /tools?profile=<own pin>` visible-row set, FR-032, without its `counts`); the diff route answers an excluded tool with the route's existing unknown-tool `404`. A server outside the pin's `servers` is treated like a server outside `allowed_servers` (its tools are absent; the `/servers/{id}/*` subtree answers the existing scoped `404`). Administrators (no profile) and unpinned agent tokens are unchanged. Server-level REST reads (`GET /servers`, per-server status, logs, diagnostics) keep today's Spec 105 token scoping and are not narrowed by the pin in this spec — they name servers, not tools, and the pin's server list is already disclosed to the operator who minted the token.
- **FR-016**: When a session has an effective profile, `management_tools` on that profile decides the profile-level visibility of the management tools `upstream_servers` and `quarantine_security`: `false` → absent from `tools/list` and refused at call; `true` → visible, subject to the credential's own rules below; **unset** (every legacy profile, and any v3 profile that leaves the field unset — per-field inheritance, research D1) → pre-108 behaviour, with the two exceptions below (confined anonymous callers, client credentials). The `profiles` tool has no legacy behaviour and follows FR-017 only. `management_tools: true` never widens a credential beyond its existing rules: `quarantine_security` stays administrator-only, `profiles` follows FR-017, and **every agent token — including a client credential — keeps the Spec 028 `AuthorizeServerOp` policy unchanged**: `upstream_servers` is limited to the non-mutating operations `list` and `tail_log`, on servers inside its effective scope; every config-mutating or process-controlling operation (`add`, `add_from_registry`, `remove`, `update`, `patch`, `enable`, `disable`, `restart`, `refresh`) is refused. (Rationale: `patch` can replace a stdio server's `command`/`args` and `restart` re-launches it before any tool-level quarantine check — granting them to an AI-client credential would be arbitrary host code execution inside the credential's "scope"; server management stays an operator action on the Web UI, macOS app, CLI or an administrator MCP session — research D14.) An anonymous caller confined by `anonymous_profile` (source `anonymous`, or a URL/session selection admitted under that confinement) is treated like a v3 profile regardless of its target's `management_tools` being unset: management tools are hidden unless the effective profile sets `management_tools: true` (the `anonymous_profile` knob is new, so no legacy population exists); anonymous callers never get `quarantine_security` or `profiles` when confined. When the confining profile does set `management_tools: true`, a confined anonymous caller gets **exactly the client-credential op set** — `upstream_servers` `list` and `tail_log` on servers inside its effective scope, every mutating or process-controlling operation refused — because enforcement evaluates `AuthorizeServerOp` for it as a **non-administrator**: today's back-compat `auth.AnonymousContext()` is `AuthTypeAdmin` (`internal/auth/context.go`), which `AuthorizeServerOp` exempts from the entire `agentDeniedServerOps` denylist (`internal/auth/server_ops.go`), so without this rule any uncredentialed local process could `patch` a stdio server's command and `restart` it (research D14). The non-administrator view is not limited to the `AuthorizeServerOp` call: **every** `IsAdmin()` branch that shapes what a scoped caller sees, in a handler a confined anonymous caller reaches, MUST read the same view (`auth.ScopedView(ac, resolution)`, data-model §3) — at `638fa805a` these are the `upstream_servers` `list` server filter (`internal/server/mcp.go` ~4255), `handleTailLog`'s choice between the whole-file and the attributed log reader (~6283) and its container-mention redaction of `last_error` (~6323), and the scoped refusal-shape branch of `handleCallToolVariant` (~2587, US5-2) — so a confined anonymous caller gets the attributed, redacted `tail_log` output and the scoped list and refusal shapes of a client credential, never the administrator branch (research D29). An **unconfined** anonymous caller (`anonymous_profile` unset) keeps today's admin-typed behaviour unchanged. A client credential without a `management_tools: true` profile (including the default "All servers" binding and profiles with the field unset) sees no management tools; with one, it sees `upstream_servers` limited as above — an intended change from keyless clients, which ran as anonymous administrators (research D5). Global `disable_management`/`read_only_mode` remain ceilings.
- **FR-017**: The `profiles` tool MUST be listed only for administrator credentials of kind `api_key` or `socket` (never anonymous, agent or client tokens) whose effective profile is none or sets `management_tools: true`, and MUST be blocked by `read_only_mode` and `disable_management` for mutating operations only. Because `buildManagementTools()` returns no tools at all under `read_only_mode` or `disable_management` (`internal/server/mcp.go`), `profiles` MUST NOT be registered through it: it is registered unconditionally on the retrieve, call-tool and code-exec servers (visibility per session by `WithToolFilter`), and the two global gates are checked per operation inside its handler, so its read operations stay available when either gate is on.
- **FR-018**: `set_profile` MUST honour FR-022 and return the Spec 105 uniform refusal for every non-permitted target (locked, not in `switchable_to`, not selectable, unknown); naming the caller's own base is admitted (FR-022). The response's new `profile_source` field (and its `active_profile`) report only what the caller selected: `session` with the selected slug, or `none`/empty after `set_profile("")`, even when the next request falls through to a pin, binding or `anonymous_profile` base — a base is never named back to a non-administrator caller (research D27). `set_profile("")` is never a switch and is admitted for **every** caller, as today (`profile_tool.go`: an empty slug clears the selection and is always accepted): it clears the stored selection and the next resolution falls through to the caller's base — the pin, the binding (a switchable client returns to its bound profile, `profile_source=binding`), `anonymous_profile`, or none; it is never answered with the uniform refusal.
- **FR-019**: Aggregated prompts and resources keep Spec 105 server-scope filtering; tier policy and tool rules do not apply to prompts or resources (they have no tier) — recorded as a decision, not a gap, and pinned by a regression test (a profile's `max_tier`, `unannotated` and `tools.deny` leave `prompts/list` and `prompts/get` identical to a legacy profile with the same `servers`; resources are not aggregated today, and a future resource aggregation inherits the same test), so a shared visibility predicate can never start filtering them silently.

**C. Resolution, identity and binding (PV-A/PV-B)**

- **FR-020**: Profile resolution MUST be, highest wins: (1) `pin` — every locked client credential (`kind=client`, `profile_mode=locked`) and every regular agent token with a non-empty `profile_pin` (regular tokens have no `profile_mode`, data-model §3) (a locked client credential therefore reports `profile_source=pin`; the client is identified by `client_id`, not by the source); (2) `url` — `/mcp/p/<slug>`, admitted for bound/anonymous-confined callers only if permitted by FR-022; (3) `session` — `set_profile` selection, **re-validated on every request** against the caller's *current* base and FR-022 (a stored selection that is no longer permitted is cleared and resolution falls through, exactly like today's stale-selection rule); (4) `binding` — the bound profile of a `switchable` client credential; (5) `anonymous` — `anonymous_profile` for credential kind `anonymous`; (6) `none`. **Dangling bases never fall through**: a pin (tier 1), a switchable binding's bound profile (tier 4) or an `anonymous_profile` (tier 5) that names a profile no longer in config resolves to a deny-all scope that keeps the missing name (source `pin`, `binding` or `anonymous` respectively) — never to a lower tier and never to `none` (which would grant the credential's full `["*"]` reach); a switchable caller with a dangling base also admits no URL or session selection (its `switchable_to` is unknown, so none is permitted). This extends today's stale-pin rule (`profile_resolver.go`) to every tier that carries a base. The resolved profile and source MUST be available to every consumer from one resolver call per request (no second lookup, Spec 105 pair discipline).
- **FR-021**: A client credential MUST be an agent token with `kind=client`, `client_id`, `profile_pin`, `profile_mode` (`locked`|`switchable`), `allowed_servers=["*"]`, all three permissions (scope comes from the profile only), expiry ≤ 365 days (default 365). `profile_mode=locked` requires a non-empty `profile_pin` (validation error otherwise; "All servers" is always `switchable`). `profile_mode` applies to `kind=client` only: a regular (`kind` empty/`agent`) token keeps today's semantics — pinned iff `profile_pin` is set — and its empty `profile_mode` means "not applicable", never an invalid locked-without-pin record. **Secret format**: a client credential's raw secret uses the prefix `mcp_cli_` (same length and HMAC scheme as `mcp_agt_`), so the kind is carried by the secret itself and a pre-108 binary never treats it as an agent token (rollback-safe, research D27). **Fail-closed invariants at authentication**: on **every** MCP request (not only at mint time) the validator checks the stored record against the presented secret — a `mcp_cli_` secret MUST resolve to a record with `kind=client`, a `client_id` matching the pattern below, `name = "client-"+client_id`, `profile_mode ∈ {locked, switchable}`, `locked ⇒ profile_pin ≠ ""`, `allowed_servers=["*"]` and all three permissions; a `mcp_agt_` secret MUST resolve to a record whose `kind` is empty or `agent` and that carries no `client_id`/`profile_mode`; an unknown `kind` value is invalid. Any violation → `401 Agent token invalid: malformed credential record` and a warning log naming the token name, never a downgrade to a regular wildcard agent token. One active client credential per `client_id`. A `client_id` MUST match `^[a-z0-9][a-z0-9_-]{0,55}$` (lower-case, ≤ 56 chars, so `client-<client_id>` always satisfies the token-name rule `[A-Za-z0-9][A-Za-z0-9_-]{0,63}` and is a single safe path segment in `/clients/{id}`); every supported connect-registry id already conforms. A custom id (`POST /clients`, CLI `client add`, Web UI/macOS "Other client") that fails the pattern, or that equals a supported-client id (those are connected with FR-024 connect, never added as custom), is rejected on every surface with `400 {error, field:"id"}` — `invalid client id %q: must be lower-case letters, digits, '-' or '_', start with a letter or digit, and be at most 56 characters` or `client id %q is a supported client; use connect instead` — and nothing is minted or written. Token names `client-<client_id>`; regular tokens MUST NOT be created with the `client-` prefix. Because token names stay reserved by soft-revoked records, minting for a `client_id` whose existing `kind=client` record is **revoked or expired** replaces it in the same bbolt transaction (activity history stays attributable through its recorded `token_name`); minting over an **active** record (reconnect, rotate) is a staged rotation (FR-021a), never an immediate replace. Minting never touches a `kind=agent` token: if a pre-108 regular token already holds the name `client-<client_id>` (grandfathered, research D8), the mint is refused on every surface with `409 {error: "token name client-<id> is held by a regular agent token", conflicting_token: "client-<id>"}` and the remediation "revoke or delete token client-<id>, then connect again"; `GET /clients` reports the row with warning `client_token_name_conflict`.
- **FR-021a** (staged rotation): rotating an active client credential — `client rotate`, and connect/reconnect over an active credential — MUST NOT invalidate the old secret before the client config holds the new one. Stage 1 (one bbolt tx): add the new secret to the same `client-<id>` record as a **pending** secret (`pending_hash`, `pending_prefix`, `rotation_started_at`, indexed by a pending-hash index); both secrets authenticate as the same credential. Stage 2: write the client config through the normal previewed connect path (supported clients), or return the new secret once (custom clients). Stage 3 (one bbolt tx, idempotent **finalize**): promote the pending secret and drop the old. Finalize runs right after a successful stage 2; otherwise a **reconciler** (on startup and on every `GET /clients`/`GET /connect` classification) reads which secret the client config holds (the existing `credential_state` classifier, constant-time) and finalizes (config holds the new secret), rolls back by dropping the pending secret (config holds the old one), or keeps both and reports `client_rotation_pending` (neither/unreadable). Custom clients finalize on `POST /clients/{id}/rotate/finalize` or automatically after a 24-hour overlap, after which the old secret stops authenticating. A crash or config-write failure at any point therefore never leaves a client holding an invalidated secret. Rotation writes one `profile_change` `change=rotate` record when it completes, with `diff.outcome` = `finalized` or `rolled_back` (no new enum value).
- **FR-022**: Switching permission: a `locked` credential may never switch. Naming the caller's **own** current base — its pin or bound profile — via `/mcp/p/<slug>` or `set_profile` is not a switch and is admitted for every credential (preserving today's `selectable()` rule that a pinned caller may select `slug == pin`, so pinned tokens configured with `/mcp/p/<own-pin>` keep working, SC-003); `set_profile("")` returns a switchable caller to its binding. A `switchable` credential, and an anonymous caller confined by `anonymous_profile`, may switch only to profiles in the **bound** (or anonymous) profile's `switchable_to` (unset = none), each also selectable under Spec 105 rules. A caller with no base — API key, socket, anonymous without `anonymous_profile`, an unpinned legacy agent token, or a `switchable` client credential with an empty pin (the built-in "All servers" binding) — keeps legacy semantics (any selectable profile).
- **FR-023**: Client credentials MUST authenticate only on MCP endpoints; the REST API (`/api/v1/*`, `/events`) MUST reject them with `403` (recognised by the `mcp_cli_` prefix before any store lookup, and by `kind=client` after it).
- **FR-024**: Connect (all surfaces) MUST mint a client credential bound to a chosen profile — default: the built-in "All servers" scope, represented as an empty `profile_pin` with `profile_mode=switchable`, which reproduces today's reach (research D5) — and write it via the client's existing carrier (header, `mcp-remote --header`, `?apikey=` for Codex). Connect MUST NOT write the instance admin API key in any mode. `--keyless` (and the UI equivalent) writes a credential-less entry only when `require_mcp_auth` is off, and the client is then unidentified.
- **FR-025**: Existing entries holding the admin API key or no credential MUST be reported (`credential_state` ∈ `client`, `admin_key`, `none`, `revoked`, `expired`) and upgradable through an explicit, previewed reconnect; no automatic rewrite on upgrade. Because detection alone would leave the P4 exposure open indefinitely, every surface MUST also offer the **admin-key remediation**: (1) "Upgrade all clients holding the admin key" — one previewed bulk reconnect (`POST /clients/upgrade-admin-key-holders`, preview first, one `profile_change` `assign` per upgraded client, clients that fail are listed) that mints a client credential ("All servers" unless a profile is chosen) for every `admin_key` row — with a named profile the upgrade creates bindings and runs the FR-008a guard: every row receives the same binding, so the guard answers for all rows at once; the preview carries the would-be refusal (`guard: {code, bindings, fixes}`) and `apply` answers `409 binding_bypassable_without_auth` and mints nothing; (2) once no supported client reports `admin_key` — or when the operator accepts that the remaining ones will stop working — the prompt "Rotate the admin API key" linking to the documented rotation (set a new `api_key`, restart), which invalidates every remaining copy including in unmanaged clients. The `client_holds_admin_key` warning (and Spec 109's Needs-attention item built from it) persists until step 1 leaves no `admin_key` row; `mcpproxy doctor` `connect.admin_key_in_client_config` prints both steps.
- **FR-025a** (connect status is administrator-only): `credential_state` tells a reader which clients still hold the raw admin API key, the exposure FR-025 exists to close, and the preview (FR-024) discloses a client's profile and mode. Today `GET /connect`, `GET /connect/{client}` and `GET /connect/{client}/preview` are open to every authenticated caller, including scoped agent tokens (`internal/httpapi/server.go`: only the write/undo/disconnect verbs are gated; Spec 075 left the reads open). From 108-c, the PR that adds `credential_state`, these three reads MUST be administrator-only through `requireAdminRead` (a non-administrator caller, i.e. `!IsAdmin()` — agent tokens, pinned or not, and server-edition non-admin session principals — gets `403 {"error":"Admin credentials required to read client connection status"}` and no body data; the tray/socket and nil-context callers keep today's passthrough), the same rule Spec 109 applies to its sibling `GET /clients`. The route comment in `server.go` that says "Status/preview reads stay open" is replaced. **Cross-spec** (codex round 3): Spec 109-h, which adds the administrator-only `GET /clients`, gates the same three reads with the same middleware and message in its own PR (Spec 109 FR-030a), so no build serves an administrator-only `/clients` next to open connect reads that disclose the same client presence; 109-h and 108-c have no edge — whichever merges first adds the gate, the second keeps it (this spec's T030b and Spec 109's T125a pin the same `403`). `credential_state` is never added to a response a non-administrator can read; no other surface (SSE payloads, `GET /status`, MCP `upstream_servers`) carries it. Client credentials are already refused on every REST route (FR-023).
- **FR-026**: Reassignment (profile or mode change) MUST be one service operation used by REST, CLI, MCP, Web UI and macOS; it updates the credential in the token store, clears the stored `set_profile` selection of every live session authenticated by that credential, emits `client.binding_changed` on the event bus, sends `notifications/tools/list_changed` to every live MCP session authenticated by that credential, writes a `profile_change` activity record, and never touches the client's config file. It applies only to a client whose `credential_state` is `client` (an active `kind=client` credential): for `none`, `admin_key`, `revoked` or `expired` it is refused on every surface with `409 {error: "client <id> has no active client credential; connect it with a profile first", code: "no_client_credential"}` and writes nothing — it never mints a credential implicitly (FR-025: upgrades happen only through the previewed connect); bulk moves skip such clients and report them in `skipped[]`. A reassignment that would make the binding bypassable is refused by the FR-008a guard (`409 binding_bypassable_without_auth`) before anything is written; a bulk move applies the guard per client and reports refused clients in `skipped[]` with that code. The Web UI and macOS disable the profile picker and lock toggle on such rows and offer "Upgrade to client credential" / "Reconnect" (the previewed connect with the chosen profile) instead.
- **FR-027**: Cache provenance (Spec 105) MUST include the effective profile's policy fingerprint **and** the tool-tier generation — a monotonic counter bumped whenever any tool's effective annotations change (upstream re-list, `annotation_overrides` once #1323 lands) or a tool appears/disappears, published with the (index, snapshot) pair — because the policy fingerprint alone does not change when a tool goes from unannotated/read to destructive with no profile edit; a cached page produced under a different policy, pin, binding or tool-tier generation is refused by the existing rule. Editing, renaming or deleting a profile — through the service or by a hand edit picked up on config reload (detected by comparing each profile's policy fingerprint and server set between the previous and the new published snapshot) — MUST send `tools/list_changed` to every live session whose latest effective profile (FR-028) or base is that profile; changing `anonymous_profile` MUST send it to every live anonymous session. Enforcement never depends on the notification (it is re-evaluated per request).
- **FR-028**: Sessions MUST record the authenticating token name and client id at initialize, and the latest effective profile and source, so session rows and reassignment notifications can find them.

**D. Attribution and filters (PV-A/PV-C)**

- **FR-029**: Every activity record written in an MCP request context MUST carry first-class `profile`, `profile_source`, `client_id`, `client_name` (reported `clientInfo.name`), `token_name`; blocked records carry `block_reason`. Values are those in effect when the call ran and are never rewritten.
- **FR-030**: New activity type `profile_change` MUST record every change in data-model §5 (`create`, `update`, `delete`, `rename`, `classify`, `assign`, `lock`, `unlock`, `forget`, `rotate`, `anonymous`) with `actor_kind` (credential kind) and `actor_name` (credential name) — two fields, data-model §5 — `surface` (`web`, `macos`, `cli`, `mcp`, `api`), `profile`, `previous_profile`, `client_id`, `token_name` and a redacted diff. Client-credential lifecycle operations are changes too, written by the one clients service (FR-026) on every surface: `rotate` (old and new token names in the diff, never a secret), `forget` (the revoked `token_name`, and `disconnected` when the config entry was removed), and a **mint** (connect with a profile, `client add`) as `change=assign` with an empty `previous_profile`. `change=anonymous` is written whenever `anonymous_profile` is set or cleared through any API path — `PATCH /config` routes that field through the profiles service (the same one that moves it on rename/delete) rather than a generic config write; hand edits of the config file are not attributed (same as every other hand edit).
- **FR-031**: `GET /activity`, `/activity/summary`, `/activity/usage`, `/activity/export` and `/sessions` MUST accept `profile`, `client`, `token` (alias: `agent`, kept); `GET /tools` accepts `profile` and `client` (view as, FR-032) and `GET /servers` accepts `profile`; `GET /clients` accepts `profile` (rows whose **current** binding is that profile; `-` = "All servers") and `client` (exact id), and `GET /tokens` accepts `profile` (tokens whose **current** `profile_pin` is that profile; `-` = unpinned) and `token` (exact name) — on these two management lists the filter is server-side and means current state, not the value recorded at call time. `client_name` (advisory, matches the self-reported name) is accepted by exactly `GET /activity` and `GET /activity/export` (REST), and by CLI `activity list`, `activity export` and `activity watch` (`watch` streams `/events` and applies all its filters client-side to the SSE activity payloads, as its existing `--server` filter does, so those payloads carry the FR-029 fields); `GET /activity/summary`, `/activity/usage` and `/sessions` reject it with `400` (`client_name is not supported on this endpoint; filter by client`) rather than silently ignoring it, and CLI `activity summary` rejects `--client-name` the same way; the Web UI and macOS show it on rows but filter by `client`. `profile` matches the recorded value (and legacy `metadata.profile`); `client` matches `client_id`; the `unattributed` sentinel (`client=-`, `profile=-`) matches records with the field empty. Authorization filtering (Spec 105 `AllowedServers`) is applied before these filters. **Availability signal**: the PR that lands these backend filters (108-e) adds `features.scope_filters: ["profile","client","token"]` to `GET /api/v1/status`; Spec 109's `useScopeQuery()` and macOS `ScopeFilter`, which already carry these parameters hidden, un-hide them when the list is present (Spec 109 contracts/url-filter-contract.md). **Version skew**: the backend never silently ignores these parameters. Spec 109-k adds a gate (`internal/httpapi/scope_filters.go`) that answers `400 {error, code: "unsupported_scope_filter", param}` for any of `profile`, `client`, `token` on the endpoints above that is not in the supported list, and `features.scope_filters` is read from that same list; 108-e fills the list (the three names) in the same change that makes the handlers honour them, so a build accepts a scope parameter exactly when it advertises it. 108-e and 109-k have no edge: whichever merges **first** creates both the single list variable and the gate function, and calls the gate in every handler it touches, so no build parses a scope parameter without the gate (a name the handler does not honour, e.g. `token` on `GET /tools`, is a `400`, never an unfiltered `200`); the second reuses both rather than adding a second one. The existing `agent` alias is not gated on `GET /activity` and `/activity/export`, which honour it today; on `/activity/summary`, `/activity/usage` and `/sessions`, which ignore it at `638fa805a`, it is gated exactly like `token` until 108-e makes them honour it (codex round 4). Each gated handler also passes the parameters it honours itself: `GET /clients` and `GET /tokens` honour `profile`/`client`/`token` only from 108-f, which always merges after 108-e, so in that window those two routes still answer `400 unsupported_scope_filter` — a loud refusal, never unfiltered rows presented as filtered. This spec never defines the URL contract itself.
- **FR-032**: `GET /tools` with `client` or `profile` MUST return every tool with `access: {visible, callable, reason}` ("view as") computed by the same enforcement chain as the access explainer (FR-035) and actual calls, walked in the canonical order of [contracts/refusals.md](contracts/refusals.md) and data-model §7 — `credential → profile → server_in_scope → tool_rule → tier_cap → token_permission → global_gate → server_state → tool_approval` — so `callable: true` holds exactly when a real call would pass every gate. `reason` is empty when callable; otherwise it names the **first failing step**, where the three steps that carry the FR-010 profile decision report its reason when the profile predicate is what fails there: `server_in_scope` → `server_not_in_profile` (server ∉ the profile's `servers`), `tool_rule` → `denied_by_rule`, `tier_cap` → `unannotated_hidden` or `above_tier_cap`. Every other failure reports the step name: `credential` (revoked/expired credential), `profile` (dangling base, FR-020), `server_in_scope` (server inside the profile but outside the subject credential's token servers — a legacy-scope token; client credentials are always `["*"]`; the profile predicate is evaluated first within the step, so a server outside both reports `server_not_in_profile`), `token_permission`, `global_gate`, `server_state`, `tool_approval`. The full value set is the data-model §7 EffectiveTool `reason` enum (one Go source of truth, FR-052). For a `profile` subject there is no credential: the `credential` and `token_permission` steps are `skip` and `server_in_scope` checks only the profile's `servers`. **Authorization** (the caller, not the subject): `client=` is administrator-only on `GET /tools` and on `GET /profiles/{name}/effective-tools`, exactly like `GET /access/explain` — a non-administrator caller gets the `requireServerOp` refusal (`403`), because another client's verdicts (e.g. `above_tier_cap`) disclose its binding; `profile=` is accepted from any non-client caller for profiles it can read (`GET /profiles/{name}` reachability; otherwise the same uniform `404`), but a **non-administrator** caller receives only the rows that are `visible` under that profile plus aggregate `counts` (`hidden` total, never per server, per tier or per reason) — never an excluded row, its tier or its denial reason, keeping FR-011's promise that discovery never names or describes a hidden tool; full excluded rows with reasons are administrator-only (the same rule applies to `GET /profiles/{name}/effective-tools`). For every caller the existing authorization filter (Spec 105 `AllowedServers`, #1166) removes the caller's out-of-scope rows **first**; a removed row never appears, so the caller's own token scope is never reported as a `reason`. Without `client`/`profile`, output is unchanged.
- **FR-033**: `GET /sessions` rows MUST include `client_id`, `token_name`, `profile`, `profile_source`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: All six audit acceptance checks pass as automated tests (Go E2E for MCP behaviour, Playwright for the Web UI deep links) and in the live-verification recipe on a real instance.
- **SC-002**: Under a `max_tier: read` profile, zero write, destructive, denied or unclassified-unannotated tools — **other than those explicitly admitted by a `tools.allow` rule that no `tools.deny` rule matches** (FR-010 step 3; e.g. `notion:update_page` in the fixture) — are discoverable or callable across the full enforcement matrix (every surface × every endpoint × every resolution source, incl. the REST discovery and dispatch routes of FR-015/FR-015a for a pinned token), measured by the matrix test.
- **SC-003**: Every Spec 057 and Spec 105 test passes unmodified; frozen tool-surface goldens change only where a new built-in (`profiles`) or the `hidden_by_profile` field is deliberately added, each listed in the PR.
- **SC-004**: A user can create a read-only profile and bind a client to it in under 2 minutes from any one of Web UI, macOS app or CLI without editing JSON.
- **SC-005**: A reassignment takes effect on the client's next request with zero client config writes (file hash unchanged) and the live session receives `tools/list_changed` within 1 s.
- **SC-006**: For the same seeded dataset, the Activity record set returned for each `(profile, client, token, status)` filter combination is identical across REST, CLI, Web UI and macOS (parity test).
- **SC-007**: `retrieve_tools` p95 latency under a v3 profile at 1,000 tools increases by ≤ 5 ms versus the same query under a legacy profile (constitution I).
- **SC-008**: After upgrade, no client config written by MCPProxy contains the instance admin API key when connect is run again; `mcpproxy doctor` reports every pre-existing entry that still does; after the FR-025 bulk upgrade plus admin-key rotation, zero client configs on the machine authenticate with an admin-equivalent credential (test: seeded `admin_key` entries → bulk upgrade → rotate → every former admin-key config gets `401` on REST).
- **SC-009**: The access explainer's verdict equals the actual call outcome for 100% of rows in the enforcement-matrix fixture.
- **SC-010**: No build between 108-a and 108-d admits a v3 policy field or `anonymous_profile` (FR-009a). In every build from 108-c on, a client bound to a named profile cannot reach a tool outside that profile by omitting or corrupting its credential (FR-008a, FR-021). On **rollback to a pre-108 binary**, a client credential never authenticates as an agent token (REST `401`; MCP `401` with `require_mcp_auth` on), but a pre-108 binary knows neither bindings nor `anonymous_profile`, so with `require_mcp_auth` **off** it treats the unrecognised `mcp_cli_` secret like an omitted credential and gives it today's unconfined anonymous reach (Edge Cases, research D27/D29). The rollback guarantee is therefore stated only for `require_mcp_auth: true`, and the downgrade procedure (docs and release notes, T124/T125) requires turning `require_mcp_auth` on before downgrading past 108-c. Pass condition: the enforcement matrix's anonymous-with-binding rows, the malformed-record table and the rollback test (a `mcp_cli_` secret against the pre-108 auth middlewares: `401` on REST, `401` on MCP with `require_mcp_auth` on, and — documented, not a guarantee — anonymous with it off) all pass.
