# Research: Profiles v3 — decisions and clarifications

Every open question the audit and the four surface inventories left is settled here. Rule applied when a choice was open: **fail closed for security, stay backward compatible for config and existing behaviour, add no dependencies** — and record the choice. Code references are to `origin/main` at `638fa805a`.

## Clarifications (session 2026-09-25, autonomous)

- Q: Does a profile with only `name`+`servers` change behaviour? → A: No. Every v3 field is optional; unset means "pre-108 behaviour" (D1).
- Q: What does a read-only profile do with tools that have no annotations? → A: Hides them by default; the user classifies them per profile (D2).
- Q: Where is a client's profile stored? → A: On the client's own credential (an agent token of kind `client`) in `config.db` (D5).
- Q: Does connect still write the admin API key? → A: Never. It writes a per-client credential; `--keyless` exists only while auth is optional (D9).
- Q: What does a new client get if the user picks no profile? → A: "All servers", switchable — today's reach (D5).
- Q: Can an agent change its own scope? → A: Only a `switchable` client, only to profiles its *bound* profile lists in `switchable_to` (D6).
- Q: Which admin credentials see the `profiles` MCP tool? → A: API key and socket only; never anonymous, agent or client tokens (D14).
- Q: Is the Clients page in this spec or M1? → A: The binding-relevant part is here; M1 keeps wizard reuse and Endpoint & mode (D16).

## D1 — Legacy vs v3 semantics

**Decision**: each v3 field is a pointer/optional; unset = inherit pre-108 behaviour: no tier cap, unannotated → read, no rules, `code_execution`/`management_tools` follow the global gates, `switchable_to` legacy (D6). New profiles created through any surface get explicit safe defaults in the editor/CLI/MCP create path (`max_tier: read`, `unannotated` left unset so FR-003 yields `deny`, `management_tools: false`); `code_execution` is left unset (inherit) unless the user chooses.
**Why**: `docs/features/profiles.md` documents behaviour (e.g. `upstream_servers list` at a profile URL) that Spec 057 tests pin; flipping it for existing configs would be a silent behaviour change. Safety for *new* profiles comes from surface defaults, not from reinterpreting old config.
**Rejected**: a `version: 3` marker (one more thing to get wrong; field presence is enough).

## D2 — Unannotated tools and classification

**Decision**: intrinsic tier from effective annotations; "unannotated" = neither `destructiveHint` nor `readOnlyHint` set. Under `max_tier` read or write the default is `deny` (FR-003). A profile may classify an unannotated tool (`tools.classify`), which applies only while the tool stays unannotated (FR-005). This is profile-local and does not change the tool's `call_with` hint, the Spec 018 variant validation, or the Spec 105 token target-tier gate (still `tierForAnnotations`, which maps unannotated → read).
**Interaction with PR #1323** (`annotation_overrides`, per-server, admin-only): overrides feed the *effective annotations* seam, so an operator override is seen by every profile, while `tools.classify` stays profile-local. Both orders of landing work because intrinsic tier reads one function (`profile.IntrinsicTier(effectiveAnnotations)`); when #1323 lands its merged annotations are passed in.
**Why fail-closed**: the audit's trap #1 — a read-only profile must not let an unannotated `delete_repo` through. Hiding is recoverable (editor lists them); leaking a write is not.
**Rejected**: changing `DeriveCallWith`'s global default (breaks every legacy caller and the Spec 018 hint); storing classification in server config (widens blast radius to every caller).

## D3 — Decision order, allow/deny

**Decision**: server membership → deny → allow → unannotated policy → tier cap (FR-010). Deny beats allow. Allow is an exception to the cap and to the unannotated policy only; it never admits a server outside `servers` and never bypasses server state, approval, token permissions, `read_only_mode`, or global gates (FR-006). Patterns are `server:tool` with `*` only (compiled once per config snapshot into anchored matchers; no regex exposure).
**Rejected**: allow-list-only mode (out of scope; can be added later as `tools.mode: allow_only`).

## D4 — `hidden_by_profile` and disclosure

**Decision**: count of query-matching tools inside the caller's effective **server** scope excluded by the tool policy (reasons deny/unannotated/cap). Server-membership exclusions are never counted (that would leak out-of-scope population, violating Spec 105). The count is computed on the same authorized corpus the Spec 105 differential oracle compares, so the two fixtures produce equal values. Omitted when the effective profile has no tool policy, preserving legacy byte-parity.
**Call-time naming vs discovery hiding**: discovery (`retrieve_tools`, `describe_tool`, `tools/list`) omits excluded tools (uniform not-found for `describe_tool`). A `call_tool_*` naming an excluded tool on an **authorized** server gets a descriptive refusal stating the tool, its tier and the reason — but, since codex round 1 (D27), **not** the profile's title or slug. Spec 105 made the *server* the disclosure unit and explicitly exempted tier denials on authorized servers from non-disclosure (FR-010 precedence); the descriptive refusal is what lets the agent and the user fix the scope. Out-of-scope servers keep the non-disclosing shape.

## D5 — Where the binding lives; default binding

**Decision**: the binding **is** the client credential: `AgentToken` gains `Kind` (`agent`|`client`, empty = `agent`), `ClientID`, `ProfileMode` (`locked`|`switchable`, client credentials only; regular tokens have no mode and stay pinned iff `profile_pin` is set, so every existing pinned token keeps its exact semantics — codex round 1: an "empty = locked" rule plus "locked ⇒ pin" would have made every unpinned legacy token invalid). No new bucket, no second source of truth to reconcile. The "Client" entity on every surface is a derived view: supported-client registry (`internal/connect`) ∪ custom client ids ∪ credential ∪ connect status ∪ session/activity aggregates.
**Default**: when the user picks no profile at connect time the credential has an empty pin and mode `switchable` = "All servers": the same servers and tools as today, and legacy `set_profile` freedom (no base). **One intended narrowing**: a keyless client used to run as an anonymous administrator and could call `upstream_servers`/`quarantine_security`; with a client credential it sees no management tools unless bound to a profile with `management_tools: true` (FR-016) — and even then only `upstream_servers` `list`/`tail_log` (the Spec 028 agent-token policy) — and never `quarantine_security` or `profiles`. Every connect surface states this in the preview ("This client can no longer add, change or restart servers; manage servers from the Web UI, the macOS app or the CLI"). `--keyless` (auth optional only) keeps the old behaviour for users who need it. `locked` with an empty pin is rejected (it would be "locked to everything").
**Why config.db, not the config file**: the binding is inseparable from a secret-bearing credential that is per machine and already stored in `config.db`; putting half in the config file would split one transaction across two stores. Recorded in plan Complexity Tracking against constitution III.

## D6 — Resolution precedence and `switchable_to`

**Decision** (FR-020): `pin`(locked credential) > `url` > `session` > `binding`(switchable credential) > `anonymous` > `none`. A stored `session` selection is re-validated on every request against the caller's current base (so narrowing a binding or its `switchable_to` takes effect on the next request), and a reassignment also clears the stored selections of that credential's live sessions (zcode review r1 finding 1). For a switchable credential or an anonymous caller confined by `anonymous_profile`, URL and session selections are admitted only if the target is in the **base** profile's `switchable_to` (unset = none) and is Spec 105-selectable. Evaluating against the base profile, never the currently selected one, makes chains non-escalating. Callers with no base (API key, socket, anonymous without `anonymous_profile`, unpinned legacy agent token) keep legacy "any selectable profile".
**Own base is not a switch** (review round 1): naming the caller's own pin or bound profile via `/mcp/p/<slug>` or `set_profile` is admitted for every credential, locked included — today's `profileIndex.selectable()` already admits `slug == pin` for pinned tokens (`internal/server/profile_tool.go`), and Spec 105 tests exercise `/mcp/p/<own-pin>`; refusing it would break SC-003.
**Dangling bases** (review round 1, high): the stale-pin deny-all rule (`profile_resolver.go`, tier 1) applies equally to a switchable binding's bound profile and to `anonymous_profile`. A switchable client whose bound profile was hand-deleted resolves deny-all with source `binding`; falling through to `none` would hand it its `["*"]` credential reach — the widening the stale-pin rule exists to prevent.
**Why a switchable binding sits below url/session**: switching is the point of `switchable`; the binding is the default the session returns to on `set_profile("")`.

## D7 — Client credentials are MCP-only and profile-scoped

**Decision**: `allowed_servers=["*"]`, permissions = all three; the profile is the only scope (fixes P7's duplication for clients). REST (`/api/v1/*`, `/events`) rejects `kind=client` with 403 in `apiKeyAuthMiddleware` (FR-023). Today REST admits agent tokens (`internal/httpapi/server.go:500`), so without this a client credential with `["*"]` could read full activity payloads — strictly worse than intended.
**Legacy tokens** (`kind=agent`) keep REST access and their fields; the UI shows them as "legacy scope".

## D8 — Naming, uniqueness, expiry, rotation

**Decision**: name `client-<client_id>` (token name rules: `[A-Za-z0-9][A-Za-z0-9_-]{0,63}`); custom ids use the same charset, lower-case, ≤ 56 chars — binding as FR-021 `^[a-z0-9][a-z0-9_-]{0,55}$`, `400 {error, field:"id"}` otherwise, and a custom id may not equal a supported connect-registry id (review round 4: the rule lived only here, so `POST /clients {id:"Dev/Laptop"}` was admitted by every FR and produced a non-conforming token name and an ambiguous `/clients/{id}` path segment). Regular tokens can no longer be created with prefix `client-` (existing ones grandfathered as `kind=agent`). **Collisions** (review round 1): token names are unique per owner *including soft-revoked records* (`storage.CreateAgentToken` checks every stored record, `internal/storage/agent_tokens.go`), so "mint new, revoke old" under the same name is impossible as two records; minting therefore replaces an existing `kind=client` record named `client-<id>` in one bbolt transaction **only when that record is revoked or expired**; over an **active** record (reconnect, rotate) the mint is the staged rotation of FR-021a/D27 — a pending secret beside the old one, finalize after the config write — never a same-transaction replace, which would invalidate the secret installed in the client before the new one is written (codex round 3 corrected this sentence, which predated FR-021a). A grandfathered `kind=agent` token with that name is never touched: the mint is refused `409` with `conflicting_token` and the remediation "revoke or delete token client-<id>, then connect again", and `GET /clients` raises `client_token_name_conflict`. Silently revoking a token created for an unrelated purpose, or suffixing the client credential's name, were both rejected (the first destroys user data, the second breaks the `client-<id>` invariant every surface relies on). Expiry default and cap 365 days (Spec 107 FR-011, `auth.MaxTokenExpiry`); from 14 days before expiry every surface shows "expires in N days". Rotate is staged (D27, FR-021a): add the new secret as a pending secret on the same record (both valid), write config via the normal previewed connect path, then an idempotent finalize drops the old one; a reconciler resolves crashes by reading which secret the config holds — never silent, never an invalidated secret in a client config. `MaxTokens` (100) counts client credentials.

## D9 — Stop writing the admin API key

**Decision**: `serverEntryParams.credential` is sourced from the minted client credential, never `config.APIKey` (`internal/connect/connect.go:252`). `--keyless` writes a credential-less entry and is refused when `require_mcp_auth` is on. Carriers unchanged (header; `mcp-remote --header` for Claude Desktop; `?apikey=` for Codex, which cannot express headers — accepted precedent, flagged in docs). Existing entries are classified by `GET /connect/{client}` into `credential_state` (`client`, `admin_key` by constant-time compare with the configured key, `none`, `revoked`, `expired`) and upgraded only through an explicit previewed reconnect. No automatic rewrite on upgrade (connect UX rule: diff + backup notice before the button).

## D10 — Live reassignment

**Decision**: tokens are validated from storage on **every** MCP HTTP request (`mcpAuthMiddleware`, `server.go:519`), so a pin change applies to the next request with no cache to invalidate in the auth path. For notification, `SessionInfo` records `TokenName`/`ClientID` at initialize (FR-028); the binding service emits `client.binding_changed`; the MCP server's event subscriber looks up sessions by token name and calls mcp-go `SendNotificationToSpecificClient(sessionID, "notifications/tools/list_changed")`. Profile edits, renames and deletes notify sessions whose last effective profile or base is the changed one (and always rely on per-request evaluation for correctness). *Review round 1*: the trigger is a per-profile diff of (policy fingerprint, server set, existence) between the previous and the newly published config snapshot, computed by the same subscriber — so service writes and hand edits picked up by the file watcher are covered by one mechanism (config reload does not push `list_changed` to routing-mode sessions today; it is content-guarded, `mcp_routing.go`). An `anonymous_profile` change notifies every anonymous session. Cache: Spec 105 stamps already include pin and profile servers; add `PolicyFingerprint` (SHA-256 of the canonical compiled policy) so pages produced under an older policy are refused by the existing comparison, **and** `ToolTierGeneration` (D27) so a page cached while a tool was unannotated/read is refused after the tool's annotations change with no profile edit.
**Concurrency**: no new locks; the subscriber runs on the existing event-bus goroutine pattern; the session index is part of `SessionStore`'s existing ownership.

## D11 — Attribution fields and filters

**Decision**: first-class `Profile`, `ProfileSource`, `ClientID`, `ClientName`, `TokenName`, `BlockReason` on `ActivityRecord` (struct fields because `ActivityFilter.Matches` compares struct fields — same reasoning as `WorkSessionID`, `activity_models.go:216`). `metadata.client_name`/`metadata.profile`/`metadata.agent_name` stay written for one release for old readers. Filters: `profile` matches `Profile` or legacy `metadata.profile`; `client` matches `ClientID` only (authoritative; self-reported names can be spoofed); `client_name` is an **advisory** filter for unidentified legacy clients, accepted by exactly `GET /activity` and `GET /activity/export` and by CLI `activity list|export|watch` (`watch` filters the `/events` stream client-side, like its existing `--server`), never by summary/usage/sessions (review round 2); `token` matches `TokenName` or legacy `metadata.agent_name` (`agent` kept as alias). Sentinel `-` = unattributed.

## D12 — Scope of the `profiles` MCP tool

**Decision**: operations `list, get, create, update, delete, rename, classify, assign, list_clients, effective_tools, explain`. No `connect`, `rotate`, `add client` or token minting over MCP: those write local client config files or mint credentials, which the codebase already treats as operator-only (issue #878 class; `requireServerOp` on `/connect`, Spec 028 refusing token minting from agents). `list_clients` returns client rows without local config paths.

## D13a — What counts as anonymous

**Decision**: the anonymous tier applies to credential kind `anonymous`, which `mcpAuthMiddleware` assigns in two branches when `require_mcp_auth` is off: no token (`server.go:485`) and an unrecognised non-agent token (`server.go:568`). An invalid `mcp_agt_` token is rejected `401` (`server.go:524`), never downgraded. FR-008/US5 use this wording (zcode r1 finding 4).

## D13 — `anonymous_profile` is operator-only

**Decision**: set via config file, Settings (Web UI/macOS) or `mcpproxy profile anonymous`; not via MCP. It governs authentication fallback for every uncredentialed caller, the same class as `require_mcp_auth`, which is not MCP-settable today. All API paths (`PATCH /config` from Web UI/macOS, the CLI) go through `profiles_service.SetAnonymous`, which validates, writes `profile_change` `change=anonymous` (FR-030) and emits `profiles.changed` (review round 1).

**Binding-bypass** (review round 1; hardened in codex round 1, D27): the omitted-credential bypass applies to every binding with a named profile, not only locked ones, so the code is `binding_bypassable_without_auth` (was `lock_bypassable_without_auth`; Spec 109 uses the same name) and the doctor check `profiles.binding_bypass`. Since D27 it is no longer only a warning: `binding_bypassable_without_auth` is the `409` refusal of every API operation that would create the condition, and the runtime guard denies anonymous callers (`anonymous_denied_by_binding_guard`) when a hand edit creates it. It fires when `require_mcp_auth` is off and any client credential has a non-empty pin while `anonymous_profile` is unset or wider than that binding — since codex round 3 (D29) "wider" compares reachable sets (incl. `switchable_to`) on servers, cap, unannotated handling, every currently admitted tool (deny/allow rules included) and the code-execution/management capabilities, not only server set and cap. The empty-pin "All servers" binding does not trigger it.

## D14 — Management tools

**Decision**: `management_tools` unset keeps legacy visibility for `upstream_servers`/`quarantine_security` (D1) — except for anonymous callers confined by the new `anonymous_profile`, which have no legacy population and therefore get hidden-unless-`true` (zcode r3 finding 4). `management_tools: true` only lifts the profile-level hiding; each credential keeps its own rules (quarantine approval admin-only; agent tokens per `AuthorizeServerOp`; client credentials are agent tokens and get exactly the same `AuthorizeServerOp` policy — `upstream_servers` `list` and `tail_log` on in-scope servers, every config-mutating or process-controlling op refused). *Review round 1 (high)*: an earlier draft granted client credentials `add`/`add_from_registry`/`patch`/`enable`/`disable`/`restart`/`refresh` on in-scope servers. Rejected: `patch` replaces a stdio server's `command`/`args` (`args_json replaces entirely`, `upstream_servers` doc in `internal/server/mcp.go`) and `restart` re-launches it before any tool-level quarantine check, so a prompt-injected client bound to any `management_tools: true` profile could run arbitrary commands on the host from inside its "scope". Server lifecycle and config stay operator actions (Web UI, macOS, CLI, administrator MCP session); a client that must manage servers is out of scope for 108 and would need its own spec with an approval step. The new `profiles` tool has no legacy: listed only for credential kinds `api_key`/`socket` with no effective profile or an effective profile with `management_tools: true`; mutating ops blocked by `read_only_mode`/`disable_management`. Anonymous excluded even though anonymous is admin-shaped today: letting an uncredentialed local process reassign a locked client would defeat the lock. Hiding uses mcp-go `WithToolFilter` on the retrieve/call/code servers (already used on the direct server, `mcp_routing.go:1123`), which re-runs at `tools/call`.
**Confined anonymous callers** (review round 2, high): `auth.AnonymousContext()` is `AuthTypeAdmin` for back-compat (`internal/auth/context.go`), and `AuthorizeServerOp` exempts every admin-typed context from the whole `agentDeniedServerOps` denylist (`internal/auth/server_ops.go`). Left alone, `anonymous_profile` naming a `management_tools: true` profile would hand any uncredentialed local process `patch` + `restart` — the host-code-execution path removed from client credentials above. Decision: for a caller confined by `anonymous_profile`, the management gates evaluate `AuthorizeServerOp` against a non-admin view of its context, giving it exactly the client-credential op set (`list`/`tail_log` on in-scope servers). Rejected alternative: forbidding `management_tools: true` on any profile used as `anonymous_profile` — it would make the validator depend on cross-field state that changes with every `anonymous_profile` edit, and still leave the admin-typed context as a latent bypass. Unconfined anonymous callers are untouched (legacy parity).
**Every dispatch path** (review round 2): `WithToolFilter` is not an enforcement boundary on its own — REST `POST /api/v1/tools/call` (`handleCallTool` → `CallToolDirect`, `internal/server/mcp.go`) calls `handleUpstreamServers`, `handleQuarantineSecurity`, `handleCodeExecution` and the `call_tool_*` handlers by name, as `handleUpstreamServers`' in-handler `AuthorizeServerOp` check (issues #877/#878) already acknowledges. The profile gates therefore live inside those shared handlers, keyed on the one `ProfileResolution`; the tool filter only keeps `tools/list` honest. On REST a profile refusal is `403` (typed capture, the Spec 097 `withCodeExecCapture` pattern) and a hidden tool answers the route's existing unknown-tool error.

## D17 — Events and activity type names

**Decision**: activity type `profile_change`; SSE `profiles.changed` (payload `{name, change}`) and `client.binding_changed` (`{client_id, profile, previous_profile, mode}`); existing `active_profile.changed` kept during deprecation. `surface` values: `web`, `macos`, `cli`, `mcp`, `api` — sent by first-party clients in `X-MCPProxy-Surface` (REST) and inferred `mcp` for the tool; unknown/absent = `api`.

## D18 — Keeping surfaces in sync

**Decision**: enumerations live in `internal/profile/contract.go`; `frontend/src/types/contracts.ts` is regenerated by the existing generator (`cmd/generate-types`); golden fixtures under `internal/profile/testdata/contract/` (`profile_full.json`, `profile_legacy.json`, `client_rows.json`, `explain_blocked.json`, `effective_tools.json`, `activity_attributed.json`) are decoded by Go tests, a vitest spec and a Swift `ProfilesV3ContractTests`. A CLI parity test asserts every REST field in `contracts/rest-api.md` has a CLI flag or column and every MCP argument name equals the REST field name.

## D19 — Rename and delete

**Decision**: delete of an in-use profile → `409 {used_by}` unless `reassign_to=<existing>` (moves pins/bindings then deletes) or `force=true` (pins dangle → deny-all; never wider). Rename = create new + move pins/bindings (rewrite `profile_pin` on every agent token and client credential in `config.db` that names the old slug, in one bbolt transaction) + rewrite other profiles' `switchable_to` and `anonymous_profile` references + delete old, executed in that order so any mid-way failure leaves both profiles present (never a widening). Delete removes the deleted name from other profiles' `switchable_to` (never replaces it with the reassign target, which could widen switch options) and, when the profile is the `anonymous_profile`, refuses unless `reassign_to` is given, in which case `anonymous_profile` moves to it. That refusal has its own shape — `409 {code: "profile_is_anonymous_profile", used_by.anonymous_profile: true}` — distinct from the `profile_in_use` case, and **`force` does not override it** (review round 2): the profile may be the `anonymous_profile` while no client or token pins it, and a forced delete would silently move every anonymous caller to a dangling deny-all base — an operator should make that choice explicitly by changing `anonymous_profile` first. Each step writes `profile_change`. Hand-edited config deletions keep the existing deny-all rule and surface "profile missing".

## D20 — Performance

**Decision**: compile each profile's policy (matchers, classification map, cap) once per published config snapshot inside the existing `profileIndex` pair (Spec 105 D17), so per-tool evaluation is a map lookup plus at most `len(allow)+len(deny)` anchored glob matches. SC-007 budget ≤ 5 ms p95 at 1,000 tools, measured with the Spec 105 scope-latency harness.

## D21 — URL parameter names

**Decision** (superseded by D27's ownership rule): the URL contract, `useScopeQuery` and every parameter name are **Spec 109's** (`contracts/url-filter-contract.md` there). 108 keeps only the REST names `profile, client, token` (identity mapping) and their backend semantics, plus the `features.scope_filters` availability signal.

## D22 — Server edition

**Decision**: profile policy, enforcement, attribution, filters and profile CRUD apply to both editions (admin-only CRUD). `/clients` and client credentials are personal-only (the server edition has no local client config files to write). Administrator-created agent tokens (`POST /api/v1/tokens`, registered in both editions) can carry a profile in this spec; server-edition **per-user** tokens cannot yet — `profile` on `POST /api/v1/user/tokens` is a follow-up, listed in tasks.md Follow-ups (spec.md Editions and Edge Cases say so since codex round 3).

## D23 — Prompts and resources

**Decision**: no tier policy (they have no tier annotation); Spec 105 server-scope filtering continues. A profile deny rule does not apply to prompts. Documented, not a gap.

## D25 — Review round 2 clarifications

- **`profile_source` of a locked client credential** is `pin` (FR-020 tier 1 covers every locked client credential and every pinned regular token); `binding` is reserved for switchable client credentials. Special-casing client credentials to `binding` was rejected: it would make a locked client credential and a locked legacy token report different sources for identical semantics, and the client is already identified by `client_id` on every record.
- **Legacy = no policy field.** `IsLegacy()` ignores `title`/`description`; `hidden_by_profile` and `profile` appear in `retrieve_tools` for every non-legacy profile (value possibly `0`) and never for a legacy one — presence depends on configuration, never on the query, so it cannot become an oracle.
- **Binding a client without a client credential** returns `409 no_client_credential` on every surface and never mints one implicitly (FR-025's explicit, previewed upgrade stays the only path); the UIs replace the picker with "Upgrade to client credential"/"Reconnect".
- **Clients and Tokens filters are server-side** (`GET /clients?profile=&client=`, `GET /tokens?profile=&token=`) and mean current binding/pin; CLI `client list --profile`, `token list --profile`, MCP `list_clients {profile}` mirror them.
- **FR-009 is pinned by a test** (T004 field-set assertion under both build tags).

## D26 — Review round 4 clarifications

- **`POST /api/v1/code/exec` is a dispatch path** (verified: `internal/httpapi/server.go` mounts it in the agent-token-reachable group; `code_exec.go` calls `CallToolDirect("code_execution")`; `classifyCodeExecError` only knows Spec 097 typed errors). The profile-hidden `code_execution` error is typed; its text stays the `unknown tool: code_execution` formatter output on MCP and `/tools/call`, and `/code/exec` maps it to `403 PROFILE_BLOCKED` naming the caller's own profile. Answering `/code/exec` with an unknown-tool error was rejected: the route exists only to run code, so non-disclosure buys nothing and the caller loses its remediation. The profile answer precedes the global `FEATURE_DISABLED` (refusal precedence: profile steps before `global_gate`).
- **`POST /api/v1/tool-calls/{id}/replay` is a dispatch path too** (found while verifying the above: `Server.ReplayToolCall` → `runtime.ReplayToolCall` calls the upstream client directly, so neither mcp-go filters nor the shared handlers see it). It runs the FR-010 decision for the recorded `(server, tool)` itself before dispatch.
- **View-as authorization**: `client=` on `GET /tools` and `effective-tools` is administrator-only, like `/access/explain` (another client's verdicts disclose its binding); `profile=` follows `GET /profiles/{name}` reachability. The caller's own `AllowedServers` removes rows first and is never a `reason`, so `server_in_scope` as a view-as reason means the **subject** credential's token servers.
- **`reason` enum is total**: canonical chain order; the `server_in_scope`/`tool_rule`/`tier_cap` steps report the FR-010 reasons, every other failure reports its step name (`credential`, `profile`, `server_in_scope`, `token_permission`, `global_gate`, `server_state`, `tool_approval`).
- **`set_profile("")`** keeps today's always-accepted semantics for every caller and falls through to the base; it is a column of the enforcement matrix.
