# Contract: REST API (Profiles v3)

Base `/api/v1`, standard `{success, data, error}` envelope, `X-API-Key` (or socket). **Client credentials (`kind=client`) are rejected on every route below with `403 {"error":"client credentials are valid on MCP endpoints only"}`** (FR-023). "Admin" = passes `requireServerOp(auth.ServerOpConfigWrite)`. First-party surfaces send `X-MCPProxy-Surface: web|macos|cli` so `profile_change` records carry the surface (absent → `api`). `oas/swagger.yaml` is regenerated in the PR that adds each route.

`ProfileConfig` fields: see data-model §1. `ProfileView` adds `effective_servers, tool_counts{read,write,destructive,unannotated_hidden}, used_by{clients:[{id,mode}], tokens:[name], anonymous_profile: bool}, calls_24h, blocked_24h, is_legacy` (`is_legacy` per data-model §1: none of the six policy fields set; `title`/`description` ignored). **`used_by` is administrator-only** (zcode review): it names which clients (and in which mode) and which tokens are bound to the profile and whether it is the `anonymous_profile` — the same binding disclosure FR-032 withholds from non-admin callers on `GET /tools?client=` and `effective-tools?client=`. Every non-admin caller therefore gets `ProfileView` **without the `used_by` key** (omitted, never an empty object, which would read as "unused") on `GET /profiles` and `GET /profiles/{name}`; `calls_24h`/`blocked_24h` are computed over the caller's scope.

Every mutating route writes one `profile_change` record and emits `profiles.changed`. Every mutating profiles route (`POST`, `PUT`, `rename`, `DELETE`) runs the FR-008a `BindingGuardDelta` check over its candidate state before writing (contracts/refusals.md guarded-route list; T070a coverage test).

**108-f: exact bodies as shipped.** `POST /profiles` answers `201 {profile: ProfileView, warnings: string[]}` and `PUT /profiles/{name}` `200 {profile, warnings}` (warnings are the validator's findings about the written profile); `POST /profiles/{name}/rename` `200 {profile, moved: {clients[], tokens[]}}`; `DELETE` `200 {deleted, moved, anonymous_profile_moved_to?}` with `reassign_to` required to name ANOTHER existing profile (`400 {field: "reassign_to"}` otherwise; there is no "All servers" target, a locked client cannot hold an empty pin) and `force` leaving pins dangling. `active` and `try` are refused for a new profile or a rename target (`400 {error: "profile name \"active\" is reserved by the REST API", field: "name"}`, `new_name` for rename); the loader is unchanged. `409` bodies: `profile_in_use` `{error: "profile in use", code, used_by}`; `profile_is_anonymous_profile` `{error, code, used_by}`; `profile_exists` `{error: "profile \"x\" already exists", code}`; `name_mismatch` `{error: "name must equal the path; use POST /profiles/{name}/rename", code}` (accepted-by-spec convenience: a `PUT` body whose `name` is omitted or an empty string takes the path's name, so `name_mismatch` fires only for a different non-empty name). `400 {error, field}` uses `field` from `name, servers, title, description, max_tier, unannotated, tools.allow, tools.deny, tools.classify, code_execution, management_tools, switchable_to, anonymous_profile`. `GET /profiles/{name}/effective-tools` answers `{profile, tools, counts: {visible, hidden, callable?, by_reason?}, stale_classifications?}` (administrator extras); `client=` evaluates that client's credential UNDER this profile. `GET/PUT /profiles/active` also send `Link: </api/v1/profiles>; rel="successor-version"`. Every config-writing route (`PATCH /config`, `POST /config/apply`, `PATCH /config/docker-isolation`) writes its `profile_change` records from the diff (FR-030).

## Tokens (existing routes, extended)

`POST /tokens` accepts `profile` (sets `profile_pin` on a regular `kind=agent` token — pinned, no `profile_mode`; `allowed_servers` defaults `["*"]` and `permissions` defaults all three when `profile` is given and they are omitted). A name held by a revoked token → `409 {error: "A revoked token named \"x\" still holds this name for activity history; choose another name"}` (a live holder keeps `A token named \"x\" already exists`). Names starting with `client-` → `400 {error: "token names starting with \"client-\" are reserved for client credentials", field: "name"}` (checked before storage). `GET /tokens` rows add `kind, client_id, profile_mode, legacy_scope: bool` (true when `allowed_servers ≠ ["*"]` or `permissions` ≠ all). `GET /tokens?profile=&token=` (FR-031): `profile` = tokens whose **current** `profile_pin` is that profile (`-` = unpinned), `token` = exact name; server-side.

## Access explain

`GET /access/explain?tool=<server:tool>&client=<id>|token=<name>|profile=<name>|anonymous=true` (exactly one subject; admin) → `AccessExplanation` (data-model §7: `steps[]`, `verdict`, `first_failure`, top-level `fixes[]`; `fixes[].profile` is the destination profile slug of a `move_client` fix, omitted for every other action). `400` when the subject is missing/ambiguous; unknown tool → verdict `hidden` with step `server_state`/`tool_approval` failing as appropriate (admin callers get full detail). Error texts: `400 exactly one of client, token, profile, anonymous is required`; `400 use client=<id> for a client credential` (`token=client-<id>`); `400 access/explain covers upstream tools (server:tool) only` (a built-in tool name); `404 client not found` / `404 token not found` / `404 profile not found`; in the server edition `client=` is `404 client not found`.

## Filters on grids (FR-031)

Added to `GET /activity`, `/activity/summary`, `/activity/usage`, `/activity/export`, `/sessions`: `profile`, `client`, `token` (`agent` is an alias of `token`; naming two different tokens is a `400` `token and agent must name the same token (agent is an alias of token)`); `-` = unattributed. **Honoured sets (108-e)**: `/activity` and `/activity/export` — `profile`, `client`, `token`, `agent` (+ `client_name`); `/activity/summary`, `/activity/usage`, `/sessions` — `profile`, `client`, `token`; `GET /tools` — `profile`, `client`; `GET /servers` — `profile`; `GET /clients` honours `profile` and `client` and `GET /tokens` honours `profile` and `token` from 108-f (`GET /clients/{client}` honours none); a name an endpoint does not honour stays a `400 unsupported_scope_filter`. `/activity/usage` under a scope filter is a window-bounded scan of the matching records (per-tool metrics are window-bounded instead of lifetime; no tokens-saved headline; the filters are part of the cache key). `/sessions` `profile` is the latest effective profile. `GET /activity/export` CSV appends `profile, profile_source, client_id, client_name, token_name, block_reason` after `parent_id`. A scoped caller's filters see another token's attribution as empty and the four identity fields are blanked on rows it did not make. Exact `400` texts: `client_name is not supported on this endpoint; filter by client`; `use either client or profile, not both`; `'-' (unattributed) is only valid on activity and session filters` (`profile=-`/`client=-` on `/tools` or `/servers`); `404 profile not found` / `404 client not found`; `403 operation requires admin access` for `client=` by a non-admin. `client_name` (advisory) is accepted by exactly `GET /activity` and `GET /activity/export`; `GET /activity/summary`, `/activity/usage` and `/sessions` reject it with `400` (`client_name is not supported on this endpoint; filter by client`), never silently ignoring it. CLI `activity watch` has no REST endpoint of its own: it streams `/events` and applies `--profile/--client/--token/--client-name` client-side to the SSE activity payloads, which carry the FR-029 fields. `GET /clients` and `GET /tokens` take `profile` plus `client`/`token` respectively (current binding/pin, see their rows above). `GET /tools` accepts `profile`, `client` ("view as"; rows gain `access{visible,callable,reason}` computed by walking the canonical chain `credential → profile → server_in_scope → tool_rule → tier_cap → token_permission → global_gate → server_state → tool_approval`, `reason` = first failing step with the FR-010 reasons reported by the `server_in_scope`/`tool_rule`/`tier_cap` steps — data-model §7 EffectiveTool enum, FR-032). **Authorization**: `client=` is admin only, like `GET /access/explain` (non-admin → the `requireServerOp` `403`, since another client's verdicts disclose its binding); `profile=` is accepted from any non-client caller for a profile it can read (`GET /profiles/{name}` reachability, uniform `404` otherwise); the caller's own `AllowedServers` filter removes rows before verdicts are computed, so the caller's scope never appears as a `reason`. `GET /servers` accepts `profile` (restricted to the profile's effective servers ∩ the caller's visible servers; each row's `tool_count` is the number of that server's tools visible under the profile and `stats` are recomputed over the returned rows). `token` is an activity/session filter only. Authorization filtering (Spec 105 `AllowedServers`) runs first. Non-admin `GET /tools?profile=`: visible rows only plus `counts{visible, hidden}` (FR-032). A disabled server contributes no rows to `GET /tools` with or without view-as (it is disconnected and has no tool set); `/access/explain` reports its tools as `server_state` (108-j, #1437 item 2). **Availability**: `GET /api/v1/status` gains `features.scope_filters: ["profile","client","token"]` in 108-e; Spec 109's `useScopeQuery()`/`ScopeFilter` un-hide these parameters when it is present (FR-031). **Before 108-e** (version skew, FR-031): a build that does not list a parameter in `features.scope_filters` rejects it on every endpoint of this section with `400 {"error":"scope filter '<param>' is not supported by this server","code":"unsupported_scope_filter","param":"<param>"}` — Spec 109-k's gate in `internal/httpapi/scope_filters.go`, reading the same list the status field reports — instead of silently returning unfiltered rows; `agent` is not gated on `GET /activity` and `/activity/export` (they honour it today) and is gated as `token` on `/activity/summary`, `/activity/usage` and `/sessions` (they ignore it today). 108-e fills the list and the rejection disappears for those names in the same change; a name a handler does not honour stays rejected (`GET /tools?token=…`, `GET /servers?client=…`). 109-k merged first and created the list variable and the gate function together (codex round 4); 108-e filled the list. Each handler also passes the names it honours: `GET /clients` (109-h route) and `GET /tokens` honour theirs from 108-f (T076a); the gate has no separate per-endpoint table, the `honoured` argument each handler passes IS the per-endpoint advertisement. The URL names, page wiring and link map are Spec 109's (url-filter-contract.md here is a pointer).

## Existing dispatch routes: `POST /tools/call`, `POST /code/exec`, `POST /tool-calls/{id}/replay` (FR-014, FR-015)

No shape change on any of them. **`POST /tools/call`**: The route dispatches built-in tools by name through `CallToolDirect`, bypassing mcp-go tool filters, so every profile gate is enforced inside the shared handlers ([mcp-tools.md](mcp-tools.md) "REST `POST /api/v1/tools/call`"): a pinned `kind=agent` token gets the same outcome as on MCP — profile refusal → `403` with the refusals.md text; hidden `code_execution`/management tool → the existing unknown-tool error (same status and body shape as a nonexistent `tool_name`, differing only in the echoed name and per-request identifiers — the error text embeds the requested name, so byte-identity to a different name is impossible). It is a column of the enforcement matrix.

**`POST /code/exec`** (CLI client mode; → `CallToolDirect("code_execution")`): the profile refusal arrives as a typed error that `classifyCodeExecError` maps with `errors.As` (Spec 097 pattern) — code execution hidden by the caller's effective profile → `403` in the route's existing `CodeExecResponse` error shape `{ok:false, error:{code:"PROFILE_BLOCKED", message:"blocked by profile: code execution is disabled for this profile"}, request_id}` plus a `status=blocked`, `block_reason=profile_code_execution` record; never the `500 EXECUTION_FAILED` fall-through. The profile answer precedes the existing global `403 FEATURE_DISABLED` when both apply (refusal precedence). Nested `call_tool` refusals inside a script started here behave exactly as on MCP (FR-013 text returned to the script, child record with `parent_id`). Administrator API keys (no profile) are unchanged.
