# Contract: REST API (Profiles v3)

Base `/api/v1`, standard `{success, data, error}` envelope, `X-API-Key` (or socket). **Client credentials (`kind=client`) are rejected on every route below with `403 {"error":"client credentials are valid on MCP endpoints only"}`** (FR-023). "Admin" = passes `requireServerOp(auth.ServerOpConfigWrite)`. First-party surfaces send `X-MCPProxy-Surface: web|macos|cli` so `profile_change` records carry the surface (absent → `api`). `oas/swagger.yaml` is regenerated in the PR that adds each route.

The check runs with and without `reassign_to`/`force` (a `force` delete dangles pins → deny-all, never bypassable, but still removes the name from `switchable_to` lists) |

| `PATCH /config` `{anonymous_profile}` | admin | existing route; when the body contains `anonymous_profile` that field is applied through `profiles_service.SetAnonymous` (same validator; writes `profile_change` `change=anonymous`, emits `profiles.changed`, notifies anonymous sessions — FR-027/FR-030) | existing | existing (`400` from the one validator — incl. the FR-009a rejection of a non-empty `anonymous_profile` before 108-d); `409 binding_bypassable_without_auth` (FR-008a; pre-apply check from **108-c**, T040) |
| `POST /config/apply` | admin | existing route (writes a whole config document, `handleApplyConfig`). Before applying, the candidate config runs the same FR-008a check as `PATCH /config` (it can turn `require_mcp_auth` off, clear or widen `anonymous_profile`, or narrow/widen profiles); after applying, the profiles service diffs the old and new snapshot and writes one `profile_change` per changed item — `change=anonymous` when `anonymous_profile` changed, `create`/`update`/`delete` per profile (surface from `X-MCPProxy-Surface`) — and emits `profiles.changed` (FR-030). Deleting a pinned or bound profile through apply leaves the pin dangling (deny-all, never wider), exactly as a hand edit. The FR-008a pre-apply check lands in **108-c** (T040), the snapshot-diff records in 108-f (T074) | existing | existing; `409 binding_bypassable_without_auth` — nothing applied |

`ProfileConfig` fields: see data-model §1. `ProfileView` adds `effective_servers, tool_counts{read,write,destructive,unannotated_hidden}, used_by{clients:[{id,mode}], tokens:[name], anonymous_profile: bool}, calls_24h, blocked_24h, is_legacy` (`is_legacy` per data-model §1: none of the six policy fields set; `title`/`description` ignored). **`used_by` is administrator-only** (zcode review): it names which clients (and in which mode) and which tokens are bound to the profile and whether it is the `anonymous_profile` — the same binding disclosure FR-032 withholds from non-admin callers on `GET /tools?client=` and `effective-tools?client=`. Every non-admin caller therefore gets `ProfileView` **without the `used_by` key** (omitted, never an empty object, which would read as "unused") on `GET /profiles` and `GET /profiles/{name}`; `calls_24h`/`blocked_24h` are computed over the caller's scope.

Every mutating route writes one `profile_change` record and emits `profiles.changed`. Every mutating profiles route (`POST`, `PUT`, `rename`, `DELETE`) runs the FR-008a `BindingGuardDelta` check over its candidate state before writing (contracts/refusals.md guarded-route list; T070a coverage test).

## Clients (personal edition only; server edition: routes not registered → 404)

`GET /clients` and `GET /clients/{id}` are **Spec 109-h's routes** (presence rows, administrator-only, Spec 109 contracts/rest-api.md). This spec decorates them additively (data-model §7 ClientView) and adds the filters and warnings below; every other route in this table is this spec's.

`POST /connect/{client}` (existing) gains body `{profile?: string, mode?: "locked"|"switchable", keyless?: bool}` (`mode` default `locked` when `profile` is non-empty, else `switchable`; `409 {error, conflicting_token}` on a `client-<id>` name held by a `kind=agent` token, FR-021; `409 binding_bypassable_without_auth` per FR-008a; over an active client credential it is a staged rotation, FR-021a); `GET /connect/{client}/preview` accepts the same as query params and returns `credential: "mcp_cli_••••"` (the masked client-credential prefix, FR-021; asserted literally by T031), `profile`, `mode`, `contains_api_key: false` always. `GET /connect` and `GET /connect/{client}` add `credential_state`.

**Connect reads become administrator-only (FR-025a, 108-c)**: `GET /connect`, `GET /connect/{client}` and `GET /connect/{client}/preview` are wrapped in `requireAdminRead` (chi middleware form, `requireAdminReadMiddleware`) in the same PR that adds `credential_state` — or earlier: Spec 109-h gates the same three reads with the same middleware and message when it adds the administrator-only `GET /clients` (Spec 109 FR-030a); no edge between 108-c and 109-h, the first to merge adds the gate and the second keeps it. Non-administrator callers (`!IsAdmin()`: agent tokens incl. pinned, server-edition non-admin session principals) → `403 {"error":"Admin credentials required to read client connection status"}`, no data; API key and tray socket unchanged. This matches Spec 109's `GET /clients` (administrator only) and closes the non-admin channel that would otherwise list which clients hold the admin key. `POST`/`DELETE` connect verbs keep their existing `requireServerOp(ServerOpConfigWrite)` gate. `oas/swagger.yaml` gains the `403` response on the three reads.

`Warning`: `{code, severity: warn|info, message, action?: {kind, target}}`, codes `anonymous_denied_by_binding_guard`, `client_holds_admin_key`, `client_credential_expiring`, `client_rotation_pending`, `profile_missing`, `client_token_name_conflict` (data-model §7). `binding_bypassable_without_auth` is an error code (`409`, FR-008a), also returned by `PATCH /config` and `POST /config/apply` when they would turn `require_mcp_auth` off or clear/widen `anonymous_profile` while a named binding exists, and by `PUT /profiles/{name}` when an edit would make an existing binding bypassable.

## Tokens (existing routes, extended)

`POST /tokens` accepts `profile` (sets `profile_pin` on a regular `kind=agent` token — pinned, no `profile_mode`; `allowed_servers` defaults `["*"]` and `permissions` defaults all three when `profile` is given and they are omitted). Names starting with `client-` → `400`. `GET /tokens` rows add `kind, client_id, profile_mode, legacy_scope: bool` (true when `allowed_servers ≠ ["*"]` or `permissions` ≠ all). `GET /tokens?profile=&token=` (FR-031): `profile` = tokens whose **current** `profile_pin` is that profile (`-` = unpinned), `token` = exact name; server-side.

## Access explain

`GET /access/explain?tool=<server:tool>&client=<id>|token=<name>|profile=<name>|anonymous=true` (exactly one subject; admin) → `AccessExplanation` (data-model §7: `steps[]`, `verdict`, `first_failure`, top-level `fixes[]`). `400` when the subject is missing/ambiguous; unknown tool → verdict `hidden` with step `server_state`/`tool_approval` failing as appropriate (admin callers get full detail).

## Filters on grids (FR-031)

Added to `GET /activity`, `/activity/summary`, `/activity/usage`, `/activity/export`, `/sessions`: `profile`, `client`, `token` (`agent` alias kept); `-` = unattributed. `client_name` (advisory) is accepted by exactly `GET /activity` and `GET /activity/export`; `GET /activity/summary`, `/activity/usage` and `/sessions` reject it with `400` (`client_name is not supported on this endpoint; filter by client`), never silently ignoring it. CLI `activity watch` has no REST endpoint of its own: it streams `/events` and applies `--profile/--client/--token/--client-name` client-side to the SSE activity payloads, which carry the FR-029 fields. `GET /clients` and `GET /tokens` take `profile` plus `client`/`token` respectively (current binding/pin, see their rows above). `GET /tools` accepts `profile`, `client` ("view as"; rows gain `access{visible,callable,reason}` computed by walking the canonical chain `credential → profile → server_in_scope → tool_rule → tier_cap → token_permission → global_gate → server_state → tool_approval`, `reason` = first failing step with the FR-010 reasons reported by the `server_in_scope`/`tool_rule`/`tier_cap` steps — data-model §7 EffectiveTool enum, FR-032). **Authorization**: `client=` is admin only, like `GET /access/explain` (non-admin → the `requireServerOp` `403`, since another client's verdicts disclose its binding); `profile=` is accepted from any non-client caller for a profile it can read (`GET /profiles/{name}` reachability, uniform `404` otherwise); the caller's own `AllowedServers` filter removes rows before verdicts are computed, so the caller's scope never appears as a `reason`. `GET /servers` accepts `profile` (restricted to the profile's effective servers with in-scope tool counts). `token` is an activity/session filter only. Authorization filtering (Spec 105 `AllowedServers`) runs first. Non-admin `GET /tools?profile=`: visible rows only plus `counts{visible, hidden}` (FR-032). **Availability**: `GET /api/v1/status` gains `features.scope_filters: ["profile","client","token"]` in 108-e; Spec 109's `useScopeQuery()`/`ScopeFilter` un-hide these parameters when it is present (FR-031). **Before 108-e** (version skew, FR-031): a build that does not list a parameter in `features.scope_filters` rejects it on every endpoint of this section with `400 {"error":"scope filter '<param>' is not supported by this server","code":"unsupported_scope_filter","param":"<param>"}` — Spec 109-k's gate in `internal/httpapi/scope_filters.go`, reading the same list the status field reports — instead of silently returning unfiltered rows; `agent` is not gated on `GET /activity` and `/activity/export` (they honour it today) and is gated as `token` on `/activity/summary`, `/activity/usage` and `/sessions` (they ignore it today). 108-e fills the list and the rejection disappears for those names in the same change; a name a handler does not honour stays rejected (`GET /tools?token=…`, `GET /servers?client=…`). Whichever of 108-e / 109-k merges first creates the list variable **and** the gate function together (codex round 4). Each handler also passes the names it honours: `GET /clients` (109-h route) and `GET /tokens` honour them from 108-f (T074), so between 108-e and 108-f those two keep the `400`. The URL names, page wiring and link map are Spec 109's (url-filter-contract.md here is a pointer).

## Existing dispatch routes: `POST /tools/call`, `POST /code/exec`, `POST /tool-calls/{id}/replay` (FR-014, FR-015)

No shape change on any of them. **`POST /tools/call`**: The route dispatches built-in tools by name through `CallToolDirect`, bypassing mcp-go tool filters, so every profile gate is enforced inside the shared handlers ([mcp-tools.md](mcp-tools.md) "REST `POST /api/v1/tools/call`"): a pinned `kind=agent` token gets the same outcome as on MCP — profile refusal → `403` with the refusals.md text; hidden `code_execution`/management tool → the existing unknown-tool error (same status and body shape as a nonexistent `tool_name`, differing only in the echoed name and per-request identifiers — the error text embeds the requested name, so byte-identity to a different name is impossible). It is a column of the enforcement matrix.

**`POST /code/exec`** (CLI client mode; → `CallToolDirect("code_execution")`): the profile refusal arrives as a typed error that `classifyCodeExecError` maps with `errors.As` (Spec 097 pattern) — code execution hidden by the caller's effective profile → `403` in the route's existing `CodeExecResponse` error shape `{ok:false, error:{code:"PROFILE_BLOCKED", message:"blocked by profile: code execution is disabled for this profile"}, request_id}` plus a `status=blocked`, `block_reason=profile_code_execution` record; never the `500 EXECUTION_FAILED` fall-through. The profile answer precedes the existing global `403 FEATURE_DISABLED` when both apply (refusal precedence). Nested `call_tool` refusals inside a script started here behave exactly as on MCP (FR-013 text returned to the script, child record with `parent_id`). Administrator API keys (no profile) are unchanged.

**`POST /tool-calls/{id}/replay`** (→ `runtime.ReplayToolCall`, a direct upstream call that passes through no built-in handler): for a caller with an effective profile (a pinned `kind=agent` token) the FR-010 decision for the recorded `(server, tool)` under current annotations runs before dispatch. The existing out-of-scope/unknown-id `404` is unchanged and evaluated first, and a `server_not_in_profile` exclusion **returns that same `404`** (byte-identical after substituting the echoed id; zero upstream calls) — a descriptive answer would confirm that a record exists on a server outside the caller's profile. Only `denied_by_rule`, `unannotated_hidden` and `above_tier_cap` (a server inside the caller's scope) → `403` with the refusals.md text, `status=blocked` record with the FR-013 `block_reason`, zero upstream calls (FR-015).

## Existing discovery routes for a pinned token (FR-015a, 108-d)

No shape change. For a caller whose resolution carries a profile (a pinned `kind=agent` token; administrators and unpinned tokens unchanged): `GET /index/search` searches through `SearchToolsAdmitted` with the `retrieve_tools` predicate (filter before limit; excluded tools absent; no `hidden_by_profile` field is added to the REST response); `GET /tools` (no `profile`/`client` view-as parameter), `GET /servers/{id}/tools` and `GET /servers/{id}/tools/export` omit excluded rows — the visible-row set of the non-admin `GET /tools?profile=<own pin>` view (FR-032) without `counts`; `GET /servers/{id}/tools/{tool}/diff` answers an excluded tool with the route's existing unknown-tool `404`. A server outside the pin's `servers` behaves like one outside `allowed_servers` (absent; the `/servers/{id}/*` subtree's existing scoped `404`). Server-level reads (`GET /servers`, status, logs, diagnostics) keep Spec 105 token scoping only. Test: T046c.
