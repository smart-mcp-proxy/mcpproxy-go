# Contract: refusals and block reasons

Texts are exact (tests compare byte-for-byte after substituting `<server>`, `<tool>`, `<tier>`, `<cap>`, `<label>`). All are returned before any upstream I/O. **A refusal names the profile only to a caller whose effective profile is its own** (research D39, which narrows D27): source `pin` or `binding` (its own credential) or `url` or `session` (its own choice). It never names it for source `anonymous` (the operator's `anonymous_profile` would be handed to any local process that connects), for a dangling base or for an out-of-scope server; those keep the original non-disclosing text and shapes (the Spec 105 `set_profile` precedent, `internal/server/profile_tool.go`). `<label>` is `"<title>" (<slug>)` with the title rendered by Go `%q`, or `"<slug>"` when the title is empty or equals the slug. The exact texts are pinned by `internal/profile/testdata/contract/tool_refusals.json`. The operator sees the profile on the activity record, in the explainer and in view-as.

Precedence when several gates fail is exactly the explainer chain (data-model §7, FR-035): `credential → profile → server_in_scope → tool_rule → tier_cap → token_permission → global_gate → server_state → tool_approval`. `credential` fails only for revoked/expired/malformed credentials. `profile` fails only for a dangling base — a pin, switchable binding or `anonymous_profile` naming a missing profile (FR-020) — and for the FR-008a binding guard: the **canonical step and reason is `profile`** in the explainer (`first_failure: profile`), in view-as (`reason: profile`) and on the activity record (`block_reason` unset, `status=blocked` with the Spec 105 out-of-scope metadata); the agent-facing **shape** is the Spec 105 non-disclosing out-of-scope refusal, because a deny-all scope makes every server out of scope — the shape is not a second step value; `server_in_scope` uses the Spec 105 non-disclosing shape; `tool_rule`/`tier_cap` use the texts above; `token_permission` is the Spec 105 target-tier refusal; `global_gate` covers `read_only_mode`/`disable_management`/`enable_code_execution`. `upstream_servers` mutating operations check `global_gate` (`read_only_mode`, `disable_management`) before `token_permission` (`AuthorizeServerOp`) on main; 108-f's explainer must model that order or reorder it (follow-up). The explainer's `first_failure` follows this order, so it and the actual refusal agree (SC-009).

**108-f: the guarded and exempt route lists (T070a).** Guarded (driven by a fixture that must answer the `409` and write nothing): `POST /profiles`, `PUT /profiles/{name}`, `POST /profiles/{name}/rename`, `DELETE /profiles/{name}`, `POST /clients`, `PUT /clients/{client}/binding`, `POST /clients/bulk-assign` (per-client refusals are reported in `skipped[]` with the same code), `POST /clients/upgrade-admin-key-holders`, `POST /connect/{client}`, `PATCH /config`, `POST /config/apply`, `PATCH /config/docker-isolation`. Exempt, each with its reason (it cannot change a binding's reach): `POST /clients/{client}/rotate`, `POST /clients/{client}/rotate/finalize`, `DELETE /clients/{client}`, `DELETE /connect/{client}`, `POST /connect/{client}/undo`, `POST /profiles/try`, `PUT /profiles/active`, `POST /config/validate`. The access explainer covers upstream `server:tool` only; built-in management operations are not explained (F23). New `409` codes: `profile_in_use`, `profile_is_anonymous_profile`, `profile_exists`, `name_mismatch`, `precondition_failed`.
