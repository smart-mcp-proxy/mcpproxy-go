# Contract: scope filters and deep links — pointer (owned by Spec 109)

**This spec does not define the URL filter contract.** Under the cross-spec ownership rule (spec.md "Ownership split with Spec 109", research D27), the composable `useScopeQuery()` (`frontend/src/composables/useScopeQuery.ts`), the full parameter table — including `profile`, `client` and `token` — the Web UI behaviour rules, the deep-link map and the macOS `ScopeFilter` are owned by **Spec 109**: `specs/109-ux-navigation-consistency/contracts/url-filter-contract.md` (branch `109-ux-navigation-consistency`, PR 109-k). An earlier revision of this file restated that contract with a diverging parameter set, `status` vocabulary, Sessions behaviour and link map (codex review round 1); it was removed so there is exactly one definition.

## What this spec provides to that contract

| Item | Owner here | Consumed by (Spec 109) |
|---|---|---|
| Backend meaning of `profile`, `client`, `token` (and `agent` alias, `client_name` advisory) on `GET /activity`, `/activity/summary`, `/activity/usage`, `/activity/export`, `/sessions`, `/tools`, `/servers`, `/clients`, `/tokens` — recorded-at-call-time vs current-binding semantics, the `-` = unattributed sentinel, `400` for unsupported `client_name` | FR-031, [rest-api.md](rest-api.md) "Filters on grids" | the `profile`/`client`/`token` rows of 109's parameter table (their REST mapping is identity) |
| Availability signal `features.scope_filters: ["profile","client","token"]` on `GET /api/v1/status`, added by 108-e | FR-031 | 109's `useScopeQuery()` and macOS `ScopeFilter` carry these parameters from 109-k but keep them hidden (no chip, no control, not sent to REST, never dropped from the URL) until the signal lists them; the backend gate (`internal/httpapi/scope_filters.go`, owned by 109-k) rejects a `profile`/`client`/`token` that is unlisted **or** not honoured by that handler with `400 unsupported_scope_filter`, reading the one list 108-e fills (version skew, FR-031). The list variable and the gate function are created together by whichever of 108-e / 109-k merges first (108-e T064), so 108-e never ships a handler that parses scope parameters without the gate — e.g. `GET /tools?token=ci-bot` is a `400`, not an unfiltered `200`. `agent` is ungated only on `GET /activity` and `/activity/export`, the two handlers that honour it today; elsewhere it is gated as `token` |
| Target pages of the 108 link-map rows: Profiles page and editor (`/profiles`, `/profiles/:name?focus=<server:tool>`), view-as rows on Tools, the access explainer modal, the Clients-row profile chip | FR-040–046 | 109's link map rows "client row → Activity · Sessions · Tools it sees · Usage", "profile card → Tools · Activity · Clients · Tokens", "Activity row chips", "blocked row → Allow in profile… / Why?", "Tools view-as row → Why?", "Token row → Activity · Usage" — wired in 109-k, shown when the signal and the target route exist |
| CLI flags `--profile`, `--client`, `--token` (`--agent` alias), `--client-name` | FR-036, [cli.md](cli.md) | 109's CLI column (names are identical) |
| *(not this spec's)* CLI `--from`/`--to` aliases on `activity list`, `watch`, `summary`, `export` | — | owned and registered by 109-k on exactly those four commands (its FR-075, T121); 108-e T065 does not register them, and a parity test written from this table covers `watch` too |

## Test obligations here

- `internal/httpapi/activity_scope_params_test.go` (T058) and the view-as tests (T059) pin the backend semantics.
- The 108-l parity test (T121) asserts that every `profile`/`client`/`token` row in **Spec 109's** parameter table maps to an FR-031 REST parameter and a CLI flag of this spec, and that `features.scope_filters` is present — it reads Spec 109's contract, never a copy.
