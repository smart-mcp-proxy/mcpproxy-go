# Research: Navigation, scope filters and cross-surface UX consistency — decisions

Every open question from the audit, the four surface inventories and the overlap with Spec 108 is settled here. Where a choice was open, the rule was: **fail closed for security, stay backward compatible for URLs, config and CLI output, add no dependencies, and prefer one shared implementation over per-surface logic**. Each choice is recorded. Code references are to `origin/main` at `638fa805a`.

## D1 — Ownership split with Spec 108

**Decision** (revised in D25 by the maintainer's ownership rule): the table in spec.md "Coordination with Spec 108" is binding. Every shared artifact has exactly **one owner**; the "first to merge creates, the other extends" rule is withdrawn. Spec 109 owns the URL filter contract and `useScopeQuery` with every parameter (incl. `profile`, `client`, `token`, hidden until `features.scope_filters`), the link map, the macOS `ScopeFilter`, the Clients page shell and `GET /clients` presence, `ClientConnectList`/`ImportServers`, sidebar/header layout, Needs-attention, health vocabulary, review queue and catalog. The owner's PR leaves these extension points for Spec 108's components:
- `Clients.vue`: a row slot and a column slot for 108's profile chip, and a banner slot for `warnings[]`.
- `GET /api/v1/clients`: rows are a struct that 108 extends with `omitempty` fields.
- `useScopeQuery`: `profile`, `client`, `token` pre-registered by 109-k with `requires: "scope_filters"` (hidden until the status feature list names them); `registerScopeParam` is the owner's internal API, not an extension point for 108.
- The header: an empty `<slot name="viewing">`.

Spec 108 D16 placed Profiles and Clients in the "Workspace" group "until M7 regroups later". 109-i is that regrouping, so both entries end up in **Connect**.
**Amendments applied to Spec 108** (its codex round 1 commit, 108 research D27): T098 mounts controls in 109's `Clients.vue` (108-i ← 109-h); T040 no longer creates `GET /clients` (108-f decorates 109's rows, 108-f ← 109-h); the former 108-j `useScopeQuery`/link-map tasks are merged into 109-k and 108-j is re-scoped to profile-specific UI (108-j ← 109-k); T102 makes no sidebar edit (109-i owns the Profiles entry); 108-i ← 109-i for the header slot; 108's `--from/--to` CLI aliases are delivered by 109-k (inside Spec 109, the parallel pair 109-b/109-c uses the same rule for `has_usable_server`: the second to merge applies the `health.usable` definition); T042 and T098 retarget their `ConnectModal.vue` changes to `ClientConnectList.vue` if 109-h merged first (and 109-h carries over any 108 connect fields already in `ConnectModal.vue` otherwise). 108-a's `profile.IntrinsicTier` calls `contracts.AnnotationTier` (added by 109-a) instead of re-implementing the mapping, and adds its effective-annotations seam and unresolved-identity → destructive rule around it; because that is a compile-time dependency, Spec 108 declares the edge **108-a ← 109-a** and an exhaustive `contracts.Tier` (string) → `profile.Tier` (int) adapter pinned by a joint test (its T005a, D28 here).
**Why**: two specs creating the same component in parallel worktrees guarantees a conflict and invites two designs. Splitting by concern (presence and navigation vs binding and scope) lets both proceed and ship independently.
**Rejected**: making 109 wait for 108 (it delays every quick win for weeks); duplicating a Clients page in 109 and deleting it in 108 (wasted work, and a flip-flop for users).

## D2 — One attention function, served, never recomputed per surface

**Decision**: `internal/runtime/attention.go` exposes a pure `Compute(in AttentionInput) []AttentionItem` over the state snapshot (servers with `health`, per-server pending/changed counts, connect status, sessions-seen-per-client, connect write times). A runtime subscriber recomputes it on `servers.changed`, tool-approval, connect and session events (debounced 250 ms) **and on a threshold timer** (codex round 1): after every recompute it arms one timer for the earliest time at which a time-based condition would flip (`StateSince + 60 s` for `connecting`/`error`, `ConnectedAt + 5 min` for `client_never_seen`), capped at 30 s, so an item appears at its threshold on a quiet instance where no event would otherwise trigger a recompute. It caches the result. `GET /api/v1/attention` serves the cache. SSE `attention.changed` fires only when the (kind, subject) set changes. Rank order: `sign_in_required`, `missing_secret`, `config_error`, `server_error`, `server_review`, `tool_review` (changed before pending), `client_never_seen`. Ties go by subject name.
**Why**: X1 shows three predicates drifting. Serving one computed list makes the count identical by construction, and the pure function is table-testable. Constitution: event-driven, no polling. II: the result is published as an immutable snapshot, with no new mutexes on the hot path.
**Rejected**: having each surface filter `/servers` itself (that is the drift we are removing); putting attention in `/status` (it would bloat a hot endpoint and mix concerns).

## D3 — Home replaces the Usage-first landing (#1044), without losing it

**Decision**: `/` = Home: the Needs-attention list first, then the Overview topology with its actions (Connect client, Add server, Browse catalog), then a usage summary strip (calls today, blocked, errors, tokens saved or estimated). When the list is empty the strip moves above the topology. `/usage` becomes its own Monitor page. `/overview` redirects to `/`. 109-a ships only the default flip (`/` → Overview panel) as an interim quick win.
**Why**: #1044 made Usage the landing page and #1049 added "what needs me" banners above it. The rev-2 audit (N8) found that new users still land on empty charts. The strip keeps analytics one glance away for returning users, and an empty attention list pushes it up, so returning users with nothing to fix see usage first.
**Rejected**: keeping the tabbed Dashboard (it is the problem N8 names); conditional landing by user type (#1044 rejected that too, for its unpredictability).

## D4 — Health: add `status`, `usable`, `actions[]`; keep `level`

**Decision**: the calculator computes `status` from the same branch it already takes: disabled → `disabled`; quarantined → `needs_review`, or `sign_in_required` when OAuth login is also required; missing secret → `needs_secret`; config/URL error → `needs_config`; OAuth required → `sign_in_required`; connecting → `connecting`; error → `error`; connected → `ready`. It sets `usable = status == ready`. `actions` lists every applicable action in the FR-012 order, and `action == actions[0]` stays true. `level` is unchanged: disabled and quarantined servers keep `healthy`, except the existing transport-fault override, where a quarantined server with `state=error` already reports `unhealthy` (`calculator.go:151-155`).
**Why**: `level` is consumed as a breakage severity. It drives the tray badge tint (`Models.swift` `isBadgeExempt`, whose documented invariant says a quarantined or sign-in-required server must not tint red), the Dashboard filter, and JSON consumers. Flipping it would retint badges and break Spec 044 invariants. The audit's goal is that the user never reads "healthy" for an unusable server, and FR-011 guarantees that by rendering only `status`.
**Rejected**: changing quarantined → `degraded` (it retints the tray and changes online counts, and it is still ambiguous); a second calculator on the frontend (drift).

## D5 — Captured annotations and tier on review

**Decision**: `ToolApprovalRecord` gains `current_annotations` and `previous_annotations` (JSON, `omitempty`), written wherever `current_description`/`current_schema` are written (`checkToolApprovals`). The approval hash is unchanged. The tier comes from `contracts.AnnotationTier` (added in 109-a, FR-028): `destructiveHint` → destructive, `readOnlyHint=false` → write, `readOnlyHint=true` → read, neither → `unannotated`. On review payloads, a record without stored annotations (captured before this spec) → `unknown`. Spec 108's `IntrinsicTier` wraps the same function (D1), so review, Tools, CLI and profile enforcement can never disagree about a tool's tier.
**Why**: the audit mockup shows "3 write · 2 destructive · 9 read" before approval. Showing unannotated as `read` would repeat P3's trap in the reviewer's head.
**Rejected**: fetching annotations live from the quarantined server at review time (the supervisor refuses to dial quarantined servers except under the scanner's inspection exemption; "Fetch tool definitions" uses exactly that path, on demand).

## D6 — Observation: annotation changes are not reviewed (follow-up, not in scope)

Annotations are excluded from the approval hash (`tool_quarantine.go:26`), so an upstream can flip `readOnlyHint` from false to true without re-review. Spec 108's tier cap relies on annotations. This spec only *displays* annotation diffs on changed tools (`previous_annotations`). Making an annotation change a review trigger (at least a false→true `readOnlyHint` or a removed `destructiveHint`) is a security-model change for its own spec, and is recorded as a follow-up in tasks.md.

## D7 — One set of review verbs; MCP cannot approve servers

**Decision**: Approve server = `security/approve` (scan-gated, `force` only after the dangerous-verdict dialog, integrity baseline). It is extended with an optional `block: [tool…]` body so the review screen's unchecked tools are blocked atomically **before** the unquarantine (codex round 1): the block records are written in the same storage transaction as the integrity baseline, so the unquarantine step never makes a `block` tool callable, even for an instant; a concurrent-call race test pins it. Reject server = `security/reject`. Approve tool = `tools/approve`. Reject tool = `tools/block` (acknowledge + disable, matching MCP `block_tool`). The macOS app switches from `approveTools` + `unquarantine` to `security/approve` in 109-f, ahead of the UI work, because the current path bypasses the Spec 077 gate. `POST /unquarantine` remains for API compatibility and has no first-party caller (SC-005 grep test). MCP keeps `approve_tool`/`block_tool` and gains no server approval.
**Why**: X2 is a security-relevant divergence, and the fix is a one-line client change plus the confirmation dialog. Reject = block rather than delete, because deleting loses the evidence and the diff.
**Rejected**: making `/unquarantine` scan-gated (it would change a documented API and break automation that relies on it after its own review); adding a server-approve op to MCP (constitution IV).

## D8 — Clients presence without credentials

**Decision**: presence joins three existing sources: the connect registry and status (installed, connected, `config_path`); the SessionStore (`client_name` per session, active sessions, last activity); and activity counts (tool calls in 24 h per client, from a per-client rolling counter added to the in-memory usage aggregate — D28; the aggregate had no client dimension). The join key is an explicit `ClientDef.ClientInfoNames` alias list (for example `claude-code` for Claude Code; the exact list is verified per client in 109-h against a live handshake and recorded in `clients.go`). An unmatched name becomes an `other` row. `connected_never_seen` = connected and no session seen since the connect write; a session seen before MCPProxy last disconnected the client (`client_disconnected_at`, D28) is not evidence of a current connection. "Seen ever" uses the onboarding store's `mcp_clients_seen_ever` (unchanged) plus a new parallel `client_last_seen` map for timestamps.
**Why**: gives Clients a useful page before Spec 108's credentials exist, without guessing. 108 later swaps the join key for the authoritative `client_id`.
**Rejected**: fuzzy matching of client names (it misattributes); waiting for 108 (D1).

## D9 — Sessions become an Activity view

**Decision**: `/activity?view=sessions` renders today's Sessions table, and `/sessions` redirects there, keeping the query. The Sessions sidebar item is removed in 109-i. Each Clients row shows "N active sessions · last seen" with an inline expander listing the sessions, each linking to `/activity?session=<id>`. macOS: an Activity segmented control (Tool calls · Sessions · System events · All). DashboardSessions stays on Home.
**Why**: N5 says an empty standalone page is confusing, while sessions are useful next to calls and clients. Keeping the URL working preserves Spec 108 acceptance check 6.
**Rejected**: deleting the table (sessions carry capabilities and token counts, which nothing else shows).

## D10 — Scope contract ownership and names

**Decision**: the Web URL uses short names; REST keeps its names; `useScopeQuery` maps between them (same as 108 D21). This spec registers `server`, `tool`, `session`, `status`, `from`, `to`, `view`, `tab`, `q` and page-local parameters. Sticky = `from`, `to`, `profile`, `client`, `token` — the last three registered here too, hidden until Spec 108-e's `features.scope_filters` (D25). `status` is page-defined: call outcome on Activity/Usage (`success|error|blocked|rejected`, plus the Web-only client-side `other` residual on Activity), tool state on Tools (`enabled|disabled|config-denied`, the spelling of `tools list --status`), health status on Servers (mirroring `upstream list --status`). It is never sticky, so the meanings never cross pages. The Tools value is spelled `config-denied` exactly like the CLI flag; the Web UI's internal `config_denied` is accepted as an alias on read and never written to the URL.
**Why**: each page's `status` then matches its CLI flag exactly, which is the parity the maintainer asked for. A global rename would break the CLI.

## D11 — CLI activity default stays "all types"

**Decision**: `activity list|watch` keep all types by default and gain `--view calls|system|all`. Web and macOS default to Tool calls.
**Why**: CLI output is consumed by scripts and by the SC-006 parity tests of Spec 108. Silently dropping system rows would change results. Recorded as accepted contradiction X10.

## D12 — Catalog: fan-out and one ranking function

**Decision**: `internal/registries/catalog.go`: `SearchAll(ctx, q, tag, limit)` runs `SearchServers` per enabled source concurrently (errgroup-free: goroutines + buffered channel, per-source `context.WithTimeout(5s)`). It merges, de-duplicates by (source, id), and sorts with `Rank(a, b)`, which is pure and deterministic: official source > verified publisher (the official registry's namespace verification, or `publisher` equal to the repository owner) > popularity desc > text relevance (title/id/description token match score) > title asc. Empty `q` returns sections `official` (official-source entries) and `popular` (top popularity across sources), each capped at 12. `unavailable[]` lists failed sources with the reason. REST `GET /api/v1/catalog/search`; MCP `search_servers` with `registry` omitted calls the same function; CLI `catalog search` calls REST.
**Why**: C1 ("forks first") is a ranking problem. Ranking must live in one place so every surface agrees (SC-008).
**Rejected**: ranking in the frontend (macOS and CLI would diverge); requiring a source pick (N3's complaint).

## D13 — Paste-first add and secrets

**Decision**: `configimport.DetectFormat` learns two formats: `url` (a single `http(s)://` token) and `command` (a single line that is not JSON/TOML; split with a quote-aware splitter; the only one in-repo is `internal/oauth/spawnargv.go` `splitCommandSegments*` (unexported), which is moved to a small shared package rather than re-implemented (`upstream add -- …` itself receives argv already split by the shell)). Preview returns proposed servers, and each env/header entry carries `secret_like` (name heuristic: `(?i)(token|secret|password|passwd|api[_-]?key|[_-]key$|auth|credential|private[_-]?key)`) and `empty_or_placeholder`. Nothing is executed during preview. On Add, entries marked Secret are written with `POST /secrets` (keyring) under the per-kind name `<server>-env-<name>` / `<server>-header-<name>` (FR-065; `-2`, `-3`, … when the name is already in the keyring, never overwriting it — D28), and the config gets `${keyring:<that name>}`. When the keyring is unavailable the toggle is disabled with the backend's reason.
**Why**: S7. The keyring path and `config-to-secret` already exist, so this only moves the choice to add time.
**Rejected**: auto-storing every value as a secret (non-secret values like paths become opaque); storing the raw value and converting later (it writes the secret to disk once).

## D16 — Header and ⌘K

**Decision**: the palette is a Web-only component (`CommandPalette.vue`) with sources: static pages from the router, servers from the store, tools from `GET /api/v1/index/search?q=<text>&limit=8` (debounced 150 ms), requested **only once the trimmed input is non-empty** — `handleSearchTools` answers an empty `q` with `400 Query parameter 'q' required` — so the palette's initial state lists pages, actions and servers and never issues that request (codex round 4), settings fields from the existing Settings field registry (`SETTINGS` field lists used by the Settings search), and actions (Add server, Connect client, Create token, Open review queue). The shortcut is ⌘K / Ctrl+K and `/` when no input is focused. The status pill shows the routing mode as a read-only chip (H3).
**Why**: H1. The field registry already backs Settings search (`Settings.vue` `allFields`), so settings search is reuse, not new data.

## D17 — Terminology decisions

- "Catalog" (browse and add) vs "catalog source" (a registry). The CLI keeps `registry` for sources because renaming a command group breaks scripts. `registry search|add` become deprecated aliases of `catalog search|add`.
- "Settings" everywhere. "Configuration" is retired from UI copy (Raw JSON stays).
- "Review queue" is the place and "Review" the verb. "Security" is no longer a nav item. Scanners live in Settings → Security → Scanners, and scan history is reached from review screens.
- Tool review states "New, needs review" / "Changed, needs review" / "Approved". Wire values are unchanged (`pending`, `changed`, `approved`).
- Tool tier vs risk: "tier" is the annotation class; "risk" stays the scan score (0–100). The Tools page's "Risk" column and filter actually show the annotation class (`getRisk`, which also misclassifies unannotated tools as write), so 109-a relabels them "Tier", switches them to the backend `tier` field, and keeps `?risk=` and CLI `--risk` as aliases (FR-028).

## D18 — Server edition

**Decision**: new REST routes are registered in both editions, except `/clients` (personal only, like 108 D22). They use the same caller classes in both editions (FR-007, contracts/rest-api.md): `/attention`, `/review` and `/servers/{id}/review` are **filtered** reads (administrators, including the server-edition `admin_user`, see everything; a scoped caller, i.e. an agent token or a non-admin OAuth user session, sees only servers passing `CanEnumerateServer`, so a user with no `allowed_servers` sees an empty list); `/catalog/search` is filtered on `added` only. An earlier draft said "admin-only" here; review round 3 aligned it with FR-007 (D24). The personal sidebar regrouping, Home and header do not apply to the server edition's `/my/*` and `/admin/*` views. The Settings "Server Edition" tab is gated on `status.edition`.

## D19 — Untrusted content on the review screen

**Decision**: captured descriptions and schemas are rendered as text nodes only (no `v-html`, no Markdown, no auto-linking), truncated at 2,000 characters with "Show all", inside a block labelled "from the server, not verified". The macOS app uses `Text(verbatim:)`. The CLI prints them indented under a label. MCP inspect ops keep their existing untrusted-content framing. A vitest test feeds a description with `<img src=x onerror>` and Markdown links and asserts no element is created. The same rule covers client-derived display names (`clientInfo.name` from any MCP `initialize`, shown in "Other: <name>" rows, attention `subject.name`/`summary`, the tray and CLI): default-escaped interpolation on Web, `Text(verbatim:)` on macOS, control and ANSI escape sequences stripped for CLI and tray strings, length capped at 64 characters. It also covers catalog results (`title`, `description`, `publisher` come from arbitrary user-added catalog sources): text-only on Web, `Text(verbatim:)` on macOS, plain text on the CLI, covered by the same vitest fixture shape in `add-server-catalog.spec.ts`.

## D20 — Performance

**Decision**: attention is served from a cached snapshot, O(servers + clients) recompute on events (SC-011 ≤ 20 ms p95 at 100 servers / 1,000 tools). Review payloads read approval records for one server, with no index scan. Catalog search is bounded by the slowest source's 5 s timeout. The palette's tool search reuses the BM25 index (< 100 ms, constitution I).

## D23 — Review round 2 decisions

Twelve findings (2 high, 5 medium, 5 low), each checked against the code at `638fa805a`. All were applied; the two marked "different fix" keep the reviewer's intent with a safer mechanism.

- **Caller classes on new read routes (high)**: `requireAdminRead` keys on `!IsAdmin()` (`internal/httpapi/tokens.go:106`), and its own comment warns that a plain server-edition OAuth `AuthTypeUser` session would pass an `AuthTypeAgent`-only check. The spec said "administrator" for `/attention`, `/review` and `/catalog/search` but only tested agent tokens. New FR-007 plus a "caller classes" preamble in contracts/rest-api.md: every new read route branches on `auth.IsScopedCaller`, never on `Type == AuthTypeAgent`, and is tested with an agent token and a non-admin `AuthTypeUser` context under `-tags server` (T055b, T075a, T099; T125 already covered `/clients`). **Different fix**: `/attention` and `/review` stay filtered reads (`canSeeServer`/`visibleServers`), not `requireAdminRead`, because the spec deliberately gives agent tokens a narrowed view and a `403` would contradict FR-006's narrowed SSE frames. A user session with no `allowed_servers` sees nothing (`CanAccessServer` denies an empty list), so the rule fails closed. `GET /servers/{id}/review` sits under the existing subtree scope guard, which answers an out-of-scope server with the missing-server `404`.
- **`/catalog/search` auth (medium)**: catalog entries are catalog-source data, readable today without an admin gate (`GET /registries/{id}/servers`), so the route has no admin gate either. The one config-derived field, `added`, is joined only against servers the caller can enumerate, so a scoped caller cannot learn from it that an out-of-scope server is configured. No field carries a configured server's name, URL or command. MCP `search_servers` has no `added` field at all.
- **Quarantined + transport fault (medium)**: both `server_error` and `server_review` matched one server. `server_error` now requires `admin_state != quarantined`; the review screen shows the transport error. Test in T053.
- **`client_last_seen` had no writer (high)**: T129 named the map but plan.md did not, and nothing said which code writes it.
