# Research: Spec 113 — Upstream resilience

**Baseline**: `origin/main` @ `8442428d1` (2026-10-05). mcp-go source: `~/go/pkg/mod/github.com/mark3labs/mcp-go@v1.0.0`. Line numbers are as of that baseline and drift; implementers re-locate by symbol.

## 1. Gap re-verification (audit 2026-10-01)

| Gap | Audit claim | Verdict | Evidence and corrections |
|---|---|---|---|

## 2. Decisions

| # | Decision | Rationale | Rejected alternatives |
|---|---|---|---|
| D1 | Pre-empt mcp-go's reactive refresh inside `PersistentTokenStore.GetToken`, only for the store instance handed to mcp-go (refresher attached after `client.NewOAuthHandler`) | `TokenStore` is the only seam mcp-go exposes; returning a fresh token means `getValidToken` never calls its unlocked `refreshToken`. Read-only probes (`manager.go:2279`, `:2682`, `appctx`) build their own stores without a refresher, so they stay network-free | Forking mcp-go; wrapping `OAuthHandler` (not an interface, `transport.WithHTTPOAuth` takes a config, not a handler); a mutex around `GetToken` alone (does not stop mcp-go from refreshing with a stale token after the lock is released) |
| D2 | Single-flight coordinator keyed by server key with re-read-under-flight | Covers all three paths; re-read makes a late caller that read the old token a no-op; waiters share success and failure | none: `golang.org/x/sync/singleflight` alone is insufficient because it has no re-read step and keys only by string; it MAY be used inside the coordinator (`golang.org/x/sync` is already in `go.mod` as indirect, so this promotes it, no new module) |
| D2a | The bound store returns tokens to mcp-go with `ExpiresAt` zeroed | `getValidToken` re-checks `IsExpired` after `GetToken`; a token returned microseconds before expiry would otherwise trigger mcp-go's unlocked refresh. Zero means never-expiring in mcp-go, so mcpproxy owns expiry entirely | Returning a token with a safety margin only (shrinks, does not close, the window) |
| D3 | Transient refresh failure inside `GetToken` returns `ErrTokenRefreshTransient`, terminal returns an error wrapping `transport.ErrOAuthAuthorizationRequired` | Returning the expired token would make mcp-go refresh again with the same (possibly already consumed) refresh token; returning a plain error keeps the call failing fast as transient | Returning the expired token with `RefreshToken` blanked (mcp-go would then report authorization required on a mere 503) |
| D4 | One BBolt transaction for token saves (`UpdateOAuthTokenPreservingClient`) | Removes the lost update without a process-wide lock on storage | A mutex in `PersistentTokenStore` (multiple store instances per key exist) |
| D5 | Endpoint overrides via AS-metadata response rewrite in `OAuthTransportWrapper` | mcp-go reads endpoints only from metadata fetched through `OAuthConfig.HTTPClient`; the wrapper is that client's transport | Patching mcp-go; dropping mcp-go's OAuth for these servers |
| D6 | Discovery cache keyed by hash(URL, oauth overrides), 1 h / 30 s TTLs | A config change naturally misses the cache; failures retry quickly; bounded LRU | Invalidating from `DetectConfigChanges` (extra wiring, and server edits are per-server) |
| D7 | Per-call status recorder in `internal/transport` for `upstream_http_status` and the jsonrpc-vs-other split | mcp-go hides status and unmapped codes in strings | Parsing error strings (brittle; FR-049 forbids it as the primary method) |
| D8 | Add `cancelled` to the 113-c class list | Caller cancellation is neither an upstream nor a proxy fault and the audit vocabulary already has it | Folding it into `timeout` or `proxy_internal` (pollutes failure-rate and dashboards) |
| D9 | Failure-rate window in memory, recorded at `Manager.callTool` + `code_execution` dispatch | Those are the only two places every upstream `tools/call` passes; keeps 113-d independent of 113-c and 113-e file ownership | Deriving from the activity log (async, and owned by 113-c); recording in `managed.Client` (owned by 113-e) |
| D10 | Session re-init followed by a synchronous `tools/list`; no `connectionEpoch` bump only when every tool identity is unchanged; `tools/call` retried only for read-only tools; mcpproxy tracks the known session id itself | Bumping the epoch unconditionally would make Spec 105 pinned retries refuse; skipping the re-list would let a restarted upstream with changed tools serve a pinned call; mcp-go maps every 404 to `ErrSessionTerminated`, so a non-conforming server could 404 after executing — repeating only read-only calls bounds the damage; a health ping or tool-count request can clear mcp-go's session id first, so the transport's id alone is not a reliable trigger | Full reconnect (today: fails the call and churns state); retrying all tools (possible double execution) |
| D11 | 113-f keeps `ttlMs:0`, scope `private` | Every listing is caller- and state-dependent; a non-zero TTL would let a client keep showing a tool after quarantine or revocation. Revisit only with a per-surface analysis | Short TTL (5–30 s): saves a round trip but makes revocation lag; `public` for any list: wrong for profile/token-scoped listings |
| D12 | No new config fields except the four 113-b overrides; all thresholds are constants | Keeps the config-field checklist to one slice | Configurable window/threshold (no request for it) |

## 3. mcp-go facts implementers rely on

- `transport.OAuthError{ErrorCode, ErrorDescription, ErrorURI}` is exported; `errors.As` works on refresh errors from `handler.RefreshToken`.
- `getValidToken`: if `GetToken` returns an error other than `ErrNoToken`, it is returned as-is; `sendHTTP` converts only `errors.Is(err, ErrOAuthAuthorizationRequired)` into `OAuthAuthorizationRequiredError`.
- `Token.IsExpired` treats zero `ExpiresAt` as never expiring.
- `StreamableHTTP.GetSessionId()` exists (`streamable_http.go:985`); `isModern()` is unexported — the protocol era must be read from mcpproxy's own state: `core.Client.serverInfo.ProtocolVersion` with `mcp.IsModernProtocol` (`internal/upstream/core/connection_lifecycle.go:112`). mcpproxy initializes with `mcp.LATEST_LEGACY_PROTOCOL_VERSION` (`:26`), so upstream sessions are normally legacy and carry a session id.
- `MCPServer` default cache hints: `ttlMs:0`, `private`, modern requests only.

## 4. Deferred items (design only; tasks T250–T259)

### R-G4 — CIMD (Client ID Metadata Documents)

**Sketch**: the MCP 2025-11 authorization spec lets a client use an https URL as its `client_id`; the AS fetches a JSON client metadata document from that URL (redirect URIs, name, logo, grant types). For mcpproxy: host `https://mcpproxy.app/oauth/client-metadata.json` with `redirect_uris` covering loopback (`http://127.0.0.1/oauth/callback`, `http://localhost/oauth/callback`; RFC 8252 loopback port flexibility), `token_endpoint_auth_method: none`, `grant_types: [authorization_code, refresh_token]`. Flow: if AS metadata advertises `client_id_metadata_document_supported: true` and no static `client_id` is set, use the document URL as `client_id` and skip DCR; else DCR as today. Removes DCR registration churn and the dead-DCR-client failure mode of G2.

**Open decision (maintainer)**: publishing a client identity document on mcpproxy.app is a product and trust commitment (every install shares one client identity; the AS will show mcpproxy's name/logo; the document must stay up). Also needs: the exact loopback redirect matching rules each AS applies, and whether server edition (non-loopback `public_url` callback) needs a per-deployment document. Placeholders: T250 (document schema), T251 (hosting decision), T252 (discovery flag + selection logic), T253 (fallback to DCR), T254 (tests against an httptest AS).

### R-G10 — Server-edition per-user upstream credentials

**Verdict**: confirmed. Per-user credentials stored by `oauth_connect` (`internal/serveredition/broker`) are never injected; there is one shared `upstream.Manager` and one connection per upstream. This is the documented Spec 107 FR-034 freeze, not an accidental bug.

**Sketch**: (1) key upstream connections by (server, user) for servers marked `per_user_credentials`; (2) resolve the caller's tenant principal at dispatch (already available for agent tokens owned by tenants) and select that user's connection, created lazily with the broker credential via a per-connection `TokenStore` adapter over `broker.CredentialStore`; (3) refresh via the 113-a coordinator keyed by (server key, user); (4) idle eviction of per-user connections; (5) tool index stays shared (tool lists assumed identical across users; differing lists need per-user filtering). **Open decisions**: connection fan-out limits; whether tool lists may differ per user; restoring the Spec 107 deleted chain via `git revert` vs a fresh design. Placeholders: T255–T259.
