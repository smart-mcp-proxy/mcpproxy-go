# Feature Specification: Agent-Token Scope Hardening — Every MCP Request Authorized by Its Own Scope

**Feature Branch**: `105-agent-scope-hardening`
**Created**: 2026-09-07
**Status**: Draft — cross-model review complete (19 rounds, gpt-6-astra, ready-for-plan 2026-09-07)
**Input**: User description: "Agent-token scope hardening: every fixed MCP surface must authorize each request by its own token and profile scope — cached responses, set_profile and profile-URL responses, retrieve_tools metadata, direct-publication filtering, target-tier execution permission, aggregated prompts, and per-server management operations"

**Related**: Spec 104 (auto routing mode — depends on this spec; its FR-016 states the invariant these corrections make true), Spec 085 (compact router, `describe_tool`), Spec 102 (schema-deferred direct mode: the publication and skew tests extended here), Spec 057 (Profiles v2), agent tokens ([docs/features/agent-tokens.md](../../docs/features/agent-tokens.md)).

## Context & Motivation

MCPProxy's security story is that an agent token is a *scoped* credential: it may see and use only the servers, profile and permission tiers it was granted. The cross-model review of Spec 104 verified that claim against the code one surface at a time and found eight places on the MCP surfaces where a scoped token can learn about or act on servers outside its grant. None is reachable by a token that behaves; every one is reachable by a prompt-injected or curious agent holding a legitimately narrow token. Each is a small correction; together they make the sentence "every MCP request is authorized by its own effective scope" true in every routing mode, before Spec 104 relies on it.

The eight gaps, in the order a scoped agent would hit them:

1. A response cached under a broad authorization can be read back under a narrower one — on the same session, another session, or through the direct call path — and pre-existing cache entries carry no authorization at all.
2. `set_profile` answers list every configured server and enumerate every profile on an invalid selection; the profile-URL endpoint's error for a missing or deleted profile does the same, and its status codes reveal whether any profile exists.
3. `retrieve_tools` runs and limits the search over the whole fleet before scope filtering and computes usage statistics, debug counts and session risk over the fleet, so a scoped token learns out-of-scope names and counts and loses authorized hits to hidden ones.
4. During a direct-surface publication a returned definition can be filtered against a catalog other than the one that produced it, and names the catalog cannot parse are treated as built-ins.
5. Retrieve-surface dispatch checks the permission of the `call_tool_*` variant the caller chose, not the tier the target tool requires, and the target-tier resolver falls back to a search that can classify the wrong tool or default to read.
6. An aggregated prompt is authorized against a server parsed from its flattened name while its handler dispatches to the recorded owner, and unparseable names are retained rather than refused.
7. `upstream_servers` `tail_log` and other per-server operations look up the named server before checking scope, and log-file identity is lossy (`a/b` and `a_b` share a file).
8. Dispatch-denial and "available servers" errors name servers the caller may not see.

Fix sessions for (1), (2), (5), (6) and (7) were started in parallel from the review; this spec is the acceptance contract they must satisfy, and it adds (3), (4) and (8). The round-1 review of this spec found each session's brief narrower than the contract below in at least one respect (effective-profile provenance, durable invalidation, target resolution identity, log-file identity, existence oracles); those items are marked ⚠ so the sessions can be updated.

## Scope Boundary *(read before planning)*

| Already exists | Reused, not rebuilt |
|---|---|
| Per-request agent-token context (caller kind, allowed servers, permission set, profile pin) and profile resolution (pin → URL scope → session selection → none) | the inputs to *effective authorization* |
| Direct-surface publication order (registry, then catalog) with skew tests (Spec 102) | extended, not replaced |
| Target-tier classification from tool annotations (used by the direct surface and code execution) | made authoritative and fail-closed |
| Response cache with paginated, recursively cached entries | gains provenance |

**Transport and caller scope.** This spec covers the HTTP MCP surfaces — `/mcp`, `/mcp/all`, `/mcp/code`, `/mcp/call`, `/mcp/p/<slug>` and the legacy aliases — for requests **authenticated as agent tokens**. Native stdio is local-administrator-only (it installs an administrator identity unconditionally and has no credential channel) and is out of scope. One narrow REST exception: the direct call path (`/api/v1/tools/call`, used by the CLI, Web UI and tray) can redeem cached responses through its `read_cache` branch; FR-001 covers that redemption door with the same effective-authorization rule — a REST caller's effective authorization is its API key or agent token **including its profile pin** (direct dispatch already enforces the pin there; a deleted pin resolves to deny-all), so a token allowing `{a,b}` but pinned to `{a}` cannot redeem an unpinned entry containing `b` through the endpoint that refuses its direct call to `b`. A pinned-token fixture compares direct dispatch and cache redemption on that endpoint. `read_cache` is not exposed on `/mcp/all`. Administrator callers (API key or local socket) keep every capability they have today. The REST management API keeps its existing policy (token server restriction without profile pin; profile listing) and is out of scope here; requests that arrive without any credential where the deployment does not require MCP authentication are administrator-shaped by that deployment's choice and are out of scope. Every correction is a deliberate change to fixed-surface runtime behaviour for agent-token callers. Administrators are affected only by the **administrator exception list**, defined once in SC-005 and referenced everywhere: legacy and internal cache entries (FR-002), exact-identity preservation including its discovery/index consequences (FR-009), withholding of definitions and prompts with no registration identity (FR-006, FR-008), and canonical container ownership and subject-bound log routing in housekeeping (FR-007). Tool-definition goldens are unchanged throughout.

## Definitions *(binding)*

- **Effective authorization** of a request: caller kind; the token's allowed-server set (wildcard = all); its permission set (exact membership of `read`, `write`, `destructive`); and the *effective profile scope* after resolution — token pin, else URL scope, else session selection, else none — expressed as the resulting allowed-server set and profile identity. A deleted pin resolves to deny-all, as today.
- **Authorized population** of a request on a surface: the servers, tools and prompts its effective authorization may see under that surface's discovery predicate (availability and approval rules unchanged; retrieve discovery remains tier-blind, the direct listing tier-filtered — Spec 104 preserves this asymmetry).
- **Registration identity** of a tool or prompt: the canonical owning server and raw upstream name recorded when it was registered on a surface, plus its tier as classified then. Never derived by parsing a flattened display name.
- **Non-disclosing refusal**: the response for a resource outside the caller's server or profile scope is indistinguishable in status, body and timing class from the response for a nonexistent resource of the same kind. Tier denials on authorized servers are not non-disclosing by design (FR-010 precedence).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — A server-restricted token cannot learn about other servers (Priority: P1)

A team issues an agent token restricted to server `a`. Through any route the MCP surfaces offer — cached responses, profile switching, `retrieve_tools` statistics or debug output, prompt listing, log tailing, error messages — the agent learns nothing about servers `b` or `a__b`: not their names, tool or prompt names, counts, status, logs, or existence.

**Why this priority**: This is the promise the scoped-token feature makes. Each leak is small; together they let a compromised agent map the fleet.

**Independent Test**: One fixture with servers `a`, `b` and `a__b`, each carrying tools, prompts, usage history and a distinctive hidden **sentinel** string in its names and descriptions; an `a`-only token; an administrator credential; and a second fixture identical except that `b` and `a__b` are absent. Every scenario runs the same request against both fixtures and asserts the `a`-only responses are equal after normalising nondeterministic fields (timestamps, cache handles, durations), and that no sentinel appears. The applicability matrix in FR-014 says which surface exposes which operation.

**Acceptance Scenarios**:

1. **Given** a response cached under a broader effective authorization (on the same session, another session, or produced by discovery or an upstream content block), **When** the `a`-only token redeems it through `read_cache` or the direct call path, any page or recursive child page, **Then** it receives a non-disclosing refusal.
2. **Given** a cache entry persisted before this feature (no provenance) in an upgrade fixture, **When** any caller — administrator included — redeems it, **Then** it is refused without content and is durably invalidated (a second attempt after restart is also refused, and the store no longer holds it).
3. **Given** the `a`-only token, **When** it calls `set_profile` with an empty selection, a selectable profile, a non-selectable profile, or a nonexistent name, **Then** the server list in the response is the effective intersection after the update, the two failing cases produce the same non-disclosing refusal, and no non-selectable profile is named.
4. **Given** the `a`-only token's pinned profile is deleted, **When** it requests the profile URL, **Then** the status and body are the same whether or not other profiles exist and whether or not any profile is configured; the same holds for `/mcp/p` and `/mcp/p/` and for a token whose pin still exists but does not match.
5. **Given** usage seeded on `b`, high-ranking tools on `b` for the query, and prompts on `a__b`, **When** the `a`-only token calls `retrieve_tools` with statistics and debug enabled, **Then** the response is identical between the two fixtures for every scope-independent field (usage summary, top tools, indexed counts, risk) under the retrieve oracle, and its ranked-window fields (tool set, `total`, filter diagnostics, ordering, scores) each equal the per-fixture derivation the oracle defines.
6. **Given** prompt aggregation is on, **When** the `a`-only token lists or fetches prompts, **Then** no prompt owned by `b`, `a__b` or `__a` is listed or fetchable, and no prompt without a registration identity is listed or fetchable by anyone.
7. **Given** the `a`-only token, **When** it calls `upstream_servers` `tail_log` (or any per-server operation it may invoke) naming `b`, `a__b`, `a/b` or `a_b`, **Then** it receives a non-disclosing refusal; and **When** an `a_b`-only token tails its own server, **Then** it receives only records attributable to `a_b` — never a line of `a/b`, never an unattributed legacy line, and never a whole-file refusal that depends on `a/b`'s presence.
8. **Given** the `a`-only token, **When** a dispatch is denied for scope or the target server has no live client, **Then** the error names neither the canonical owner of the tool nor any server outside its authorized population.

### User Story 2 — A read-only token cannot execute above its tier (Priority: P1)

A team issues a read-only agent token. The agent tries to run an approved write or destructive tool by choosing `call_tool_read`, with strict server validation on or off. Every attempt is refused because the target tool's own tier, resolved from its registration identity, decides.

**Why this priority**: Permission tiers are the difference between a token that can look and a token that can delete. The direct surface already enforces this; the retrieve surface, which 92% of installs use, does not.

**Independent Test**: The permission-set × target-tier × variant table of FR-009, run on the retrieve surface through `call_tool_*`, on the direct surface through direct-name dispatch, and inside a code-execution script through nested `call_tool`/`call_tools`, asserting insufficient-permission results and **zero upstream calls**.

**Acceptance Scenarios**:

1. **Given** a `{read}` token and an approved write tool, **When** it calls `call_tool_read` with strict validation on, **Then** the call is refused for insufficient permission and the upstream is never invoked.
2. **Given** the same token and an approved destructive tool, **When** it calls `call_tool_read` with strict validation off, **Then** the call is refused for insufficient permission and the upstream is never invoked.
3. **Given** a token holding the target's tier but selecting a mismatched variant, **When** it calls, **Then** the existing variant/intent mismatch handling applies unchanged.
4. **Given** server `a` exposes a read tool `erase` and a destructive tool `ns:erase`, **When** a `{read}` token calls the latter by any route, **Then** the classification is of `ns:erase`, not `erase`, and the call is refused.
5. **Given** a tool whose registration identity cannot be resolved (stale or missing metadata), **When** a scoped token calls it, **Then** the call is refused for insufficient permission — never authorized as read by default.
6. **Given** a script that calls a tool above the token's tier, **When** the script completes, **Then** the nested call's refusal envelope shows insufficient permission and the script's success does not mask it.

### User Story 3 — A listing never returns a definition its own publication would not authorize (Priority: P2)

Server `a`'s tool `b__c` is replaced by server `a__b`'s tool `c`, so display name `a__b__c` survives with a new owner. An `a`-only token listing tools at any moment during the publication — before, between, or after the registry and catalog switch — never receives the new owner's description or schema, in either skew direction, in full or deferred rendering. Dispatch at each seam is governed by whichever handler is registered at that moment (see scenarios 3–4).

**Why this priority**: The window is short and needs a specific rename, but the disclosure is of a full definition, and the existing skew test checks names and dispatch, not the returned definition.

**Independent Test**: The origin-flip fixture with a pause seam between registry and catalog publication, asserting the complete returned definition for every listing served at every seam, plus the malformed-name, built-in and tier-change cases below.

**Acceptance Scenarios**:

1. **Given** the origin-flip fixture, **When** the `a`-only token lists tools at any seam, **Then** each returned definition's owner and tier come from the registration identity of the publication that produced that definition.
2. **Given** a newly registered name the catalog cannot parse (a leading `__`, or a `b__`-prefixed name absent from the old catalog), **When** it is listed, **Then** it is authorized by its own registration identity — never classified as a built-in, never withheld merely for being unparseable; built-ins are positively identified. A definition with no registration identity is withheld.
3. **Given** a same-owner tool whose tier changes from read to destructive during publication, **When** a `{read}` token lists on the direct surface, **Then** the tool is withheld once the new tier is registered; dispatch expectations follow the **handler registered at each seam**: while the read registration is installed the call may execute, and once the destructive registration is installed it is refused for insufficient permission — no earlier revocation is required.
4. **Given** dispatch is attempted for the flipped name at each seam, **Then** the outcome follows the registered handler: while the name is registered to authorized server `a` (before the forward flip, after the reverse flip) the call may execute; while it is registered to out-of-scope `a__b` it receives a non-disclosing refusal (the current error, which names the hidden owner, is replaced).

### Edge Cases

- **Administrator callers.** Unchanged everywhere except the administrator exception list of SC-005 (legacy and internal cache entries; exact-identity preservation and its discovery/index consequences; withholding of definitions and prompts with no registration identity; canonical container ownership and subject-bound log routing in housekeeping).
- **Unrestricted agent tokens** (no server restriction, no pin, full permission set) keep the same successes except where this spec mandates a security refusal that applies regardless of grant: (1) an **empty profile** (valid today) is refused through `set_profile` and the profile URL; (2) exact-identity policy gates (FR-009) — a config-denied or unapproved `a:ns:erase` no longer succeeds because `a:erase` is allowed, and a failed or stale identity resolution is refused; (3) definitions and prompts with no registration identity are withheld (FR-006, FR-008). Administrators keep (1); (2) and (3) apply to administrators too, as named exceptions in SC-005. Their refusal bodies change where this spec changes error shapes. Fixtures exercise (1)–(3) with an unrestricted agent and record the administrator outcome.
- **Same-authorization cache reads** are byte-identical to today, including pagination, after nondeterministic-field normalisation.
- **Internal cache entries** (registry and guesser caches) are not agent responses and are non-redeemable through `read_cache` by any caller.
- **Durable invalidation.** Invalidation of a refused entry MUST survive the refusal path: the existing expiry branch deletes inside a transaction and then errors, which rolls the deletion back; the upgrade fixture asserts absence after restart.
- **Profile selection predicate.** An unpinned token may select a profile whose server set intersects its allowed-server set; profiles with an empty intersection and nonexistent profiles are both refused identically. Profile names are therefore disclosed only for selectable profiles.
- **URL precedence.** `set_profile` on a URL-scoped endpoint records the session selection but the URL still governs the request; the response reports the effective scope, not the stored selection alone.
- **Ranking under scope.** Scoped discovery applies scope filtering *before* limiting. The **search corpus** is the one the existing index selection already chooses for the request: the profile-specific index when the effective profile has one (this applies to profile-scoped administrators too), otherwise the shared fleet index, with the existing fallback to the shared index when the profile index is unavailable — this selection is preserved unchanged. Scores, and therefore ordering, are computed over that selected corpus and are documented as such: a hidden tool present in the selected corpus (a token-only restriction on the shared index) can change an authorized tool's score, the order of authorized hits, and — for a multi-term query — which authorized hits survive the top-K cut; a profile-scoped request sees only its profile corpus. "Not displaced" is defined against an exhaustive search of the **selected corpus** filtered to authorized hits before taking K: the returned set equals the top-K of that filtered list. A multi-term fixture covers a profile-scoped agent, an equivalent token-only restriction on the shared index, and a profile-scoped administrator, plus the fallback case. **The retrieve oracle** (referenced by US1.5, FR-013 and SC-001). Per fixture, the expected response is derived as: the search over the selected corpus (profile index or shared index, as the existing selection chooses), filtered to authorized hits, cut to the ranked candidate window (`limit`), then passed through the existing annotation filters (`exclude_destructive` and kin) exactly as today. Cross-fixture equality excludes everything that depends on that ranked window: `score`, ordering, top-K membership, `total`, the complete `filter_diagnostics` payload (presence, counts and suggestions), the ranking-derived fields of `explain_tool` (`found_in_results`, `rank`, presence of `tool_details`), and the ranking-dependent payload consequences (truncation occurrence, retained prefix, `total_size`, pagination metadata). Each excluded field is asserted against the per-fixture derivation above. Everything else — indexed counts over the authorized population, usage summary and top tools, risk, and every scope-independent field — is compared across fixtures. A multi-term ranking-change fixture and a `limit: 1` + `exclude_destructive` fixture pin the documented effects.
- **Retained, documented effects** that this spec does not remove: fleet-wide display-name collision admission on the direct surface (a hidden server can withhold an authorized entry); the prompt collision rule and global prompt cap; fleet-wide list-changed notifications on the fixed surfaces (Spec 104 makes them per recipient on the auto endpoint); and **shared-resource contention** — the proxy-wide call limiter is global, so a saturated limiter held by calls to a hidden server can make a call to an authorized server fail with the existing "proxy-wide limit saturated" response (a success-versus-refusal oracle that only scope-isolated admission would remove, which is out of scope). A deterministic held-call fixture (global capacity 1, no queue, a held call on hidden `b`, a call to `a`) pins the retained behaviour. Also retained: **cross-server security-scan admission** — the scan gate for a post-baseline tool addition under `trust_mode: scan` consumes other servers' tool metadata, so a same-name near-identical tool on hidden `b` can hold authorized `a`'s new tool pending (a shadowing finding), changing `a`'s discovery membership, counts and execution outcome for an `a`-only token; the approval behaviour is preserved, and this effect is excluded from the differential oracle. Fixture: real discovery with an established baseline on `a`, then an added tool that scans clean without `b` but is held with a matching peer on `b`; assert authorized ownership of everything returned and the documented approval/discovery/dispatch difference. Also retained: **shared prompt-refresh deadline** — prompt collection visits servers sequentially under one fleet-wide deadline, so a slow hidden `b` can exhaust it before authorized `a` is visited and `a`'s approved prompts drop out of the published set until the next refresh; the effect is documented, excluded from the differential oracle, and pinned by a controlled-order fixture (hidden `b` consuming the deadline; `a`'s prompt absent from list/get; no hidden content). Also retained: **shared log rotation and retention** for colliding server names (FR-007) — attribution filters what is returned, not what history survives rotation. The invariant in FR-012 is stated with these named.
- **Upstream text.** Authorized upstream content that happens to mention another server's name is not scrubbed; the guarantee is about proxy-produced data, not semantic filtering of authorized responses.
- **Operator-published content.** Two kinds of operator-authored content are published to every caller by design and sit outside the semantic-disclosure guarantee: (1) custom initialization `instructions` (Spec 104 FR-019 preserves them on every rung); (2) stored code-execution scripts — their names and any constants they return without an upstream call. Documentation MUST warn operators not to place server names or secrets in either. What the guarantee does cover: a missing-script error MUST NOT enumerate other script names or the script count to an agent-token caller (non-disclosing refusal), while administrators keep today's enumeration; and every upstream call a script makes remains scope-checked (FR-009). Because the published `code_execution` definition currently tells callers to discover scripts by requesting a nonexistent name, that definition text MUST be corrected to say enumeration is administrator-only and agent-token callers must already know the script name — the one **narrow golden exception** in this spec (FR-012): the affected description strings change, nothing else in the goldens does, and both caller kinds are tested. Fixtures: a scoped initialization with instructions mentioning `b:private_search` (published, documented), a missing-script request under a restricted token (no enumeration), and a script returning a constant (published, documented) while its nested call to `b` is refused.
- **Case-insensitive filesystems.** Log-file identity handling is tested with names differing only in case.
- **Prompt refresh interleaving.** Prompt sets are installed per surface instance in sequence, and approval-triggered refreshes can overlap event-triggered ones; ownership is bound to the accepted registration the handler dispatches to, so an interleaving cannot authorize against a stale owner.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001** *(cached responses)* ⚠: A cached response MUST carry the **same immutable authorization snapshot that authorized producing it** — resolved once at dispatch authorization and carried to the cache write, never re-resolved from mutable profile or session state at response completion (fixtures: a held call to `b` under profile `{a,b}` while the session selection, and separately the profile definition, is narrowed to `{a}` before the response completes; the entry is stamped `{a,b}` and is not redeemable under `{a}` on MCP or REST). That snapshot is the producing request's **effective authorization** (Definitions), and every redemption door — `read_cache` on any MCP surface, the REST direct call path's cache branch (Scope Boundary exception), and recursive child pages — MUST refuse a request whose current effective authorization is neither equal to nor a superset of the snapshot. Superset is ordered by **caller kind first**: an administrator qualifies for any snapshot; an agent token never qualifies for an administrator-produced snapshot; between agent snapshots, allowed-server set, permission set and effective profile scope must each contain the snapshot's. **Recursive provenance is monotone**: a page produced by redeeming a parent entry carries the *parent's* snapshot (or, if the redeemer's authorization is narrower, the narrower one), never a snapshot broader than the parent's — so an administrator with a narrow session profile redeeming a broad entry cannot mint a child that a pinned agent could later redeem. Fixture: administrator with session profile `{a}` redeems an entry containing `b`, the recursive child is then requested by a wildcard full-permission agent pinned to `{a}` — refused, on MCP and on the REST direct call path. Refusal is non-disclosing.
- **FR-002** *(legacy and internal entries)*: Entries with absent, legacy or unrecognised provenance — including every entry persisted before this feature — MUST be refused for every caller and durably invalidated on first redemption; internal registry and guesser cache entries MUST be non-redeemable. An upgrade fixture with a pre-feature record MUST assert refusal, absence after restart, and no content in the response.
- **FR-003** *(`set_profile`)* ⚠: The server list in a `set_profile` response MUST be the effective intersection after the update (token restriction ∩ effective profile, with URL scope still governing where present); an unpinned token may select only profiles whose server set intersects its allowed servers; non-selectable and nonexistent profiles MUST produce the same non-disclosing refusal, and no non-selectable profile is ever named. `active_profile` reports the stored session selection; the server list reports effective scope.
- **FR-004** *(profile URL)*: The profile-URL endpoint MUST apply the same selectable-profile predicate as FR-003: an unpinned token may initialize through a profile URL only if that profile's server set intersects its allowed servers. Its agent-facing status and body MUST be identical across "profile missing", "profile deleted", "profile exists but is not selectable" (empty intersection, empty profile, or empty server grant), "pin mismatch", "no profiles configured" and "other profiles exist" — pin mismatch evaluated independently of fleet population — for `/mcp/p/<slug>`, `/mcp/p` and `/mcp/p/`. Tests initialize through a selectable and a non-selectable existing profile URL with an unpinned restricted token.
- **FR-005** *(`retrieve_tools`)*: Scoped discovery MUST apply scope filtering before result limiting; indexed counts MUST be computed over the authorized population, and `total` and filter diagnostics over the authorized ranked candidate window (as today, but with only authorized candidates in that window); usage ranking MUST be computed over the authorized population's approved tools (stale history for hidden or removed tools excluded) before the top-N cut; session risk MUST be computed over the authorized servers' tools under the existing availability rules, tier-blind; `include_disabled` and `explain_tool` follow the same population (caller-supplied names echoed by `explain_tool` are not disclosure). Scoring over the existing selected corpus (profile index or shared index) is retained and documented.
- **FR-006** *(aggregated prompts)*: A prompt MUST be authorized for listing and fetching against the registration identity the handler dispatches to. Because that identity records the owner at registration, an unparseable **display name** (an owner beginning with `__`, which is a valid server name today) is not unknown ownership: the prompt is authorized normally for callers who may see that owner and withheld from others. Ownership is unknown only when no registration identity exists (an empty upstream prompt name, or a display entry with no accepted registration); such prompts MUST be withheld and unfetchable (fail closed). Fixture: server `__a` with prompt `review` is listed and fetchable by an unrestricted agent and by administrators, and withheld from an `a`-only token. Tests cover authenticated `prompts/list` and `prompts/get`, malformed names, collisions in both input orders, retained old registrations, and overlapping refreshes.
- **FR-007** *(per-server operations)* ⚠: Every server-management operation that names a server MUST authorize the name against the caller's effective authorization before lookup, with non-disclosing refusal. Log tailing MUST additionally establish canonical ownership of the log resource: where two server names map to one log file, the reader MUST return only records attributable to the authorized server (each record carries its writer's canonical server identity; records without one are non-attributable). The policy is **uniform and independent of hidden co-owners**: a scoped caller never receives a whole-file refusal that depends on whether another server shares the file — it receives exactly the records attributable to its own server, and legacy records with no attribution are withheld, whether or not a co-owner exists. Ownership filtering MUST precede tail limiting, and `lines_returned` MUST count the authorized tail, so an interleaved foreign line never displaces an authorized one from the returned window. Shared-file **rotation and retention** remain shared (isolating them per owner is out of scope): a hidden co-owner's output can rotate an authorized record out of the readable history, so this is a retained, documented effect excluded from the differential oracle. Fixtures: an `a_b`-only token tailing with and without hidden `a/b` present, with interleaved lines, receives the same attributable records within the retained history and no foreign or unattributed record; a forced-rotation fixture pins the documented eviction difference. Tests include `a/b` vs `a_b` and case-only differences. Attribution MUST be **subject-bound for shared-service producers**: a component serving several servers (the OAuth callback manager, and any similar shared service) MUST write each record through the logger of the server that record concerns — callback shutdown uses the target callback server's recorded logger, never whichever server's logger was installed last — so no server's name, port or flow state is written into another server's log; legacy records whose stamped identity conflicts with their subject are withheld from scoped callers. Fixture: start hidden `b`'s OAuth flow, start `a`'s, complete `b`, then the reverse interleaving, with distinct log files; `a`'s tail contains no `b` metadata in either order. The resulting log-routing change is administrator-visible and is listed in SC-005. Ownership MUST also hold for the **container resources** proxy housekeeping references: Docker cleanup for server `a` MUST match only containers canonically owned by `a` (never `a-b`'s by name prefix), so no foreign container name or id is ever written into `a`'s log; legacy foreign-container records already present in a log are treated as non-attributable and withheld from scoped callers. Fixture: `a` and hidden `a-b` with distinct log files, cleanup run, `a`'s tail contains no `a-b` container name or id.
- **FR-008** *(direct publication)*: Each definition returned by direct-surface discovery MUST take its owner and tier from its own registration identity in the publication that produced it, at every seam of the publication and in both skew directions, in full and deferred rendering. A definition is withheld only when it lacks a valid registration identity — never merely because its display name is unparseable or absent from the previous catalog (server `__a`'s tool has a recorded owner and tier and is authorized normally). Built-ins are positively identified, never inferred from a parse failure. Fixture: direct tool on server `__a` — listed, describable and dispatchable for an unrestricted agent and administrators; refused to an `a`-only token.
- **FR-009** *(target-tier execution)* ⚠: On every dispatch path (`call_tool_*`, direct-name dispatch, nested script calls), authorization MUST resolve the target's registration identity from exactly the canonical server / raw tool pair that will be dispatched, and every policy gate — tier classification, configured tool denial, approval and callability — MUST be evaluated on that same pair (never on a name with a namespace prefix stripped); tests cover same-tier paired names (`erase` approved, `ns:erase` config-denied or unapproved) through retrieve and nested dispatch with zero upstream calls. Identity MUST be preserved end to end: approval-record creation, baseline capture, index updates and direct publication MUST record and look up the same canonical server / raw name pair as discovery and dispatch — a namespaced tool never collapses to its suffix at any stage, so a pending approval for `ns:erase` is a pending approval for `ns:erase`, and "no record found" is never classified as callable for a tool the discovery snapshot contains. Legacy approval records whose identity was collapsed (a record for `erase` on a server whose snapshot also holds `ns:erase`) are treated conservatively: they approve only the exact raw name they store, and the namespaced tool remains pending until approved by its own name. Fixture: run real discovery and approval processing on a manual-trust server whose baseline exists, then add read-tier `ns:erase`; assert it is pending under its own name and that direct, retrieve and nested dispatch all refuse it with zero upstream calls. It MUST classify the tier from that identity, and require the caller's permission set to contain that tier **in addition to** the existing variant check. A known tool with no annotations is classified by the existing annotation-defaulting rule and that rule is documented; a failed or stale resolution MUST refuse scoped callers. Acceptance tables: (a) retrieve dispatch — permission sets `{read}`, `{read,write}`, `{read,write,destructive}` × target tiers read/write/destructive × variants read/write/destructive × strict validation on/off; (b) direct-name dispatch and nested script dispatch — permission sets × target tiers only (no variant exists there). Cells are classified before the run, in this order: *permission-disallowed* (the caller's set lacks the target tier **or**, on retrieve dispatch, lacks the selected variant's tier — e.g. `{read}` calling a read target through `call_tool_destructive`) → refused for insufficient permission; then, among cells passing both permission checks, *intent-mismatch* (the variant disagrees with the target tier under the existing strict-validation predicate) → refused by the existing mismatch handling; the remainder → *allowed* and dispatched. Every refused cell asserts zero upstream calls; the two refusal kinds are asserted with their own oracles.
- **FR-010** *(refusal shapes)*: Refusal precedence, evaluated in this order: (1) a resource on a server or profile outside the caller's effective scope → **non-disclosing** refusal (indistinguishable from nonexistent), on every surface and mode; (2) a resource on an **authorized** server that the caller may not execute because of its tier → an **insufficient-permission** refusal on every dispatch path, including the direct surface where the over-tier tool is withheld from the listing (tier denial on an authorized server is not a scope leak: the caller may already discover that tool on the retrieve surface); (3) other refusals unchanged. Dispatch denial for scope MUST NOT name the canonical owner; "available servers" suggestions MUST be limited to the authorized population. `describe_tool` MUST produce its not-found response — including any case-correction suggestion — through one policy evaluated over the **authorized** corpus only, so an unauthorized existing id and a nonexistent id yield the same response (a hidden exact match with an authorized case-equivalent alternative gets the same suggestion as a nonexistent id would). Tests cover hidden `b:read` vs authorized `B:read` on both the indexed and the direct surface. On the direct surface, agent-facing resolution of both display names and canonical ids — including alias admission and precedence between a hidden display entry and an authorized canonical alias — MUST be computed over the **authorized corpus**, so an id that resolves to an authorized tool when a hidden server is absent resolves the same way when it is present (cross-namespace fixture: authorized `x__y` exposing `z` vs hidden `x` exposing `y:z`, in definition and check modes; administrator resolution unchanged and tested separately).

### Key Entities

- **Effective authorization snapshot**: the request-derived provenance stored with a cached response and compared on redemption (FR-001).
- **Registration identity**: the owner, raw name and tier recorded at registration for a tool or prompt on a surface; the sole source of ownership and tier for filtering, listing and dispatch (FR-006, FR-008, FR-009).
- **Authorized population**: the per-request set every count, ranking, risk figure and suggestion is computed over (FR-005, FR-010).

## Assumptions

- **Non-disclosing refusal** is the chosen strategy, matching the entitlement pattern already used for hidden REST resources (status parity with an absent resource, never "body must not contain the name").
- **Superset redemption** (FR-001) is safe because a broader authorization could have produced the entry itself; equality-only would break administrators reading agent-produced entries.
- **Profile selection intersects** rather than being public: this narrows what unpinned tokens can see and select compared with today, deliberately.
- **Selected-corpus scores** are retained: profile-specific indexes already exist and are used as today; token-only restrictions search the shared index, and adding per-token indexes is out of scope. The result-set stability guarantee is what matters.
- **Strict server validation** is one boolean; the table tests both values and introduces no third mode.
- **Parallel sessions** implementing (1), (2), (5), (6), (7) were briefed before this contract existed; the ⚠ marks name where their briefs are narrower.

## Out of Scope

- The REST management API's scope policy and profile listing; native stdio (administrator-only by construction).
- Deployments that allow unauthenticated MCP requests.
- Changing which quarantined, pending or disabled tools each surface shows, or the retrieve/direct tier asymmetry.
- Per-recipient list-changed notifications, collision admission, and the prompt cap (retained; notifications addressed for the auto endpoint in Spec 104).
- New token capabilities or a new authorization model; scope-local search scoring.
