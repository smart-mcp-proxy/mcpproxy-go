# Implementation Plan: `admin_action` audit events

**Branch**: `133-admin-action-audit` | **Date**: 2026-11-24 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `specs/133-admin-action-audit/spec.md`; door inventory [inventory.md](inventory.md); line contract [contracts/admin-action-line.md](contracts/admin-action-line.md); decisions [research.md](research.md).

## Summary

Add a fourth event kind, `admin_action`, to the Spec 107 audit JSONL: one line per committed administrative effect, written synchronously where the effect persisted, from what persisted, with the caller derived the way `authz` lines derive it. The action list follows the reporter's priority order — tokens, then approvals, then config — and ships in five PRs, each mergeable alone. A door-registry test lands in the first PR, so no administrative write door can merge afterwards without either a line or a written exemption.

The unit of record is the committed effect, not the response (spec FR-013): the line is written where a change persisted, from what persisted.

## Technical Context

**Language/Version**: Go 1.26 (backend only; no Web UI, macOS or CLI output change beyond docs)
**Primary Dependencies**: none new. `internal/audit` (builder, `redact.go` masking, `sink.go`), `gopkg.in/natefinch/lumberjack.v2` (already used by the file sink), `chi.Walk` and the Cobra command tree for the registry test
**Storage**: the existing audit file or stdout stream. No BBolt bucket, no activity schema change (two additive by-products, spec Out of Scope)
**Testing**: `go test -race` on `internal/audit`, `internal/runtime`, `internal/server`, `internal/httpapi`, `internal/management`, `internal/security/scanner`, `cmd/mcpproxy`; `-tags server` for `internal/serveredition`; schema validation with the JSON Schema compiler `internal/audit/schema_test.go` already uses
**Target Platform**: personal (macOS, Windows, Linux) and server edition (Docker)
**Project Type**: single Go module
**Performance Goals**: one synchronous sink write per committed change (the same cost as one `authz` line); administrative changes are rare next to tool calls, so no batching beyond FR-014
**Constraints**: never through the event bus (FR-018); never refuses a change (FR-017); no secret, token value or hash of one on a line (FR-016)
**Scale/Scope**: about 90 mutating (door, branch) pairs (inventory.md §1–§5 plus the round-1 additions), ~55 actions, 5 implementation PRs

## Design

### D-1. Builder (`internal/audit`)

`NewAdminAction(AdminActionInput) (Line, error)` beside `NewAuthz`/`NewToolCall`/`NewAuthEvent` in `line.go`. Input is a typed struct: `Ts`, `RequestID`, `Origin`, `Source`, `Caller`, `ClientName/Version/IP/Surface`, `Profile`, `Action` (typed constant), `Target` (typed per kind), `Changes []Change`, `Trigger`, `Policy`. A `Change` can be built only by `Literal(field, before, after)` — whose value parameters are a sealed, package-owned `LiteralValue` interface implemented by `Bool`, `BoundedInt`, `Timestamp`, per-field closed-enum wrappers (built only by a parser that returns `ok=false` for a value outside the set), `TokenPrefix`, `Count`, `NameList` and `ProfileName` (validated per side against the pre-/post-commit profile set; a failure on either side yields `Withheld(field, WithheldValue)` for the whole entry), with the field↔type pairing checked against the classifier — or by `Withheld(field, WithheldSecret|WithheldValue)`. A value whose parser fails becomes `Withheld(field, WithheldValue)`. The bundle digest is not a `Change` at all: it has its own constructor on the `tpa_bundle` target only. There is no constructor that takes a `string` or `any` value and no hashing path, so FR-016 is structural. `newBase` is not reused as is: it always sets `request_id`, which must be omitted (not `""`) on background lines. The builder enforces the contract's `iff` rules, the batch caps and the 16 KiB budget (contract §Size), and returns an error for a violation. Today a builder rejection is only logged (`internal/server/audit_funnel.go:334-345`) and the field mask discards its hit flag (`internal/audit/redact.go:70-87`); PR-1 adds two counters — build/serialize failures, per-field mask hits — beside `WriteFailures` and `SanitizerHits`, all four in `mcpproxy doctor`. PR-1 also makes the sink recover at a record boundary after a short write (it remembers the failure and prefixes the next record with a newline), so a partial write cannot glue onto the next line (`internal/audit/sink.go:100-123`).

The classifier — literal, withheld secret, withheld value — is one table keyed by field path in `internal/audit/admin_fields.go`; an unknown path is `WithheldValue`. PR-1 also adds `mcp_(agt|cli|oat|ort)_[A-Za-z0-9_-]{16,}` to `credentialPatterns` (`internal/audit/redact.go:38`), which every event kind and the whole-line sanitizer share.

### D-2. Seam (`internal/runtime`) and attribution

```go
// AdminAuditor writes admin_action lines. nil = audit off.
type AdminAuditor interface {
    AdminAction(ctx context.Context, rec AdminRecord)
}
```

`Runtime.SetAdminAuditor` is called by `internal/server` when it receives the sink (`server.go:504`, where `mcpProxy.auditSink` is set). The implementation derives `audit.Caller` with `auditCallerFromContext` (`audit_funnel.go:231`) — one derivation for every event kind — reads `origin`/`source`/`client.ip`/`client.surface` from the ingress tag the mount middleware stores (not from `RequestActor`, whose surface MCP handlers overwrite with `mcp` even on a REST `/tools/call`, and which falls back to `api` on unstamped native MCP contexts, `mcp.go:5661,6241,7845-7847`, `activity_actor.go:33-47`), and writes through `p.auditSink`. Request ids follow contract rule 3: reuse the id in the context, mint only at an ingress that has none; the MCP admin wrappers stop minting unconditionally (`mcp.go:4797,4918-4934`) and use the context's id for their wrapper row and the mutation alike.

`AdminRecord` carries an explicit attribution override for effects the proxy decided (`Decider{Kind: none|internal|cli_offline, Trigger, Policy}`). It replaces **only** `caller`, `trigger` and `policy`; `source`, `origin`, `request_id` and `client` still come from the context when there is a request (contract rule 3), so request-caused reconciliation keeps its request id, and a background effect with no request has none. A nil AuthContext on an admin funnel never becomes `anonymous`.

Attribution plumbing (round-1 and round-2 findings, all verified):

- **One request id per admin ingress.** The MCP admin tools mint a local correlation id for their wrapper row and pass the original context to the mutation (`internal/server/mcp_credentials_tool.go:174-180,345-351`, `mcp.go:4797,4955`); they will install it with `reqcontext.WithRequestID` before dispatch. Connect records its mint and finalize with `context.Background()` (`internal/runtime/clients_service_connect.go:217-233,328-363`); it will receive the request context.
- **Native stdio** installs the stdio connection source and an admin context but no mount tag (`internal/server/server.go:1510-1516,1564-1566`); PR-1 tags it `source: mcp`.
- **Writers that drop the context**: `handlePatchUpstream` (`internal/server/mcp.go:6803-6809`) and the production add/update/remove writer (`mcp_upstream_writer.go:67-95`) take no context; the server-edition sharing updater takes only name and flag and discards its commit result (`internal/serveredition/api/admin_handlers.go:578-594`, `internal/runtime/server_sharing.go:17-39`). Each gains a context-taking variant in the PR that owns its line.
- **Registry writers** drop the HTTP context before their commit (`internal/httpapi/server.go:6893-6894,6930-6931,6975-6976`, `internal/server/add_registry_source.go:132-143`); PR-3 passes it.
- **SSO provisioning** runs on a public route before any session, outside the sibling group (`internal/serveredition/setup.go:275-286`); PR-1 tags that route too; PR-4 attributes provisioning and group changes through an explicit caller override built from the verified identity the callback committed, never from the empty AuthContext. Public OAuth registration uses an explicit `anonymous` override (PR-1).
- **Locks** (PR-1, contract §CLI ownership): `serve` resolves the config path without side effects, canonicalises it, takes `<config>.lock` before it reads or writes the file and holds it for its lifetime, then the audit-file lock before it opens a file sink; config-editing CLI commands take the config lock non-blocking across their read-modify-write and audit attempt. Lock order: config, then audit file.
- **Server-edition mount.** The server-edition routes are a sibling group with their own auth middleware (`internal/serveredition/setup.go:343-350`), outside the core `/api/v1` chain that runs `TagRequestMeta` and `actorContextMiddleware` (`internal/httpapi/server.go:1100-1111`); an untagged context would make `auditSourceFromContext` default to `mcp` (`audit_funnel.go:198-207`). PR-1 installs both middlewares on that group.

## Tests that pin each door

1. **Door registry test** (D9 in research.md): enumerates doors from the constructed personal and `-tags server` routers (`chi.Walk`, every route and method, the server-edition sibling group included, each classified by name); the REST built-in dispatch descriptors PR-1 introduces in place of the `switch toolName` (`mcp.go:7841-7894`); the outer `http.ServeMux` OAuth doors from production descriptors that carry the methods each handler accepts (the pattern tables hold paths only; methods are checked inside the handlers, `oauth_login_http.go:195-291`); every registered built-in tool per surface — the default server that native stdio serves (`GetMCPServer()` returns `p.server`, with its own `registerTools`, `server.go:1510-1516`, `mcp.go:984-985,1771-1774,7675-7678`), call-tool, code, direct and single-server registrations are separate (`mcp_routing.go:1513-1540`, `mcp_single_server.go:285-346`) and compared per surface, not as a union — across the supported registration configurations (`enable_skills`, management disabled, read-only), plus the admin tools' dispatch descriptors (operations, aliases, effect branches); and every runnable node of the constructed Cobra tree. The CI guarantee is "every registered door and descriptor-backed operation is classified"; branches inside an existing `RunE` or service are pinned by the exact-effect fixtures, not discovered. Each must be in the registry (`{door, branch, action | exempt reason, slice}`), each registry entry must still exist, and the pending set may only shrink.
2. **Door table test** per slice: for each `done` (door, branch), drive the real handler (`httptest` against the router with an API key, a socket context, an agent token, a browser-login token, a session admin and a session user in `-tags server`; the MCP tool handler, and through REST `/tools/call` for the tools it actually dispatches (`upstream_servers`, `quarantine_security`); native stdio; the CLI command against a temp `HOME`) with a capturing sink, and assert the **exact set** of lines: `action`, `caller.kind`, `target`, `source`, `origin`, `client.surface`, `request_id` equal to the activity row's where one exists (asserted as two equalities: ingress id = activity row id, and audit id = activity row id when unmasked; for a credential-shaped id the audit line carries the expected masked form and `request_id_masked: true`), no forbidden key, schema-valid. Each driven `GET` is checked against its effect-branch classification: a read-only or named bookkeeping branch writes zero admin lines (and only the permitted storage delta); a mapped `GET` branch (reconcile-on-read, the broker callback, Connect preview's reconcile) asserts its exact effect set and the initiating request's attribution.
3. **No-op, refusal and partial-failure tests**: a no-op body and a refusal before any eligible effect commits (scoped token, 404, a 409 from a precondition checked first) write zero lines; a refusal after an effect committed writes exactly that effect — pinned: the reconcile that finalizes or rolls back a staged rotation before supported-client rotate or Connect answers `409` (`client_bindings.go:307-328`), with its ingress `request_id`; an injected failure after the first of two effects writes exactly the first effect's line (config-to-secret, Connect, security review with blocks saved before a failed promotion).
4. **Count invariant under a saturated bus**: fill the event bus, commit 2,000 effects, assert 2,000 lines (the Spec 107 pattern for `authz`).
5. **Failure semantics**: a sink whose `Write` always fails — every change still succeeds, `WriteFailures()` counts them, doctor reports it; short writes of both kinds (torn JSON; JSON written, newline lost), a full-length write that still returns an error, a short write at the rotation threshold, and a reopen of a file that ends mid-record each leave every file well-delimited and the next record parseable (read back from the files); a builder rejection increments the build-failure counter; an offline command with an unwritable path or a lock held by the daemon warns once on stderr, writes nothing and keeps its exit status; a daemon starting while an offline command holds the instance lock waits for it, and a CLI started while `serve` is loading config takes the daemon path, with file, stdout and disabled sinks alike; watcher fixtures for a pending-field reversal and for a late observation of already-recorded surviving bytes.
6. **Redaction**: an enum-shaped field carrying a non-member string (a secret in `protocol` via MCP patch) is withheld; an `env` key containing `.`, `/` and `~` round-trips through the JSON Pointer, and a key long enough to hit the cap stays a valid pointer; a CLI whose discovered endpoint belongs to another daemon is refused by the nonce check (two daemons, two configs); two configs naming one audit file through a symlink and its target share one lock; a watcher edit interleaved with a commit, and an edit to a key an environment override masks, are each attributed correctly; two long keys that collide after capping keep their original order with `field_masked`; a tenant whose stored email is not a valid address mutates a server and the line omits `user_email`; a registry created with a derived id, edited to a new URL and removed never shows the id; a long valid `X-Request-Id` is kept whole; a credential-shaped one is masked with `request_id_masked: true` and counted by the field-mask counter; classifier table test (every literal path has a literal Go type; every path under `env`, `headers`, `oauth`, `secrets` is `WithheldSecret`; an unknown path is `WithheldValue`); a compile-level test that `Change` has no string/any value constructor; the config fuzz test of PR-3; a test that a `mcp_agt_…` value in a name or `X-Request-Id` is masked and counted; `SanitizerHits()` zero across all door tests.
7. **Schema**: validation runs on the **captured sink output** (after the whole-line sanitizer, so a masked `request_id` containing `*` is validated as emitted), not on `Line.JSON()`. `internal/audit/schema_test.go`'s recursive strictifier, which closes partial `if`/`then` schemas and would make event predicates fail on real lines, is replaced by event-specific exact-key checks; a frozen legacy fixture with a shipper extension key passes the published schema and fails the producer-strict check; `admin_action` examples and forbidden-key rejections; "pre-133 examples still validate"; contract and published copies stay identical (the existing test).

## Deferred implementation design

Eight rounds of spec review kept finding races inside the mechanisms this plan first sketched (locks, commit stages, watcher baselines, sink repair). Those mechanisms are implementation design; the spec fixes their requirements (contract §Rules, §CLI ownership, §Count invariant) and each item below is settled in its PR, with its own cross-review and the fixtures listed. The sketches elsewhere in this plan are starting points, not commitments.

- **D-A — CLI and daemon ownership (PR-1).** Meet contract §CLI ownership 1–6. Known traps from review: `--config` and `--data-dir` are independent (`cmd/mcpproxy/main.go:836-875`); `serve` saves a generated key before opening `config.db` (`main.go:567-594`); a lock beside the config breaks the read-only Compose deployment (`examples/compose-stdio-sidecars/docker-compose.yml:38-46`), so a lock location keyed by canonical config identity in a writable directory, or a read-only mode, is needed; atomic-rename saves replace a symlink alias (`internal/config/loader.go:529-536`); the CLI resolver can reach another instance (`daemon_client.go:72-123`), so the daemon must verify an expected-instance token **on each rerouted mutation**, not only on a status probe (`internal/cliclient/client.go:182-200,859-867`); the shared CLI loader can create a default config (`cmd/mcpproxy/cli_config.go:34-54`). Fixtures: two daemons with two configs and a misleading endpoint; daemon replaced between probe and write; read-only config directory; first-run CLI/daemon race; fresh home with a read-only command.
- **D-B — Commit stages and attribution of file bytes (PR-1 for the result type, PR-3 for the writers).** Report storage, disk and publication results of one commit separately and immutably, also on error (`noDisk` reloads and restart adoption persist rows with no disk delta, `commit.go:920-944,1001-1006`, `lifecycle.go:2310-2318,2619-2627`); one writer preimage serves merge, compensation and attribution, so an external edit already present in it (possibly override-masked, `internal/config/process_overrides.go:520-549`) is credited to `none` and the writer's own delta to its caller; restart adoption of one server advances the accounting for that server only. Fixtures: storage commit then publication failure; API save over an un-reloaded external edit; restart adoption beside an edit to another server.
- **D-C — Sink boundaries (PR-1).** Repair a torn tail in the affected file before rotation or another record; refuse to append while a boundary cannot be established; stdout best-effort. Fixtures: torn JSON, lost newline, full-length errored write, each at the rotation threshold and on reopen.
- **D-D — Bundle commit points (PR-2).** Durable pin/watermark transitions versus serving-corpus publication (`tpa_bundle_runtime.go:467-506,586-598`); ordered consumption of commit results by refresh and reload. Fixtures: fallback with a failed state save; refresh while a commit's post-work is paused.
- **D-E — Cancellation capture (PR-1).** Approved-authorization cancellations reported from the request-store lock on every exit of revoke, legacy client-token revoke, Forget and switch-off. Fixtures: cancellation-only error; legacy revoke with no stored grant; key-only route at zero cancellations.

## Open questions (left to review)

- **Q1**: `auth tokens decrypt` (offline) changes how upstream OAuth tokens are stored at rest. Exempt as maintenance, or `config.update` with `field: oauth_token_storage`? The contract exempts it; a reviewer may prefer a line.
- **Q2**: Recording refused administrative attempts (spec A4) — a separate `admin_authz` event, or `outcome: denied` on `admin_action`? Out of scope here; named so it is not lost.
- **Q3**: Upstream OAuth login/logout (`POST /servers/{id}/login|logout`) is exempt as "not an access rule". If reviewers count an upstream credential as a rule, it is a P1-shaped `secret.*`-like action.
- **Q5**: Pre-existing servers are withheld on audit lines until renamed or confirmed (spec A7). If that hurts readability too much, the alternative is a one-time startup classification that marks as `explicit` every legacy server whose name differs from the sanitized suggestion of its current inputs, accepting a residual exposure for imports edited before upgrade.
- **Q4**: `request_id` on REST is the caller's `X-Request-Id` when sent, so it is a join key, not a uniqueness guarantee. A separate proxy-minted id for admin requests would change existing REST correlation; left as is unless review asks.

## Complexity Tracking

| Violation | Why needed | Simpler alternative rejected because |
|---|---|---|
| Synchronous write outside the event bus | FR-018: the record must survive bus saturation | Consuming activity events from the bus drops them on overflow (inventory.md §0.2) |
| `CommitResult` committed delta | FR-013: the line must describe what persisted; today several writers diff the candidate or discard the result | Diffing at each door duplicates the logic and misses admission rewrites and restart-only reloads |
| `ctx` variants of the tool-approval funnels | FR-008: tool approvals must name the caller, and today the funnel receives only the string `"api"`/`"mcp"` | Passing the actor as a string would duplicate the caller derivation and lose `token_prefix`/`profile_pin` |
