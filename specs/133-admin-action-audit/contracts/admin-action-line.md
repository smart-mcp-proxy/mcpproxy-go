# `admin_action` line — contract (schema_version 1, additive)

Binding for PR-1..PR-5 (plan.md). The machine-readable form lands in PR-1 in `docs/schemas/audit-line-v1.schema.json` and its identical contract copy `specs/107-server-edition-sso-hardening/contracts/audit-line.schema.json` (both loaded by `internal/audit/schema_test.go`), same `$id`. The schema change is more than one `allOf` block:

- the **root** enums widen: `event` gains `admin_action`; `caller.kind` gains `none` and `cli_offline`;
- every constraint on a new key (`action`, `target`, `changes`, `changes_truncated`, `changes_count`, `request_id_masked`, `trigger`, `policy`, `client.surface`, `caller.token_name_withheld`, and every key inside `target` and `changes`) lives **inside** the `if event == admin_action` block, together with the required set, the `iff` rules and the forbidden keys. None is declared at the root: a root-level type for `target` or a shared enum for `client.surface` would reject an old `authz` line that carries a shipper-added `target` or `client.surface` extension key, which v1 accepts today (`docs/schemas/audit-line-v1.schema.json:7-9,64-71`). `outcome` stays the shared root property `tool_call` already uses, and the `admin_action` block restricts it to `success`;
- the **published** schema stays consumer-tolerant: it does not forbid the new keys on the other three kinds (the old schema tolerates extension keys at the root and in `client`, `docs/schemas/audit-line-v1.schema.json:7,64-71`, and narrowing that would itself be a breaking change). Exclusivity is enforced only by `schema_test.go`'s producer-strict check, which becomes event-aware (it closes `properties` per event, so the proxy can never emit an `admin_action` key on another kind);
- compatibility, case by case: an old shipped line validates under the new schema unchanged (tested over every pre-133 example **and** over old lines carrying colliding extension keys such as `target` or `client.surface`); a cached old published validator accepts new keys on old kinds but rejects `admin_action` lines (closed `event` and `caller.kind` enums); a producer-strict copy of the old schema rejects both — it was never meant for consumers;
- the schema's own `description` drops the claim that a strict consumer holding v1 keeps validating after any additive change.

## Unit of record

A line records one **committed effect**: one durable transition of one target (a token row written, a server entry committed, an approval record saved, a keyring entry stored), observed at the place it persisted. It is **not** tied to the HTTP or MCP response:

- a request that commits two effects and then fails writes the line(s) for what persisted (config-to-secret that stores the keyring entry and then fails the config patch: one `secret.set`, no `server.update`);
- a request that reports success but commits nothing writes nothing (a no-op toggle, `EnableServerCtx` on an already-enabled server — the existing activity row for that case invents `previous = !enabled`, `lifecycle.go:2437`; the line must not copy that);
- a few administrative decisions change in-memory state that governs access, not stored state; they are effects at their decision point: `login.approve` / `login.deny` (the pending authorization, `oauth_login_consent.go:843-937` — an approval later abandoned by the client keeps its line), `login.cancel`, and `jwt.issue` (stateless signing, server edition);
- tool, prompt and skill decisions are grouped: one line per **batch key** = (request or automatic pass) × server × `target.kind` × `action` × `policy`. A security review that approves 10 tools and blocks 2 on one server writes two **tool-decision** lines (`tool.approve`, `tool.block`), in addition to the baseline and server lines of the effects that commit (§P2 gives the exact set).

## Rules that bind every hook

These rules are normative for PR-1..PR-5. The action tables below are the floor, not the ceiling: an implementing PR that finds a committed effect the tables do not name adds an `action` (or a registry exemption with a reason) in the same PR, with an exact-effect fixture.

1. **Observe the backend's result, once.** A hook reports what the storage transaction, keyring backend or config writer reports it changed — the changed identities, the before/after, a no-op flag — never the success of the API call around it. A keyring `Set` that lands before the listing registry update fails is a `secret.set` even though the call returns an error (`internal/secret/keyring_provider.go:139-159,237-252`); a delete of an already-absent entry is not a `secret.delete`; a backend call that completes after its timeout wrapper gave up is recorded **when it completes, after the response** — one of the two exceptions to "before the request returns" (spec FR-013; the other is rule 1a). The hook therefore sits in the backend completion path, not at the caller (the wrapper discards the late result today). The daemon records late completions while its sink is open; one that completes after shutdown closed the sink is lost (counted as a documented gap). An offline command waits for its backend calls to finish, holding its locks, up to the wrapper's own timeout once more; if a call is still outstanding it exits with a warning that the outcome is unknown and writes no line for it. Storage interfaces that today return a count or nothing (user disable's token revocation, the sharing updater, permanent token delete) return the changed identities.
1a. **Detached work keeps its initiating request.** An effect committed by work a request started and did not wait for is written at its own commit (or batch) boundary — before or after the response, whichever comes first; nothing orders them — and carries the initiating request's `source`, `origin`, `client` and `request_id`; `caller`/`trigger`/`policy` are those of the decider (an automatic approval or hold inside it is `internal`). The handle that starts the work captures that metadata once and the work carries it, so a later wakeup cannot re-attribute it. Named cases: a scan job's settlement (§Exempt, scan row); the discovery pass a restart or reconnect starts (`restartConnectWorker`, `lifecycle.go:2756-2761,2810-2814`) and the approval transitions it saves (`tool.approve` automatic, `tool.hold`, `tool_quarantine.go:1942-1963`); a prompt or skill refresh run because a request's config commit reloaded (`server.go:1017-1029` → `RefreshPrompts`, `prompt_quarantine.go:275-342`) — the reload's commit result names the request. Work with no initiating request — scheduled passes, a file-edit reload (`none`), startup — writes background lines with no `request_id`. Pinned (with the worker held until the response is sent): a restart that returns and then produces a `tool.hold` carrying the restart's `request_id`, and a `POST /config/apply` whose reload-triggered prompt refresh writes `prompt.hold` with the apply's `request_id`.
2. **Compensation is its own effect — except inside one writer.** (Stage-level mechanics — storage, disk and publication results of one commit, `noDisk` reloads and restart adoption that persist rows with no disk delta, `commit.go:920-944,1001-1006`, `lifecycle.go:2310-2318,2619-2627` — are deferred item **D-B**: the commit reports each stage's result immutably, also on error, and an effect is recorded at the stage where it became durable or, for in-memory effects, visible.) Across steps that each persist on their own (Connect, security review, profile repin), an undo, restore or rollback that persists writes its own line, and a compensation that fails leaves the original effect's line standing. Inside one config commit, a staging write that the same commit successfully compensates (disk written, storage failed, disk restored, `internal/runtime/commit.go:893-936`) is not an effect: nothing persisted net, no line. If the compensation fails, the disk writer reports the exact bytes it persisted (`writeCommitDisk` / `SaveConfigWithEdits` can write a plan that differs from both the desired and the published snapshot, `commit.go:1049-1068`, `internal/config/loader.go:547-572`) and lines are written for that surviving delta; the self-write marker is kept so the watcher does not count the same bytes again (`config_watcher.go:334-349`).
3. **Metadata from the ingress, identity from the decider.** `source`, `origin`, `request_id` and `client` come from the request that actually entered the proxy. One precedence rule for `request_id`: **reuse the id already in the context; mint one only at an ingress that has none** (native MCP, the public OAuth mux, stdio), and use that one id for the wrapper activity row, the mutation and the line. A REST `/tools/call` that dispatches `upstream_servers` or `quarantine_security` is `source: api` with the REST request id (`internal/httpapi/server.go:6541-6552`, `internal/server/mcp.go:7841-7847`); the built-in wrapper must not overwrite it. `caller`, `trigger` and `policy` come from whoever decided: an `internal` effect caused inside a request (reconcile-on-read) replaces only `caller`/`trigger`/`policy` and keeps the request's metadata.
4. **Bookkeeping is not a decision.** Transient status the proxy maintains for itself — a scanner image `pulling`/`error`, a skill marked `unusable` by integrity checks, a scan job state, a cache invalidation — writes no line. Decisions that change who can call what do. The registry records each bookkeeping exemption by name.
5. **One owner per effect** (see [CLI ownership](#cli-ownership)).

## Caller

The trusted request context is normative: `caller` is built by the same derivation as `authz` lines (`auditCallerFromContext`, `internal/server/audit_funnel.go:231-287`: AuthContext type first, then the anonymous bit, then the connection source). The activity `actor_kind` string is **not** an input; the table shows how the two vocabularies line up so one query can join them.

| Request context | `caller.kind` | Identity keys (omitted when empty) |
|---|---|---|
| API key over TCP | `api_key` | — |
| API key over the tray socket / named pipe | `socket` | — |
| Native stdio transport (administrator, no listener) | `stdio` | — |
| `mcp_agt_` / `mcp_cli_` token, or a Spec 132 `mcp_oat_` browser login (both `AuthTypeAgent`) | `agent_token` | `token_name`, `token_prefix`, `profile_pin`; when owned, `user_id`, `role` and `provider` together, `user_email` only when valid (below) |
| Administrator session (cookie or bearer JWT, server edition) | `session_admin` | `user_id`, `user_email`, `role: admin`, `provider` |
| Tenant session (server edition) | `session_user` | `user_id`, `user_email`, `role: user`, `provider`. The kind follows the request's role, not the route: `/user/*` admits administrators too, who are `session_admin` there (`user_handlers.go:1745-1759`) |
| SSO callback provisioning a user or changing their groups (server edition; public route, no session yet, `setup.go:275-279`) | `session_user` / `session_admin` by the role derived at that callback | an explicit caller override built from the **verified** identity the callback just committed: `user_id`, `role`, `provider` of the stored record, and `user_email` only when it is a valid address (the store requires only a non-empty string, `users/models.go:53-68`, the schema says `format: email`), never from the empty AuthContext, which the shared helper would call `anonymous` |
| Public OAuth registration (`POST /oauth/register`) | `anonymous` | an explicit override: there is no credential by design |
| `require_mcp_auth: false`, no credential | `anonymous` | — |
| Offline CLI, core stopped | `cli_offline` (new) | — |
| No request; the proxy decided (policy, admission, startup reconcile, schedule) | `internal` | — |
| No request; the proxy observed a change it did not make (config file edit) | `none` (new) | — |

Activity `actor_kind` alignment: `api_key`→`api_key`; `socket`→`socket` (the activity layer also says `socket` for an agent token on the tray socket, `activity_actor.go:42-44`; the audit derivation keeps `agent_token`, which is more specific); `agent_token`/`oauth`→`agent_token`; `cookie`/`bearer_jwt`→`session_admin` or `session_user` by role; `anonymous`→`anonymous`; `cli_offline`→`cli_offline`; `system`→`internal`; no actor→`none` or `internal`. Native stdio has no activity spelling of its own (activity falls back to `api_key`); the audit line says `stdio`.

**Precedence** (one rule): an explicit override on the record (`Decider` for background and request-caused internal effects, which always carries its `trigger` and, where required, `policy`; the verified-identity override of the SSO callback; the `anonymous` override of public registration) wins; otherwise the caller comes from the request's AuthContext by the `authz` derivation's **credential mapping** — without its dispatch-specific `SourceInternal` shortcut (`audit_funnel.go:220-239`), so an admin line is `internal` only through an explicit `Decider` and never without a trigger; an admin funnel reached with neither is a bug the door table test fails on — the shared helper's nil-means-`anonymous` default is never reached on an `admin_action` path.

On every `admin_action` session or owned-agent caller, `user_email` is emitted only when, after masking and capping, it is a valid address (the store accepts any non-empty string, `users/models.go:53-68`, `users/store.go:512-519`); otherwise it is omitted and `user_id`/`role`/`provider` stay. The schema's owned-agent all-or-none identity rule is scoped to `authz`/`tool_call` (old lines are only those kinds, so nothing they could carry is newly rejected) and the `admin_action` block states its own rule: `user_id` ⇒ `role` and `provider`; `user_email` optional.

`session_user` is already legal on `auth_event`; this feature makes it legal on `admin_action` too (it stays forbidden on `authz`/`tool_call`). `none` and `cli_offline` are legal only on `admin_action`. A background line (`internal`, `none`, `cli_offline`) carries no identity key.

**Derived labels.** Some labels are derived from text that may be private. They are withheld — `name_withheld: true` plus `ref` in every position that would repeat them: `target.name`, `target.server` of tool/prompt/skill batches (`server_withheld: true` plus `server_ref`), a caller's `token_name`, JSON Pointer segments and name-list diffs — unless an administrator demonstrably chose them. A ref is never spelled where a name could be: in a **name-list diff** (`added`/`removed`, §Changes) each member is either a literal string or exactly the object `{"ref": "<ref>"}` for a withheld member — counted in that side's `added_count`/`removed_count` like any other — so the two cannot collide; in a **JSON Pointer** the path stops at the parent collection (`/mcpServers`, `/profiles`) and the entry carries `segment_ref: <ref>` with `field_masked: true` (pinned: a literal server name spelled like a ref). The rule applies to:

- **Server names (PR-1).** Every server carries a **persisted, sticky name origin** (`explicit` \| `derived` \| `unknown`) and a `ref`, stored by the proxy beside the entry (keyed by server name, kept across restarts, moved by a rename, deleted with the server), not recomputed from the current config: import sanitizes the suggestion before storing it (`internal/configimport/import.go:85-128`, `mapper.go:12-18`) and a later PATCH can replace `url`, `command` or `args` without renaming (`internal/httpapi/server.go:2824-2877`), so a comparison with the current inputs is not reliable. Paste import of a URL or command whose name was not changed by the administrator writes `derived` (`internal/configimport/url_command.go:20-127`, `internal/httpapi/import.go:608-618`); a door where the administrator typed the name writes `explicit`; edits carry the origin unchanged, and only an explicit rename sets `explicit`. A server that existed before this feature is `unknown`, and `unknown` is withheld like `derived` — the conservative error; the admin-only server detail shows the `ref`, so an operator can resolve it, and renaming the server (or confirming its name through an explicit-name save) makes it `explicit` (assumption A7). The rule applies to **every** position that names a server: `target.name`, `target.server` of tool/prompt/skill batches, server-edition `user_server.name` and `user_credential.server`, JSON Pointer segments and name-list diffs — each with the same `ref`. It ships in PR-1 with the line builder, so no slice can emit a derived server name, whatever the merge order. Fixtures: sanitized URL import and command import → endpoint change by PATCH → tool approval → restart → removal, the same `ref` throughout; a pre-existing server is withheld; a rename makes it `explicit`.
- **Registry-added server names (PR-3).** A name taken from a registry entry without a name override (`add_from_registry.go:93-134,194-213`) is recorded only when the entry was fetched from a compiled-in default registry whose **effective listing source** is unchanged from the default — the `servers_url` the fetcher actually used (`internal/registries/official.go:80-87`), not only `url`, and an unauthenticated fetch — (published catalog data, residual-exposure list). When public provenance cannot be established from the entry's recorded fetch source, the name is withheld; fixture: a config override that keeps the `official` id, provenance and `url` and changes only `servers_url`. A private, edited or unknown source (`docs/registries.md:103-109`; an id can be overridden while keeping `official` provenance, `internal/registries/registry_data.go:19-58`) is withheld. Until PR-3 ships, PR-1's builder withholds every registry-added name it cannot classify.
- **Registry ids (PR-3)** derived from the (withheld) URL — see the `registry` row.
- **Client ids (PR-1).** A browser-login client id the consent page suggested from the registration's caller-supplied `ReportedName` and the administrator accepted unchanged (`oauth_login_consent.go:429-431,546-592`, `frontend/src/views/AuthorizeRequest.vue:228-295`, persisted on the grant at exchange, `oauth_login_service.go:552-563`) — slugification can strip the prefix a mask would recognise. The origin is a property of the **client**, keyed by the trusted `AuthContext.ClientID`, not of the credential kind: the same client can later hold an API key whose record name is `client-<id>` (`storage/client_credentials.go:156-168`, `auth/agent_token.go:337-348`, `oauth_login_clients_test.go:237-252`), and that name is withheld as well. A client whose origin is not recorded — every client registered before this feature, since grants and bindings do not keep it (`storage/oauth_login.go:110-145`) — is **unknown** and withheld the same way in every position (`target.name` of `client`, `target.client_id` of `login`, and a `caller.token_name` derived from the id), until an administrator renames or re-confirms it. Fixtures: an `mcp_oat_` and an `mcp_cli_` caller of the same derived client both omit the name and carry the same `caller.ref`; a pre-upgrade grant and API-key pair are withheld on revoke.

`ref` is an opaque random identifier. A client's is assigned when the pending authorization first suggests the derived id and travels with it into the exchange, so `login.approve`, `login.cancel` and later client lines join; a server's, a registry's or a legacy client's is assigned and stored the first time a line names it.

On `admin_action` lines a withheld caller is `token_name_withheld: true` and `caller.ref`. The v1 schema requires `token_name` for every `agent_token` caller (`docs/schemas/audit-line-v1.schema.json:48-49`), and a conditional cannot relax a root requirement, so — as for the owned-agent email rule — that requirement is scoped to `authz`/`tool_call` (old lines are only those kinds), and the `admin_action` block defines two mutually exclusive agent shapes: `token_prefix` with `token_name`, or `token_prefix` with `token_name_withheld: true` and `ref`. Both are validated on captured sink output, and the legacy validation is tested unchanged.

Every string goes through `maskCredential` and its length cap. Before that, the builder withholds any **label** that contains a private-key block header (`-----BEGIN … PRIVATE KEY-----`, `-----BEGIN PGP PRIVATE KEY BLOCK-----`; the repository already notes that masking a header leaves the body, `internal/security/mask.go:110-117`): no byte of it — header or body — is capped, masked or serialized, and its position decides the shape: a **target identity name** (`server`, `agent_token`, `user_server`, `profile`, `registry`, `client`) becomes `name_withheld: true` beside that target's `ref`, and a batch or credential's `server` becomes `server_withheld: true` beside `server_ref` (every such kind carries one; `name` and `name_withheld` are mutually exclusive, also for `agent_token`); a **batch member** of `target.names` is dropped from the list, still counted in `count`, and the line sets `names_withheld: <n>`; a **JSON Pointer segment** (an `env` or `headers` key) is replaced by the fixed parent path (`/env`, `/headers`) with `field_masked: true` and the value withheld as for any secret field; an **optional metadata** string (`client.name`, `client.version`, a profile description) is omitted. A label that fits no position is a rejected record (counted), never serialized. The schema validates every one of these shapes on captured output. A tenant token name is the reachable case (the create handler only trims it, `user_handlers.go:1502-1512`). Fixture: a PEM block as a token name, a server env key, an upstream tool name in a batch, a client name and an `X-Request-Id`; the captured sink output contains none of its body bytes (an `X-Request-Id` cannot carry one: its pattern admits no `-----` header with spaces, and a body-only id is a shapeless label, residual exposure). PR-1 extends the fixed credential patterns (`internal/audit/redact.go:38`) with the proxy's own token shapes — `mcp_(agt|cli|oat|ort)_[A-Za-z0-9_-]{16,}`, long enough that a display `token_prefix` (8–16 characters in all) never matches — which today are not on the list; that change also protects `authz`/`tool_call` lines and the whole-line sanitizer pass, so a token value pasted into a name or an `X-Request-Id` is masked and counted. Masking is a pattern match and catches only recognisable shapes: a generated 64-hex API key pasted into a name or an `X-Request-Id` is not masked (`internal/config/config.go:1987-1998`). The guarantee is therefore scoped: **values** never enter a line (they have no path in); **labels** are recorded as chosen, pattern-masked. The label sources, by who controls them: administrator-chosen names (server, token, profile, registry, field paths under `env`/`headers`; keyring names are never on the line, see `secret`); caller-chosen strings (`request_id` from `X-Request-Id`, `client.name`/`client.version`; a public OAuth client's registration metadata is never on the line, only its assigned `client_id`); upstream-controlled names (tool, prompt and skill names in `target.names`). The audit-log page lists these sources and states the residual exposure: a secret with no recognisable shape placed into any of them reaches the audit file, as it already reaches the activity log and `authz` lines (which carry the same `tool`, `client` and `request_id` values today).

## Changes

`{field, before?, after?, withheld?}` — either a literal (`before`/`after`, a side that does not exist is omitted) or `withheld: "secret" | "value"` with no value and **no hash**.

- `field` is a **JSON Pointer** (RFC 6901: `/enabled`, `/env/GITHUB_TOKEN`, `/profiles/dev/tier`), an injective encoding (`~0`, `~1` escapes), so a key containing `.` or `/` cannot be read as nesting. Paths come from a fixed schema, never from a value. A dynamic segment is allowed only where the classifier says so — map keys under `env`/`headers`, server names, profile names. Classification, diffing and the sort order (by the original structured path) all happen **before** any segment is masked or capped; a masked or capped segment sets `field_masked: true` on that entry, and entries whose rendered pointers collide keep their original order. (Examples elsewhere in this spec write paths in dotted form for readability.) Below an **opaque** block that preserves arbitrary keys (the personal build keeps `server_edition` as raw JSON, `internal/config/server_edition_config_stub.go:35-56`) nothing is descended into: the change is reported at the nearest fixed parent (`{field: server_edition, withheld: "value"}`).
- **Literal** (value verbatim) — a field is literal only when the classifier table names it **and** the committed value converts to that field's closed wire set; a value outside the set (for instance an arbitrary string in `protocol`, which is a `string` in config, `internal/config/config.go:748`, and is not enum-checked on every write path, `internal/config/merge.go:214-219`) is `withheld: "value"`. Literal kinds: `bool`; a closed enum type (`protocol`, `trust_mode`, profile `mode`, tier caps, permission tiers); a bounded integer (rate limits, `max_*`, `*_days`, the **port** of `listen` — the host part is free text); a timestamp (`expires_at`); a display prefix (`token_prefix`, already shown in every token list); a count (`logins` removed by `client.forget`); a list of server or profile **names** (`allowed_servers`, profile server lists), capped like `target.names`; a **single profile name** on exactly two paths, `/anonymous_profile` and a rename's `/name` — `before` validated against the pre-commit profile set and `after` against the post-commit set, masked and capped like every label (`field_masked: true` when either changes it); when either populated side names no profile on its own snapshot (a hand-edited dangling selector is legal with a warning, `internal/config/profiles.go:463-474`) the **whole entry** is `{field, withheld: "value"}` — there is no per-side withholding. Pinned: dangling → valid and valid → dangling.
- **Name lists** contain only names that resolve: each `before` entry against the pre-commit set of that entity kind, each `after` entry against the post-commit set (profile validation accepts unknown `servers` and `switchable_to` entries with a warning, `internal/config/profiles.go:389-433`, so an entry can be arbitrary text). An unresolved entry is never rendered — it is counted in `added_count`/`removed_count` and sets `unresolved: true` on the entry; documented sentinels (`*` in `allowed_servers` and server lists) are an explicit allowlist. Resolved server names then follow the derived-server rule (a withheld member is the `{"ref": "<ref>"}` object of §Target, Derived labels). They are reported as a diff, not as two sides: `{field, added: [...], removed: [...], added_count, removed_count, truncated?}` — so a list of 66 names that gains one shows exactly the one added name, and a capped side says how many it holds.
- Tool and skill approval hashes are **not** literal: they cover upstream-controlled descriptions, schemas and defaults (`internal/runtime/tool_quarantine.go:47-66`) and skill files (`internal/skills/hash.go:11-66`), which nothing proves secret-free. A `tool.approve` line names the tools and says nothing about their hashes; the activity row keeps them.
- **Withheld `secret`** — `env.*`, `headers.*`, `api_key`, `oauth.*` secrets, `oauth_token_encryption_key`, keyring values, and any value that is or resolves from `${env:}`, `${file:}`, `${keyring:}`.
- **Withheld `value`** — everything else: `url`, `command`, `args`, `working_dir`, the host of `listen`, descriptions, schemas, rule patterns, registry URLs. They can carry a credential with no recognisable shape (a positional password in `args`), so they get neither the value nor a fingerprint; the line says the field changed, and the activity row (admin-only, redacted best-effort) keeps the detail.
- The classifier is one table keyed by field path; an unknown path is `withheld: "value"`, a path under a secret-class prefix is `withheld: "secret"`.

## Size

A serialized line is at most **16 KiB**, not counting the newline the sink appends. Every name and label is processed in one order: provenance and the private-key check on the **original** string, then `maskCredential` on the original string, then the cap at 64 characters (the mask's own 256-rune cap is the ceiling for other strings), then escaping and serialization — so a credential that straddles the cap is masked before it is cut (`internal/audit/redact.go:58-77`; pinned). A field path is shortened **per segment, before escaping** (each segment to 64 characters), so a rendered JSON Pointer is never cut mid-escape and is always valid; if the rendered pointer still exceeds 256 characters, the entry is reported at its fixed parent path with `field_masked: true`. All ordering uses the original structured path. Then, in order, until the line fits: `target.names` and name-list diffs to 64 entries each; `changes` to 128 entries; drop `changes` entries from the end; drop `target.names` (the key is then absent, not `[]`, and `truncated: true`). `truncated` / `changes_truncated` are set whenever anything was dropped; `target.count` / `changes_count` always report the full set. With every list dropped, a line is bounded by its fixed keys and capped labels, well under the budget. The test asserts the final serialized byte length.

## CLI ownership

Normative requirements; the mechanism is deferred design item **D-A** in plan.md, settled and cross-reviewed in PR-1 (rounds 3–8 of the spec review showed that every concrete lock layout has deployment-specific failure modes, so the spec fixes what must hold and the PR proves its mechanism against the fixtures named there).

1. **One owner per effect.** Every effect a CLI command causes has exactly one recorder: the daemon (the change went through it, recorded with the CLI's caller) or the CLI itself (`cli_offline`).
2. **No unaudited edit beside a running daemon.** When a daemon serves the config a CLI command would change, the change goes through **that** daemon — verified to be the one serving that config, and verified by the daemon on the mutation itself, not only by a prior probe — or the command does not mutate and exits non-zero. Socket reachability alone is not proof (`cmd/mcpproxy/daemon_client.go:72-133` can pick another instance's endpoint).
3. **Ownership covers the whole read-modify-write and the audit attempt**, including first-run creation: CLI config loading never creates a config as a side effect (today the shared loader can, `cmd/mcpproxy/cli_config.go:34-54`, `internal/config/loader.go:185-208`).
4. **Supported deployments keep working**: a read-only config directory with the API key supplied separately (`examples/compose-stdio-sidecars/docker-compose.yml:38-46`) still starts and reloads; the proxy then refuses its own config writes as it does today.
5. **The keyring has no observer**, so the process that performs a keyring write records it; with a daemon serving the config, keyring commands go through it so the line lands in its file.
6. **One writer per audit file**: two processes never append to or rotate one audit file at once, whatever path aliases they use; aliases the mechanism cannot collapse are documented as unsupported.
7. **The watcher records only edits no proxy process made**, as `caller.kind: none`, `trigger: config_file`, one line per changed target per observed delta (it debounces, `config_watcher.go:112-136`). Bytes a proxy writer produced — including what a failed compensation left behind, and an external edit already present in a writer's preimage — are attributed once, to the right party (deferred item **D-B**).

## Count invariant

Three counts, kept apart (round-6 finding):

- **Obligation** — one record per eligible committed effect, in batch-key units for `tool`/`prompt`/`skill` targets and one per signed JWT for `jwt.issue`, while an enabled sink exists. Holds with the event bus saturated.
- **Attempts** — every obligation produces exactly one write attempt, unless the builder rejects the line (counted by the build-failure counter), the effect completes after the sink closed at shutdown (lost; logged once), or an offline command stopped waiting on a backend call (rule 1: warned on stderr, no attempt). A crash between commit and attempt loses that line (the documented crash window).
- **Records** (informative) — parseable lines in the file. Counters (`WriteFailures`, build failures, mask hits, sanitizer hits) count attempts and events, not records: an errored attempt may still leave a complete line, so records are verified by reading the file back, never by arithmetic over the counters. The sink keeps every file well-delimited — a torn tail is repaired in the affected file before it can rotate or receive another record, and if the boundary cannot be established the sink appends nothing until it can (deferred item **D-C**; stdout has no file to repair and is documented as best-effort per line). Shippers skip malformed lines (`jq -R 'fromjson? // empty'`).
