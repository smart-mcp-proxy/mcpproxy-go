# `admin_action` line — contract (schema_version 1, additive)

Binding for PR-1..PR-5 (plan.md). The machine-readable form lands in PR-1 in `docs/schemas/audit-line-v1.schema.json` and its identical contract copy `specs/107-server-edition-sso-hardening/contracts/audit-line.schema.json` (both loaded by `internal/audit/schema_test.go`), same `$id`. The schema change is more than one `allOf` block:

- the **root** enums widen: `event` gains `admin_action`; `caller.kind` gains `none` and `cli_offline`;
- every constraint on a new key (`action`, `target`, `changes`, `changes_truncated`, `changes_count`, `request_id_masked`, `trigger`, `policy`, `client.surface`) lives **inside** the `if event == admin_action` block, together with the required set, the `iff` rules and the forbidden keys. None is declared at the root: a root-level type for `target` or a shared enum for `client.surface` would reject an old `authz` line that carries a shipper-added `target` or `client.surface` extension key, which v1 accepts today (`docs/schemas/audit-line-v1.schema.json:7-9,64-71`). `outcome` stays the shared root property `tool_call` already uses, and the `admin_action` block restricts it to `success`;
- the **published** schema stays consumer-tolerant: it does not forbid the new keys on the other three kinds (the old schema tolerates extension keys at the root and in `client`, `docs/schemas/audit-line-v1.schema.json:7,64-71`, and narrowing that would itself be a breaking change). Exclusivity is enforced only by `schema_test.go`'s producer-strict check, which becomes event-aware (it closes `properties` per event, so the proxy can never emit an `admin_action` key on another kind);
- compatibility, case by case: an old shipped line validates under the new schema unchanged (tested over every pre-133 example **and** over old lines carrying colliding extension keys such as `target` or `client.surface`); a cached old published validator accepts new keys on old kinds but rejects `admin_action` lines (closed `event` and `caller.kind` enums); a producer-strict copy of the old schema rejects both — it was never meant for consumers;
- the schema's own `description` drops the claim that a strict consumer holding v1 keeps validating after any additive change.

## Unit of record

A line records one **committed effect**: one durable transition of one target (a token row written, a server entry committed, an approval record saved, a keyring entry stored), observed at the place it persisted. It is **not** tied to the HTTP or MCP response:

- a request that commits two effects and then fails writes the line(s) for what persisted (config-to-secret that stores the keyring entry and then fails the config patch: one `secret.set`, no `server.update`);
- a request that reports success but commits nothing writes nothing (a no-op toggle, `EnableServerCtx` on an already-enabled server — the existing activity row for that case invents `previous = !enabled`, `lifecycle.go:2437`; the line must not copy that);
- a few administrative decisions change in-memory state that governs access, not stored state; they are effects at their decision point: `login.approve` / `login.deny` (the pending authorization, `oauth_login_consent.go:843-937` — an approval later abandoned by the client keeps its line), `profile.activate` (the server-wide selector, `internal/httpapi/profiles.go:145-160`, only when it changed), and `jwt.issue` (stateless signing, server edition);
- tool, prompt and skill decisions are grouped: one line per **batch key** = (request or automatic pass) × server × `target.kind` × `action` × `policy`. A security review that approves 10 tools and blocks 2 on one server writes two lines (`tool.approve`, `tool.block`).

## Rules that bind every hook

These rules are normative for PR-1..PR-5. The action tables below are the floor, not the ceiling: an implementing PR that finds a committed effect the tables do not name adds an `action` (or a registry exemption with a reason) in the same PR, with an exact-effect fixture.

1. **Observe the backend's result, once.** A hook reports what the storage transaction, keyring backend or config writer reports it changed — the changed identities, the before/after, a no-op flag — never the success of the API call around it. A keyring `Set` that lands before the listing registry update fails is a `secret.set` even though the call returns an error (`internal/secret/keyring_provider.go:139-159,237-252`); a delete of an already-absent entry is not a `secret.delete`; a backend call that completes after its timeout wrapper gave up is recorded **when it completes, after the response** — the one exception to "before the request returns" (spec FR-013). The hook therefore sits in the backend completion path, not at the caller (the wrapper discards the late result today). The daemon records late completions while its sink is open; one that completes after shutdown closed the sink is lost (counted as a documented gap). An offline command waits for its backend calls to finish, holding its locks, up to the wrapper's own timeout once more; if a call is still outstanding it exits with a warning that the outcome is unknown and writes no line for it. Storage interfaces that today return a count or nothing (user disable's token revocation, the sharing updater, permanent token delete) return the changed identities.
2. **Compensation is its own effect — except inside one writer.** Across steps that each persist on their own (Connect, security review, profile repin), an undo, restore or rollback that persists writes its own line, and a compensation that fails leaves the original effect's line standing. Inside one config commit, a staging write that the same commit successfully compensates (disk written, storage failed, disk restored, `internal/runtime/commit.go:893-936`) is not an effect: nothing persisted net, no line. If the compensation fails, the disk writer reports the exact bytes it persisted (`writeCommitDisk` / `SaveConfigWithEdits` can write a plan that differs from both the desired and the published snapshot, `commit.go:1049-1068`, `internal/config/loader.go:547-572`) and lines are written for that surviving delta; the self-write marker is kept so the watcher does not count the same bytes again (`config_watcher.go:334-349`).
3. **Metadata from the ingress, identity from the decider.** `source`, `origin`, `request_id` and `client` come from the request that actually entered the proxy. One precedence rule for `request_id`: **reuse the id already in the context; mint one only at an ingress that has none** (native MCP, the public OAuth mux, stdio), and use that one id for the wrapper activity row, the mutation and the line. A REST `/tools/call` that dispatches `upstream_servers` or `quarantine_security` is `source: api` with the REST request id (`internal/httpapi/server.go:6541-6552`, `internal/server/mcp.go:7841-7847`); the built-in wrapper must not overwrite it. `caller`, `trigger` and `policy` come from whoever decided: an `internal` effect caused inside a request (reconcile-on-read) replaces only `caller`/`trigger`/`policy` and keeps the request's metadata.
4. **Bookkeeping is not a decision.** Transient status the proxy maintains for itself — a scanner image `pulling`/`error`, a skill marked `unusable` by integrity checks, a scan job state, a cache invalidation — writes no line. Decisions that change who can call what do. The registry records each bookkeeping exemption by name.
5. **One owner per effect** (see [CLI ownership](#cli-ownership)).

## Caller

The trusted request context is normative: `caller` is built by the same derivation as `authz` lines (`auditCallerFromContext`, `internal/server/audit_funnel.go:231-287`: AuthContext type first, then the anonymous bit, then the connection source). The activity `actor_kind` string is **not** an input; the table shows how the two vocabularies line up so one query can join them.

| Request context | `caller.kind` | Identity keys (omitted when empty) |
|---|---|---|
| API key over TCP | `api_key` | — |
| API key over the tray socket / named pipe | `socket` | — |
| Native stdio transport (administrator, no listener) | `stdio` | — |
| `mcp_agt_` / `mcp_cli_` token, or a Spec 132 `mcp_oat_` browser login (both `AuthTypeAgent`) | `agent_token` | `token_name`, `token_prefix`, `profile_pin`; owner `user_id`/`user_email`/`role`/`provider` all-or-none |
| Administrator session (cookie or bearer JWT, server edition) | `session_admin` | `user_id`, `user_email`, `role: admin`, `provider` |
| Tenant session (server edition, acting on their own servers/tokens/credentials) | `session_user` | `user_id`, `user_email`, `role: user`, `provider` |
| SSO callback provisioning a user or changing their groups (server edition; public route, no session yet, `setup.go:275-279`) | `session_user` / `session_admin` by the role derived at that callback | an explicit caller override built from the **verified** identity the callback just committed: `user_id`, `role`, `provider` of the stored record, and `user_email` only when it is a valid address (the store requires only a non-empty string, `users/models.go:53-68`, the schema says `format: email`), never from the empty AuthContext, which the shared helper would call `anonymous` |
| Public OAuth registration (`POST /oauth/register`) | `anonymous` | an explicit override: there is no credential by design |
| `require_mcp_auth: false`, no credential | `anonymous` | — |
| Offline CLI, core stopped | `cli_offline` (new) | — |
| No request; the proxy decided (policy, admission, startup reconcile, schedule) | `internal` | — |
| No request; the proxy observed a change it did not make (config file edit) | `none` (new) | — |

Activity `actor_kind` alignment: `api_key`→`api_key`; `socket`→`socket` (the activity layer also says `socket` for an agent token on the tray socket, `activity_actor.go:42-44`; the audit derivation keeps `agent_token`, which is more specific); `agent_token`/`oauth`→`agent_token`; `cookie`/`bearer_jwt`→`session_admin` or `session_user` by role; `anonymous`→`anonymous`; `cli_offline`→`cli_offline`; `system`→`internal`; no actor→`none` or `internal`. Native stdio has no activity spelling of its own (activity falls back to `api_key`); the audit line says `stdio`.

`session_user` is already legal on `auth_event`; this feature makes it legal on `admin_action` too (it stays forbidden on `authz`/`tool_call`). `none` and `cli_offline` are legal only on `admin_action`. A background line (`internal`, `none`, `cli_offline`) carries no identity key.

Every string goes through `maskCredential` and its length cap. PR-1 extends the fixed credential patterns (`internal/audit/redact.go:38`) with the proxy's own token shapes — `mcp_(agt|cli|oat|ort)_[A-Za-z0-9_-]{16,}`, long enough that a display `token_prefix` (8–16 characters in all) never matches — which today are not on the list; that change also protects `authz`/`tool_call` lines and the whole-line sanitizer pass, so a token value pasted into a name or an `X-Request-Id` is masked and counted. Masking is a pattern match and catches only recognisable shapes: a generated 64-hex API key pasted into a name or an `X-Request-Id` is not masked (`internal/config/config.go:1987-1998`). The guarantee is therefore scoped: **values** never enter a line (they have no path in); **labels** are recorded as chosen, pattern-masked. The label sources, by who controls them: administrator-chosen names (server, token, profile, registry, keyring entry, field paths under `env`/`headers`); caller-chosen strings (`request_id` from `X-Request-Id`, `client.name`/`client.version`; a public OAuth client's registration metadata is never on the line, only its assigned `client_id`); upstream-controlled names (tool, prompt and skill names in `target.names`). The audit-log page lists these sources and states the residual exposure: a secret with no recognisable shape placed into any of them reaches the audit file, as it already reaches the activity log and `authz` lines (which carry the same `tool`, `client` and `request_id` values today).

## Changes

`{field, before?, after?, withheld?}` — either a literal (`before`/`after`, a side that does not exist is omitted) or `withheld: "secret" | "value"` with no value and **no hash**.

- `field` is a dotted path from a fixed schema (`enabled`, `env.GITHUB_TOKEN`, `profiles.dev.tier`), never built from a value. A dynamic segment is allowed only where the classifier says so — map keys under `env`/`headers`, server names, profile names — and is masked. Below an **opaque** block that preserves arbitrary keys (the personal build keeps `server_edition` as raw JSON, `internal/config/server_edition_config_stub.go:35-56`) nothing is descended into: the change is reported at the nearest fixed parent (`{field: server_edition, withheld: "value"}`).
- **Literal** (value verbatim) — a field is literal only when the classifier table names it **and** the committed value converts to that field's closed wire set; a value outside the set (for instance an arbitrary string in `protocol`, which is a `string` in config, `internal/config/config.go:748`, and is not enum-checked on every write path, `internal/config/merge.go:214-219`) is `withheld: "value"`. Literal kinds: `bool`; a closed enum type (`protocol`, `trust_mode`, profile `mode`, tier caps, permission tiers); a bounded integer (rate limits, `max_*`, `*_days`, the **port** of `listen` — the host part is free text); a timestamp (`expires_at`); a display prefix (`token_prefix`, already shown in every token list); a count (`logins` removed by `client.forget`); a list of server or profile **names** (`allowed_servers`, profile server lists), capped like `target.names`.
- **Name lists** are reported as a diff, not as two sides: `{field, added: [...], removed: [...], added_count, removed_count, truncated?}` — so a list of 66 names that gains one shows exactly the one added name, and a capped side says how many it holds.
- Tool and skill approval hashes are **not** literal: they cover upstream-controlled descriptions, schemas and defaults (`internal/runtime/tool_quarantine.go:47-66`) and skill files (`internal/skills/hash.go:11-66`), which nothing proves secret-free. A `tool.approve` line names the tools and says nothing about their hashes; the activity row keeps them.
- **Withheld `secret`** — `env.*`, `headers.*`, `api_key`, `oauth.*` secrets, `oauth_token_encryption_key`, keyring values, and any value that is or resolves from `${env:}`, `${file:}`, `${keyring:}`.
- **Withheld `value`** — everything else: `url`, `command`, `args`, `working_dir`, the host of `listen`, descriptions, schemas, rule patterns, registry URLs. They can carry a credential with no recognisable shape (a positional password in `args`), so they get neither the value nor a fingerprint; the line says the field changed, and the activity row (admin-only, redacted best-effort) keeps the detail.
- The classifier is one table keyed by field path; an unknown path is `withheld: "value"`, a path under a secret-class prefix is `withheld: "secret"`.

## Size

A serialized line is at most **16 KiB**, not counting the newline the sink appends. Every name, field path and label is first capped at 64 characters (the mask's own 256-rune cap is the ceiling for other strings). Then, in order, until the line fits: `target.names` and literal name lists to 64 entries each; `changes` to 128 entries sorted by `field`; drop `changes` entries from the end; drop `target.names` entirely. `truncated` / `changes_truncated` are set whenever anything was dropped; `target.count` / `changes_count` always report the full set. With every list dropped, a line is bounded by its fixed keys and capped labels, well under the budget. The test asserts the final serialized byte length.

Each step that persists writes its own line at its own persistence point: at `Issue`, `client.create` (fresh mint) or `client.rotate_stage`, plus `client.bind` if the mint transaction changed an existing binding (`storage/client_credentials.go:208-231`); `client.bind` for a later binding write; `client.rotate_finalize` at finalize; at `Abort` of a fresh mint, `client.key_revoke` plus `client.bind` only if it actually restored a binding (`storage/client_credentials.go:573-592`) — never `client.forget`, grants are untouched; at `Abort` of a rotation, `client.rotate_rollback`; `client.bind` for a compensating restore. A config-write failure, a finalize failure and a failed compensation each leave exactly the lines of what persisted (tested). The client's **own** config file (the external file Connect installs, removes or restores, including the whole keyless branch, `internal/connect/connect.go:1266-1280`) is not a proxy access rule and is exempt; Connect's undo backup already records it.

## CLI ownership

Two questions, two mechanisms (round-4 finding: one lock cannot answer both).

**Who owns this data directory right now?** An **instance lock**, `<data_dir>/instance.lock`, exclusive and advisory, with a small owner record (`daemon` + pid, or `cli` + pid). `serve` takes it **before** it loads or saves the config (today `serve` saves a generated API key before it opens `config.db`, `cmd/mcpproxy/main.go:567-594,664`, so the `config.db` lock alone leaves a window) and holds it for its lifetime. A rule-changing CLI command that works without the daemon (`status --reset-key`, `telemetry enable|disable`, the config-only fallback of `upstream add`, `secrets set|del`, `upstream add` keyring flags, offline `connect`/`disconnect`, offline `upstream add|add-json|remove|import`) takes it non-blocking and holds it across its whole read-modify-write **and** its audit attempt. A probe that is released before the write would let a daemon start, or a second CLI, in between. Socket reachability is not the test: discovery can fall back to TCP or miss a live process (`cmd/mcpproxy/daemon_client.go:72-133`). Lock order is always instance lock, then audit-file lock.

- **Held by a daemon** → the change goes through the daemon (REST `PATCH /config`, `POST /secrets`, `POST /servers`), so the daemon's commit owns the line with the CLI's caller (`socket`/`api_key`, `client.surface: cli`). If the daemon cannot be reached, the command **does not mutate**: it exits non-zero with "core is running but unreachable" (a silent unaudited edit is the outcome this feature exists to prevent).
- **Held by another CLI command** → wait up to a few seconds, then fail with "another mcpproxy command is changing the configuration".
- **Free** → the CLI takes it, makes the change itself and owns the line as `cli_offline`, through its own file sink, only when `audit_log` is effectively enabled and has a `path`.

**Who may write the audit file?** Whoever holds an exclusive advisory lock on `<audit_log.path>.lock` — the daemon from before it opens a file sink until exit, an offline writer across its line. With the instance lock already held this lock never contends between a daemon and a CLI of the same data directory; it protects against two data directories configured with one audit path, and keeps rotation single-writer (the sink mutex is process-local, `internal/audit/sink.go:61-65`). A daemon with a stdout sink, with auditing off, or still writing to a path the config has since changed (the sink is restart-pinned, `internal/runtime/config_hotreload.go:529-541`) does not affect ownership — the instance lock decides that.

**The watcher** is an observer of edits no proxy process made (a hand edit, another tool). It debounces (`config_watcher.go:112-136`), so it records the net delta it sees as `caller.kind: none`, `trigger: config_file`, one line per changed target, not one per save. The watcher compares a change against the **last committed desired disk state** (by content hash), not against a time-limited self-write marker (markers expire, `config_watcher.go:141-150,252-265`): bytes equal to what the proxy last wrote — including the surviving bytes of a commit whose disk compensation failed, already recorded under rule 2 — are not counted again, however late the watcher sees them; an edit that restores the running value of a pending field (a reversal of a pending `audit_log` edit) is a real change against the desired state and is reloaded and recorded, even though it matches the published snapshot (today the watcher skips that case without reloading, `config_watcher.go:317-340`).

## Count invariant

`#admin_action == #committed effects` over the action list, counted in batch-key units for `tool`/`prompt`/`skill` targets and one per signed JWT for `jwt.issue`. A line exists only if the enabled sink's write succeeded; a failed write is counted (`WriteFailures`) instead. Holds with the event bus saturated.
