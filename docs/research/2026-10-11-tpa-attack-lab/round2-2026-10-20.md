## Part 2 — New findings (round 2)

### R2-1 (HIGH) — Auto-baseline poisoning: an unquarantined first-seen server's tools are approved with no scan

- **Mechanism**: the MCP-2931 trust-baseline model — a non-quarantined server
  whose tools have never been approved treats its CURRENT toolset as the
  baseline and auto-approves every tool (`approved_by: "auto-baseline"`) with
  **no operator action and no scan**.
- **Experiment** (`scripts/tpa-lab-redteam-round2.sh`, R2-1): the attacker ran
  with `quarantined: false` and the FULL 18-vector poisoned catalog
  (`--profile all`). Result:
  - all 22 tool rows `approved` (18 poisoned vectors + controls);
  - verbatim log: `New tool discovered, auto-approved {"tool": "summarize_text", "approved_by": "auto-baseline"}`
    and the same for `finance_convert_currency` (the blatant exfil imperative);
  - the poisoned `summarize_text` was **called successfully through the proxy**
    (its simulation report came back via `call_tool_read`);
  - only the operator-triggered `security scan` afterwards reported
    `dangerous` — i.e. detection exists but nothing invokes it before the
    tools are live, indexed and callable.
- **Reach**: any hand-written `mcp_config.json` entry with `quarantined: false`,
  or an operator who unquarantines before scanning. The entire hardened
  detection apparatus (detect engine, tpa-db, rug-pull gate) is bypassed by
  never being consulted on the first-seen contract.
- **Recommended fix**: gate the baseline auto-approval on the offline scan —
  run `scanner.ScanToolMetadataVerdict` on first-seen tools of an
  unquarantined server and only auto-approve when the verdict is `clean`
  (fail to `pending` on `warnings`/`dangerous`, exactly like the
  `trust_mode: scan` new-tool path that already exists). Alternatively,
  require one explicit operator approval for the first toolset of every
  server regardless of quarantine state.
- **Acceptance criteria**: R2-1 flips to HOLDS — with `quarantined: false`,
  `summarize_text`/`finance_convert_currency` land `pending` (or worse), are
  not indexed, and a call is blocked until approval; benign controls may
  still auto-baseline (or be approved in one bulk action).

### R2-4 (MEDIUM, offline) — Combining diacritics defeat the de-obfuscation pipeline

`combining-diacritics` (each vowel of a payload keyword followed by U+0301
COMBINING ACUTE ACCENT, e.g. "ígnore áll prévious") scans **clean** on the
override vector. Root cause: NFKC does not strip combining marks (it composes
precomposed forms), and confusable folding maps single-rune lookalikes — a
base+mark sequence is two runes. The exfil cases survive only via
`secret.embedded` on file paths (downgraded, not clean).
Fix: strip Unicode category Mn (nonspacing marks) in
`detect.NormalizeForPhrase` before phrase matching, with the existing
false-positive gates.

**On the P4 design limit (name squat).** The handoff asked for a soft finding
on a name-only collision "unless the description genuinely explains the
overlap". The review proves what MCP-3520 already argued: by name alone the
squat is indistinguishable from two honest servers sharing a compound name,
and *any* text-based exemption is attacker-controlled (the attacker picks the
server name and the prose). The shipped rule — own-server provenance in the
description — keeps the MCP-3520 *test* pair clean but not the live pair
(their real descriptions name no server), so on an install with both a soft
`shadowing.cross_server` finding appears on each `list_models` and, under P1,
the second server's tool lands pending once. The shape is therefore a review
hint that makes the lazy squat visible, not a boundary; the boundaries remain
admission quarantine, `server:tool` namespacing and server provenance in
`retrieve_tools`. Keeping it soft is the deliberate choice; whether to keep
the exemption, drop it (every distinctive collision reviewed once) or demote
the shape to `info` (no hold; the harness would report BYPASS again) is a
product decision for the maintainer.

### Considered, documented, not implemented

- **`llm_judge` backstop for uncovered languages.** The deterministic corpus
  now covers 15 languages; anything else (Arabic, Hindi, Vietnamese, Thai,
  Indonesian, …) still scans clean on a pure translation of the override. A
  backstop that sends only the *uncovered-script* clauses of a first-seen or
  changed description to an LLM judge (soft tier, review-only, never
  auto-quarantine) would close the long tail without new regex families. It
  is not trivial: it needs an opt-in config block (model, endpoint, budget),
  a prompt-injection-resistant judge prompt (the text being judged IS an
  injection), an offline/deterministic fallback for CI and the qapilot policy
  model, and a decision on whether a judge verdict may ever count toward
  `coverageOK`. Recommended as its own spec; until then the documented gap
  stands and `cmd/tpa-redteam` keeps measuring it (add a `translate-<lang>`
  mutation per language before claiming coverage).
- **Baseline hold on a whole server.** P1 holds per tool, so a server that
  ships one poisoned tool among benign ones gets the benign ones baselined.
  Holding the entire first toolset when any tool is `dangerous` is a
  one-line policy change (`baselineScanResult.holdFor`), left as is because the
  acceptance criteria allow benign controls to auto-baseline and the per-tool
  evidence tells the operator exactly which tools were refused.
- **R2-1's second reach — operator unquarantine before scanning.** The plain
  server unquarantine still promotes the server's pending tools as its
  baseline (`approveBaselineToolsForServer`, internal/runtime/tool_quarantine.go); the informed review
  (`security/approve` with `expected_hashes`, Spec 117 PR-2) is the path the
  Web UI and CLI use. Gating the plain door on the same scan is a separate
  change (server-approval semantics, Spec 109/117 callers) and is noted here
  rather than folded into P1.
